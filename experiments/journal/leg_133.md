**Date: 2026-08-06. Kind: regression check — standard. No figure, no new physics, and none
claimed.** `solver/boussinesq.py` read only, **edited under neither gate outcome**. No link

## Answer

**YES on both clauses.**

## The control, first — because every number above is a zero

Lesson 90: a control that cannot come out differently is not a control, and the tell is that
its numbers are identical. Four zeros in a row is exactly that shape, so the leg's first
obligation was to show the harness can still report non-zero.

PART 2 loads the **pre-repair module source** (git blob `af2772d…`, `git show
4959e6b:solver/boussinesq.py`) into a subprocess, grafts it onto the `solver` package as
`solver.boussinesq` *before* the battery imports it, and runs the identical 90 cases through
the identical classifier. It reports:

|---|---|---|

| secondary silent | 4 | **4** |

Not just the totals — **all 90 verdicts** match leg 89's banked artifact label by label. The

## Provenance: is the file on disk still leg 89's battery?

The repair commit `0c54d8a` **touched leg 89's battery file** (+1995 bytes). Checked rather
than assumed: splitting both revisions at `\ndef main(`, the **27886 bytes** above that line —
every case constructor, the verdict vocabulary, and the `run_case` classifier — are
**byte-identical**, sha256 `d0227e2c…` on both sides. The entire diff is a `"history"` block
inside `main()`'s payload dict. So importing `family_a…family_f` from `HEAD` *is* running leg
89's original battery.

Unlike leg 99's frozen driver (which leg 104 found dies with `KeyError: 'verdict'` post-repair),
leg 89's runs to completion, because `run_case` wraps every call in `try/except` and classifies
the exception as `RAISED`. A fix that converts silence into a `ValueError` moves a case between
verdicts rather than crashing the driver. This leg never calls the battery's `main()`, so leg
89's frozen artifact is never overwritten.

**Honest ceiling on independence:** reusing leg 89's classifier means the *verdict predicate* is
inherited, not independent. That is stated, not hidden, and PART 3 compensates with five defect
probes written from the defect descriptions in this leg's own code.

# BLOG

The worst thing a numerical solver can do is not to crash. It is to answer.

Leg 89 found `solver/boussinesq.py` doing exactly that, four different ways. The headline was
the ugliest: hand it a vorticity field that lives entirely above the 2/3 dealiasing cut —
`sin(15x)sin(15y)` on a 32² grid — and the mask annihilates it. What is left is roundoff:
a represented maximum vorticity of **1.797e-16**. The solver did not notice. It set its
blow-up threshold at a thousand times *that*, ordinary buoyancy forcing cleared the bar in a
single step, and the function returned `blowup_candidate` — the most consequential label the
module emits — off an amplification of **5.566e13**, computed from nothing but dealiasing
noise. Every field a caller reads to check validity looked perfectly healthy.

The repair landed, and it came with an audit saying no banked Phase-1 number was affected.
That audit was written by the repair. This repository learned at leg 60 not to let a fix be
the only witness for itself, so leg 133 went and checked.

The check has a shape worth describing, because "we found zero problems" is the easiest
sentence in the world to write and the hardest to trust. Everything this leg measured came out
zero: zero silent cases, zero contaminated call sites, zero banked numbers that moved. So
before believing any of it, the leg reached into git, pulled out the *broken* version of the
module, and ran the identical 90 tests through the identical classifier. It reported 19 silent
cases, 4 secondary, 13 masked NaNs — leg 89's original numbers, exactly, and matching all 90
verdicts label by label. The instrument still bites. Only then do the zeros mean anything.

The second thing worth saying is that "0 silent cases" was not the real test. Totals can stay
flat while individual cases quietly get worse. So the leg compared every case to leg 89's
record along a ladder of loudness — silent is quietest, a raised exception is loudest — and
asked how many moved **down**. Forty moved up. Fifty stayed put. **None moved down.** All
twenty-three formerly-silent cases now raise an exception that names what is wrong.

And a repair can regress in the other direction too: a guard that refuses real data is its own
kind of bug. So the new zero-vorticity guard was pointed at every initial condition the
Phase-1 record actually used, at every resolution. The least-resolved of them sits a factor
**1.0e+12** above the rejection threshold. Fifteen well-formed runs at n=32 are bit-identical
before and after — same float64 bit patterns, not "close". All four banked N=128 measurements
reproduce on all six of their recorded quantities, to zero difference.

That is the whole result: the severest finding of the audit run is closed, the fix took nothing
with it, and the 90 cases that caught it are now a permanent test that runs its own
falsifiability check every time. No physics moved. That was never on offer — this is a leg
about whether the instruments are honest, and today they are.

## §5 What this does and does not establish

It establishes that commit `0c54d8a` did what it claimed, measured from outside it, and that
the fix carried nothing with it. It does **not** establish that `solver/boussinesq.py` is
correct — the battery tests what the module does with *hostile* input, and
`test_boussinesq_dedicated.py` (17 checks, all passing) remains the well-behaved-input
validation. It adds no physics and moves no link of the chain.
