# Leg 121 — Route-CDA: adversarial audit of `solver/critical_dissipation.py`

**Branch** `leg/cda-v1`. **Agent** LEG-Q. **Date** 2026-08-06.
**Gate (verbatim).** *Under an adversarial battery of degenerate or poisoned inputs, does
`solver/critical_dissipation.py` ever silently return a wrong exponent instead of flagging
the input?*

## GATE ANSWER: **YES.** Escalated, not patched.

`solver/critical_dissipation.py` is untouched by this leg, under the gate's own instruction.
The headline case is precise, reproducible, and the corruption is at machine-precision
residual — the corrupted run does not merely look plausible, it is bit-identical to an
honest run of a *different* input.

**The exact failing case:** `CriticalDissipativeFlow(0.0, mu=0.1, p=1.9, K=64)`. The module's
own docstring states the precondition `p` a positive integer, `2s = p` — so `p = 1.9`
requests `s = 0.95`. `self.p = int(p)` silently builds `p = 1` (`s = 0.5`) instead. The Newton
solve converges to residual `9.71e-16` (machine precision — this is not an under-resolved
run), and `flow.alpha(b) = 1.0`, `alpha_slope(...)["alpha_1"]` are **bit-identical** to an
honest `p = 1, mu = 0.1` request. No exception, no warning, no field records the
substitution. The same holds one integer band up: requesting `p = 2.9` (`s = 1.45`) silently
builds `p = 2` (`alpha = 1.0897181208302058`, residual `1.4985625166838781e-05`, bit-identical
to an honest `p = 2` run); requesting `p = 3.9` builds `p = 3`
(`alpha = 1.172042517613463`, residual `2.880015486532439e-06`, again bit-identical).

## What the novelty pass changed about the leg

**It named the defect class instead of judging it by taste.** CWE-197 (MITRE, *Numeric
Truncation Error*) states exactly the failure this leg's headline demonstrates: casting to a
smaller/different primitive silently discards the information that distinguished the input.
A maintainer-acknowledged NumPy issue (`numpy/numpy#7730`) reports a researcher losing a
month tracking the identical shape of bug — a float silently truncated on assignment into an
integer-typed container — in the same numerical-Python ecosystem this repository runs on.

**It ruled out the obvious false-positive reading.** The published fractional-Laplacian
literature (Q3 of `writeup/novelty/leg_121.md`) treats the operator order as continuous over
`(0, 2)` or wider — none of it imposes an integer restriction, and one paper explicitly
generalizes to *variable*, space-dependent order. This module's `p` must be a positive
integer for a reason specific to its own construction (Route-E's compactified sine basis
makes `Lambda^p` an exact finite matrix only when `p` is a positive integer — see the
module's own "THE KNOWN ANSWER" docstring section), **not** a physical admissibility
boundary. That means a caller arriving from the wider literature has every reason to expect a
non-integer `s`/`p` to be legitimate input, which sharpens the finding rather than closing it
as "correctly refusing an invalid physics regime" (contrast leg 91's `s < 0`, which *was*
outside a published range).

**It explained the string/float asymmetry battery C4/E2 measures.** Python's `int()` gives a
float the "benefit of the doubt" (truncates its integer core) but gives a numeric string
none (raises on any non-integral literal) — so `p = '3.5'` is refused while `p = 3.5`, the
identical value as a float, is silently accepted and rounded down. The type that looks more
validated is the one that is actually more dangerous.

**It re-used, rather than re-derived, leg 91's sign boundary for `mu`.** `mu = nu / (A
L^{2s})` is the same physical quantity leg 91 audited as `nu` in `fractional_gclm.py`, carried
into Route-E's rescaled flow. The dissipative-gCLM corpus's `sigma = 2s >= 0` floor applies
unchanged; what was unknown before this leg is only whether *this* module was built with the
guard leg 91's escalation recommended. It was not.

## The nine batteries (`experiments/p2_route_cda_v1_adversarial.py`)

**C1 — `lambda_power` truncation.** 5 of 5 non-integral `p` values (`1.9, 1.0000001,
2.9999999, 2.9, 3.9`) accepted with no exception, silently floored to the next-lower integer.
Negative and sub-1 `p` (`-0.5, 0.5`) correctly raise `ValueError` — but only because `int(p)`
then lands below the `p >= 1` check, not because integrality is validated.

**C2 — THE HEADLINE.** Full pipeline (`CriticalDissipativeFlow` → `mu_branch` →
`alpha_slope`) at `a = 0`, `K = 64`, three integer bands. Every one of 9 tested non-integer
`p` requests (`1.1, 1.5, 1.9, 2.1, 2.5, 2.9, 3.1, 3.5, 3.9`) returns output **bit-identical**
to an honest, lower-integer `p` request, at the SAME machine/near-machine-precision residual
the honest request achieves. See the exact numbers in the disposition above.

**C3 — a realistic route to the same defect.** Nobody types `1.9` by hand; `p` is more
plausibly computed as `2 * s` from a fitted or subtracted float. `2.0 * (2.5 - 1e-12)` — a
magnitude of floating-point noise far smaller than any fit in this repository achieves —
gives `p = 4.999999999998`, and `int()` takes the floor: `4`, a full unit below the intended
`5`. (Two adjacent constructions, `5 * 0.1 * 5` and an accumulated sum of five `0.5`s, land
exactly on `5.0` in float64 and do **not** trigger the defect — recorded so the case is not
overstated: the near-miss depends on which direction the rounding error falls, not on every
arithmetic route to a half-integer.)

**C4 — the type-coercion asymmetry.** `p = '3.5'` (string) raises `ValueError`; `p = 3.5`
(float, the identical value) is silently accepted and truncated to `p = 3`. `p = '3.0'` also
raises (Python's `int()` refuses any non-integral string literal, including one that is
numerically an integer). `p = '3'` and `p = 3.0` are both correctly accepted.

**C5 — negative `mu` (anti-dissipation).** At `a = 1/2, p = 3` — the resonance where `alpha`
genuinely depends on `mu` (at `a = 0`, `alpha == 1` identically regardless of `mu`'s sign, so
it cannot show this) — the Newton continuation converges for `mu < 0` to a residual
comparable to the admissible branch's own, and returns a finite, structurally
indistinguishable `alpha`. (Regression-test resolution, `K = 48, da = 0.05`: worst residual
positive branch `1.65e-05`, negative branch `7.18e-06`, `alpha(mu=-0.2) = 3.09`. Production
resolution `K = 96, da = 0.02` banked in `writeup/data/p2_route_cda_v1_adversarial.json`.)

**C6 — `mu_decay_time` domain violations.** The formula assumes `0 <= target < mu0`. None of
the three is checked. `target > mu0` (asking for the time to decay to a *larger* value, which
is meaningless under `mu_tau = -alpha_1 mu^2 < 0`) silently returns a **negative** time
(`-23.08` against the control's `+346.15`). So does a negative `target` on its own
(`-423.08`). A negative `mu0` is silently accepted and returns a plausible-looking
*positive* time (`+423.08`) with no domain check anywhere.

**C7 — `marginal_verdict` on non-finite `alpha_1`.** `alpha_1 = NaN` — which can legitimately
arise upstream (`test_critical_dissipation.py`'s own test 10 documents that `alpha_slope`
"cannot know" when its fit is residual-dominated) — gets the definite classification
`"dissipation_runs_away"` rather than an exception or an explicit "undefined" outcome.
`alpha_1 = +inf` reads as `"relaxes_to_inviscid"`, `alpha_1 = -inf` as
`"dissipation_runs_away"`. The three finite branches remain correct.

**C8 — `amplitude_eigenvalue` sign, reported at honest strength.** The module's own docstring
already says this formula is *"AN EMPIRICAL FIT ... AND IS NOT DERIVED ... because it is
gated, not because it is understood."* `mu = -0.1` (inside the real branch) is silently
accepted and returns a finite, unphysical eigenvalue (`-0.7746`) with no domain check;
`mu = -0.3` (past the real branch) correctly propagates as `NaN` with a `RuntimeWarning` — the
module gets the harder case right. Recorded as the weakest finding of the battery, not
inflated.

**C9 — positive controls, recorded as loudly as the failures.** `lambda_power(K, p)` for
`p ∈ {0.5, 0.999, -0.5, -3, 0}` correctly raises `ValueError`, 5/5. `p = '3.5'` (string)
correctly raises. `amplitude_eigenvalue(-0.3)` correctly propagates NaN with a warning.

## Downstream exposure — measured, not asserted

24 call sites of `CriticalDissipativeFlow`, `mu_branch`, `lambda_power` or
`dissipative_spectrum` outside `solver/critical_dissipation.py` and its own test file were
grepped and inspected by hand: 6 in `solver/marginal_flow.py`, 7 in `test_marginal_flow.py`,
1 in `experiments/p2_route_mfg_v1_adversarial.py`, 4 in
`experiments/p2_route_h_v1_critical.py`, 6 in `experiments/p2_route_i_v1_driven.py`. **Every
one passes `p` as a literal integer (`1`, `3`, `5`) or a name that traces back to one**
(`self.p`, `A.p`, `CRITICAL_POINTS`'s `P_CRIT`, or a function parameter `p` whose own
callers are themselves literal integers; `solver/marginal_flow.py:576` even performs an
explicit `p=int(p)` cast of its own, the identical pattern, one level up).
**Zero call sites in the repository currently compute `p` arithmetically from a float.**

> **BANKED NUMBERS AT RISK: 0.** `alpha_1 = 0` at `a=0`, `sigma=3` at `a=1/2`, and
> `alpha_1 = +0.133683` at `a=1/2` (all per `capabilities.py`) all trace to hardcoded integer
> `p`. C1/C2/C3 are **LATENT** — exactly the severity shape legs 66, 69, 79 and 120 measured
> for their own findings — but C3 shows the arithmetic mistake that would trigger it is
> ordinary float64 rounding, not a contrived construction, so the latency is fragile against
> any future caller who computes `p` from a fitted `alpha` rather than a literal.

## Disposition

**ESCALATE. Do not patch under this leg's authority.** `solver/critical_dissipation.py` is
byte-identical to `origin/main`; this leg's territory forbids editing it under any outcome,
and the yes-branch says escalate. The repair, when authorised, is small and is **not** this
leg's to make: validate that `p` is (already) integral in both `lambda_power` and
`CriticalDissipativeFlow.__init__` (e.g. `if float(p) != round(float(p)): raise ValueError`,
before the existing `p = int(p)`); validate `mu >= 0`, matching the guard leg 91's escalation
already put on `fractional_gclm.py`'s `nu`; validate `0 <= target < mu0` in `mu_decay_time`;
and have `marginal_verdict` raise (or return an explicit sentinel) on non-finite `alpha_1`.

`test_critical_dissipation_adversarial.py`'s six `PIN:`-marked checks (E1a, E1b, E2, E3, E4,
E5, E6) will start FAILING the day any of these guards lands — that is the intended signal,
and the pin should be updated in the same commit as the repair, per legs 66/91/120's
precedent. C9's controls and the three finite-`alpha_1` cases in E6 are ordinary regressions
and must not regress.
