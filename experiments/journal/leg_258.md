Per the thesis's own principle — "a floor that is breached invites an exception" — the floor is
encoded now, while it holds, rather than after a future breach.

## What was built

1. **A machine-readable marker in `DIRECTION.md`**, added directly under the file's front matter
   (before the existing `## Status` section), fenced by `<!-- FLOOR-TABLE-START -->` /
   `<!-- FLOOR-TABLE-END -->` HTML comments. It is a 10-row pipe table (`Slot | Leg | Route |
   Eligible`) carrying only a `yes`/`no` eligibility snapshot per slot, prefaced by one paragraph
   asking the DM to keep it in sync with the prose "Live-slot roster" table on every
   refill/promotion that changes a slot's occupant or type. It states the same facts already in
   this file's own prose (no new source of truth), and is deliberately small and flat so the DM's
   maintenance burden per update is one row edit, not a re-derivation.
2. **`parse_floor_table(text)` in `test_plan_of_record.py`**: extracts only the text between the
   two HTML comments, walks its pipe-table rows (skipping the header and the `---` separator),
   and returns `(total_slots, eligible_count)` by counting rows whose fourth cell is exactly
   `yes`. It never looks outside the marker block, so it is insulated from `DIRECTION.md`'s
   ~10,000 lines of freely-evolving prose (the leg's explicit non-goal: no prose parsing).
3. **`test_9_composition_floor_is_met`**: reads the real `DIRECTION.md`, asserts `total == 10`
   and `eligible >= 3`.
4. **`test_10_composition_floor_parser_rejects_a_breached_fixture`**: builds a hand-written
   10-row table with exactly 2 `yes` rows (a fixture string, not a real-file edit), runs it
   through the same `parse_floor_table`, and asserts the result is `(10, 2)` with `2 < 3` —
   proving the same threshold check the real test uses actually discriminates a breach from a
   pass, rather than passing vacuously.

## Gate answer

  fixture returns `eligible == 2`; the same `assert eligible >= 3` used by test_9 raises
  `AssertionError: BREACH: 2/10 < 3` when run against it (checked interactively before
  committing test_10, and test_10 itself asserts `eligible < 3` on the fixture as a standing
  regression check).
- **(b) Passes against the current roster:** `test_9_composition_floor_is_met` reads the live
  `DIRECTION.md` marker and finds `total == 10`, `eligible == 3`, satisfying `eligible >= 3`.
- **(c) Runs inside the existing merge gate without touching any other test's behavior:** all
  10 functions in `test_plan_of_record.py` (the original 8 plus the 2 new ones) pass; no
  existing assertion was edited, weakened, or reordered. `scripts/merge_gate.sh origin/main`
  confirms this (see the commit this leg lands with).
