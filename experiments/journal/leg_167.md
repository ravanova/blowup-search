## 1. The novelty pass changed the leg, three times

Recorded because the value of running it first is the whole reason the rule exists.

**F1 — leg 115's own runner ABORTS against the repaired module, on its first probe.**
`experiments/p2_route_dca_v1_adversarial.py` dies at line 114 with
`DecayCollocationDomainError: gauged_jacobian: J = 1 ...`, inside the *first* G1 probe, so it
never reaches G2 or G3 at all. Leg 147 named this shape ("the repair landed a guard the battery
could not run past and nobody noticed"); leg 131 found it too. **Three for three — it is a
property of repair legs in this repo, not an accident.** Consequence: every case here is
classified **per case**, in its own `try/except`, into `REFUSED` / `FLAGGED` / `SILENT_VALUE`.
A raise is *data*. A driver inheriting leg 115's control flow would have reported "0 cases
checked" and could have been mistaken for a pass.

**F2 — the on-disk battery is not leg 115's battery.** `git diff --stat 53f03fe 746c57a --
test_decay_collocation_adversarial.py` → **191 insertions, 91 deletions**: leg 151 inverted all
7 of leg 115's pins *in the same commit as the repair*. It prints 15/15 passing today, and its
own trailer says why. Running it is the repairer grading its own homework — **lesson 90, a
control that cannot come out differently.** Consequence: every case here is re-derived from the
battery **and** the runner as they stood at **`53f03fe`**, read out of git.

**F3 — clause (b) must be same-process, not JSON-versus-JSON.** Leg 105 measured a ~2.1%
discrepancy against a committed JSON that turned out to be environment drift predating both
repairs; leg 147 saw 22/763 leaves move ≤3 ULP with 6 on paths that never touch the module.
This matches the literature's own split: bitwise identity is achievable *between versions of
the same implementation*, not *across environments* (WG21 P3375R3; Demmel et al., ACM TOMS
`10.1145/3389360`). Consequence: the pre-repair module is loaded out of git at **`a595dcb`**
into the **same interpreter** as the shipped one and compared at **0 ULP**.

`git log --oneline main -- solver/decay_collocation.py` returns exactly two commits — `a595dcb`
(creates) and `746c57a` (leg 151 repairs) — so the pre/post boundary needed no judgement call.

## 2. Clause (a): 76/76 refused, against a control that refuses 0/76

Cases are the **union** of leg 115's battery and its runner at `53f03fe`, deliberately, because
the two do not agree: the battery's G3 list is 4 complex alphas and the runner's is 6 (it adds
`1.0+0.0j` and `1.5+1e-10j`). Using either file alone would have skipped two cases leg 115
banked.

| | cases | post-repair | pre-repair control |
|---|---|---|---|
| **G1** J=1 grid collapse | 32 | **32 REFUSED**, 0 flagged, 0 silent | 0 refused, 0 flagged, **32 SILENT** |
| **G2** `sup_op_norm` 1-D axis swap | 31 | **31 REFUSED**, 0 flagged, 0 silent | 0 refused, 0 flagged, **31 SILENT** |
| **G3** complex `alpha` | 13 | **13 REFUSED**, 0 flagged, 0 silent | 0 refused, **13 flagged**, 0 silent |
| **ALL** | **76** | **76 REFUSED, 0 SILENT** | **0 refused, 63 SILENT** |

All 76 refusals are the module's **own** `DecayCollocationDomainError` — checked by type, not
just by "something raised". A bare `ZeroDivisionError` or a NumPy shape error would be a refusal
by accident, and none occurred.

**The control is the point, and it could have come out differently.** The identical case lists
bound to the pre-repair module in the same process refuse **nothing**, and reproduce leg 115's
banked corruption: the J=1 collapse to `1.681792830507429` for every `c` including `nan`/`±inf`,
and the G2 axis swap returning `12.0` where the caller meant `10.0` — both bit-exact.

**No over-refusal, measured not assumed.** 0 of 8 probes failed to return a clean value: the
unambiguous `(3,1)` column spelling still returns `10.0`; real alphas as `float`, `int`,
`np.float64`, `np.int64` all still answer; `J ∈ {2,8,16}` all finite. In the banked suite,
additionally, all 16 gauge × in-range-`drop` combinations at `J=8` still build, and the guards
fire on **0 of 64** shipped configurations. Leg 115's own `J ≥ 2` CONTROL survives intact: a
poisoned `c` still **propagates to NaN** rather than being refused, at every `J ∈ {2,3,4,8,16}`
— so the guard is about `J = 1` specifically and was not over-broadened into a general NaN
check, which is the obvious way this repair could have been wrong and was not.

### 2.1 G3 is `FLAGGED` rather than `SILENT` only because the harness forces it

Honest reading of the one asymmetry in the table. `classify()` runs under
`warnings.simplefilter("always")`, which is the **generous** setting — it lets NumPy's
`ComplexWarning` count as a flag. That is not what a caller sees, so the claim was measured at
all three filter settings on the pre-repair module rather than repeated from leg 115:

| filter | calls | warnings surfaced | returned an ordinary finite float | exceptions |
|---|---|---|---|---|
| `always` (what `classify()` forces) | 6 | **6** | 6 of 6 | 0 |
| **`default` (production)** | 6 | **1** | 6 of 6 | 0 |
| `ignore` | 6 | **0** | 6 of 6 | 0 |

**Under Python's default filter, six corrupt calls surface one warning** — the default action
reports once per call site, so 5 of the 6 are entirely silent — **and all six return an
ordinary finite float at every setting, with zero exceptions ever raised.** So G3's 13
"FLAGGED" entries are not a disagreement with leg 115's "silent corruption" verdict; under the
caller-visible criterion that matters (does an ordinary-looking number come back?) they are the
same finding, and leg 115's characterization is confirmed with a magnitude rather than assumed.
Reported this way rather than folded into the silent count, because the gate's wording admits
flagging and it would be dishonest to score G3 as silent under a filter setting that did not
produce it.

## 3. Clause (b): 24,370,487 leaves, 0 moved

Same process, same interpreter, same NumPy 2.5.1, both modules live at once. Instrument:
**sha256 over the raw IEEE-754 bit patterns** (`uint64` view), which compares NaN payloads and
distinguishes `-0.0` from `0.0` — not `allclose`, and not `==`.

| arm | measured |
|---|---|
| public-surface sweep | **2,491 / 2,491** quantities, **24,370,487 / 24,370,487** float64 leaves bit-identical, **0 moved** |
| `capabilities.py` validated line (`test_decay_collocation.py`) | passes; **stdout byte-identical** pre- vs post-repair across all **6** gates |
| inheritance arm (`ACollocation`, `solver/collocation_newton.py`, not edited by leg 151) | **133,896 / 133,896** leaves bit-identical |

Coverage was **enumerated from the module's public surface here, not inherited from leg 151** —
that is where the independence lives, since re-running leg 151's own quantity list would
inherit whatever leg 151 did not look at. It spans `grid`, `transforms`, `H`, `D`, `transport`,
`anchor`, `residual`, `jacobian_matrix`, `dc_column`, `quadratic`, both weights, both norms,
`gauged_jacobian`, `graded_inverse_norm` and `sup_op_norm`, over `J ∈ {2,3,4,8,16,32,64,128,
256,400}` with full matrices and `{512,800,1000}` vector-only, 10 alphas, 4 speeds, both gauges
and 4 `drop` values. For scale, leg 151 reported 1,672 quantities; this is 2,491. **The larger
number is not a better result** — it is a differently-chosen one, which is the entire point.

The validated line's stdout being byte-identical is the strongest single item here: those six
lines print *measured numbers*, so it says every number the repo's own known-answer gate
reports is unmoved, which is more than "both passed".

**Declared limit, stated rather than hidden.** The `O(J³)` inverse arm is swept in full only to
`J = 400`; above it the alpha set is reduced to `{0.0, 1.5, 3.0}` and the `drop` set to
`{0, J−1}`. Every *cheap* quantity is swept at every `J` with the full 10-alpha set. This is the
same shape as leg 151's own declared cap (its inverse arm stopped at `J = 1000` while its cheap
arm reached `J = 2000`).

## 4. Two findings the gate did not ask for

### 4.1 One of leg 115's three banked headline values does not reproduce — by 1 ULP, and it is not a regression

| banked | leg 115's JSON | live here (PRE-repair) | drift |
|---|---|---|---|
| G1 `J=1` collapse | `1.681792830507429` | `1.681792830507429` | **0 (bit-exact)** |
| G2 worked case | `12.0` | `12.0` | **0 (bit-exact)** |
| G3 end-to-end | `3.5626111859714866` | `3.562611185971488` | **1 ULP, `3.7395818965489845e-16` relative** |

**It is not a regression: the PRE-repair module produces it**, so the drift predates leg 151's
patch entirely. The mechanism is exactly the one the other two escape — G1's value inverts a
1×1 and G2's is a plain sum, while this one passes through `np.linalg.inv` on a 16×16, i.e.
LAPACK, whose last bit is not fixed across library builds. **Leg 151's own commit message
quotes the drifted `3.562611185971488`** without flagging that it disagrees with leg 115's bank.

This is the **third independent confirmation** of the leg-105 / leg-147 phenomenon, and it is
the empirical vindication of novelty finding F3: in one process both arms share one LAPACK and
the drift cancels identically, which is why clause (b) reports 0 moved out of 24.37M.

It also caught a flaw in *this leg's own first draft*: the runner's control initially demanded
this value match bitwise, and therefore printed `clause (a) = NO` on a run whose measurement was
76/76 refused. **That NO was the comparison's arithmetic, not the module's behaviour**, and it
is recorded here rather than quietly corrected. Both the runner and the suite now compare this
value to a tolerance (`1e-14`, ~45 ULP of headroom around the 1 ULP observed) and pin the other
two bitwise. Pinning it exactly would make the permanent suite fail on a different LAPACK build
— a statement about the build, not about the repair.

### 4.2 The BLAS thread pool made a generic 400×400 inverse 60× slower, and pinning it is a correctness fix before it is a speed one

With four legs running in parallel on this box, `np.linalg.inv` on a 400×400 took **3.5 s**;
pinned to one thread it took **0.0589 s**. The first measurement was not a property of this
module — a *generic* random 400×400 inverse showed the same 3.7 s — it is thread
oversubscription across concurrently-running legs.

The reason it belongs in the journal is not the speed. **Multi-threaded BLAS chooses its
reduction order dynamically, so the last bit of a dot product can depend on how many threads
happened to be free.** Clause (b) asserts 0 ULP, so the reduction order has to be *fixed by
construction, not likely to repeat*. The runner therefore pins
`OMP/OPENBLAS/MKL/NUMEXPR/VECLIB` thread counts to 1 before NumPy loads, and the two
validated-line subprocesses inherit it — which is what makes their stdout comparable byte for
byte rather than racing. Worth knowing for any future leg that asserts bitwise identity while
the orchestrator is running four legs at once.

## 5. What this does NOT establish

Per the published limitation of golden-master / characterization testing (Feathers; novelty
pass Q1), and stated in the JSON itself: **golden master does not infer correctness.** A 0-ULP
result says **the repair moved nothing**. It does **not** say any banked number is right. The
`Z1`-analogue truncation error this module's own docstring declines to bound is exactly as
unbounded after leg 151 as before it, and nothing here touches it.

Nor is any bound sharpened, any constant improved, or any link of the L1→L4 chain moved. The
in-repo base rate for this method is now **1 incomplete fix in 13** (leg 147 remains the only
NO), against a published 22–33% supplementary-fix rate (Park et al., MSR 2012) and a 6–10%
reopen rate — this repo continues to run better than the literature's prior, which is a fact
about a small sample and is not claimed as more.
