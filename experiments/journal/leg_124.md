## Why the obvious battery would have been wrong, and what replaced it

The first instinct for `K` is "run the solver at every `K` and see if the residual it reports
disagrees with an analytic answer" — but there is no analytic answer here (the module's own
docstring says it has never converged at any `K`, and that remains true: the default `K=24,
a=0.5` case reproduces the docstring's own claim, `converged=False`, residual 0.65, `Xc=2.67`,
matching the order the docstring records). Scoring against "did it converge to the right
answer" is not available. What **is** available, and what the battery actually does, is to take
the module at its own word — `converged: True` claims the equation is satisfied — and check
that claim against the SAME equation, evaluated by a SECOND, independently-constructed
`FiniteSupportOps` at a fixed set of interior points the Newton iteration never touched. A
correct `converged: True` should show a small residual there too, by the continuity of the
underlying integral equation; a false one should not, and at degenerate `K` it does not, by up
to 15 orders of magnitude (`K=1, a=0.5`: reported residual 5.55e-17, independent residual
3.30e-01, `K=4, a=0.3`: independent residual 3.71e+00).

The same discipline applies to `c`: rather than assert "Newton shouldn't converge here", the
battery checks whether the `Xc` it lands on is a physically meaningful finite-support radius or
the algebraically trivial `Xc = 0` root that the free-boundary equation admits for any `b` when
`c` is small. It is the latter, sharply, for `|c| <= 1e-9` and not for `|c| >= 1e-8` — a
boundary set by measurement, not chosen to make a nice story.

## Result — three mechanisms, all independently verified

### F1 — degenerate `K` reports false convergence (14/27 cases, sharpest at `K=1`)

`FiniteSupportProfile`'s collocation node count is `K - 1` (`solver/finite_support.py:258`). At
`K = 1` that is **zero**: `self.v` is an empty array, so `ops.residual` — the actual PDE row —
is evaluated **zero times**, and the (K+1)-unknown system is constrained only by the gauge
condition and the free-boundary condition. Newton nonetheless reports:

| `a` | `K` | nodes | reported `converged` | reported residual | independent off-node residual |
|---|---|---|---|---|---|
| 0.5 | 1 | 0 | **True** | 5.55e-17 | **3.30e-01** |
| 0.3 | 2 | 1 | **True** | 5.55e-17 | **7.12e-01** |
| 0.3 | 4 | 3 | **True** | 5.77e-15 | **3.71e+00** |
| 0.8 | 2 | 1 | **True** | 1.67e-16 | **2.17e-02** |

8 of 9 tested `(a, K)` combinations at `K ∈ {1, 2, 4}` are silent by this criterion; larger `K`
(6, 8, 12, 16, 24) correctly report `converged: False` at every `a` tested, matching the
module's own known non-convergence.

### F2 — near-zero `c` collapses to the trivial zero-radius root (30/57 cases)

`edge_condition(b, Xc) = c + a·Xc·(-U1·b)` admits the algebraic root `Xc → 0` for any `b`
whenever `c` is small, because every term scales with `Xc`. Measured at `a ∈ {0.3, 0.5, 0.8}`
over 19 values of `c` each:

| `|c|` | `converged` | `Xc` |
|---|---|---|
| 1e-8 | False | 1.38e-11 |
| **1e-9** | **True** | **2.25e-12** |
| 1e-10 | True | 6.85e-13 |
| 1e-14 | True | 7.38e-15 |
| **0.0 (exact)** | **True** | **4.03e-15** |
| -1e-9 | True | 2.28e-12 |

The boundary is sharp and reproducible across all three `a` values: silent at `|c| ≤ 1e-9`,
flagged at `|c| ≥ 1e-8`. `c = 0.5`, the module's own default and the value used everywhere else
in this file's docstring, is nowhere near the collapse zone.

### F3 — out-of-domain `v` treated three different ways in one call (6/6 `a` values)

`FiniteSupportOps.fields`, evaluated at `v > 1` — outside the module's own declared domain
(its docstring: "The profile on its own support: `[0, X_c]`" in the scaled variable "`v` in
`[0,1]`"):

- **`U`** (`Utilde`, via `np.interp`) **silently clamps** to the `v = 1` boundary value for
  every `a` tested, with zero warnings — `numpy.interp`'s documented default
  (https://numpy.org/doc/stable/reference/generated/numpy.interp.html: *"value to return for
  `x > xp[-1]`, default is `fp[-1]`"*), which `FiniteSupportOps` never overrides or guards.
- **`f`**'s weight power `(1 - v²)^p` is computed on the RAW, unclipped `v` (line 176), while
  `even_cheb`'s polynomial part uses the internally CLIPPED angle. When `p = 1/a` is an exact
  integer — `a ∈ {0.5, 1.0, 0.25, 1/3}`, giving `p ∈ {2, 1, 4, 3}` — a negative base to an
  integer power is well-defined and `f` returns a finite, WRONG, unwarned extrapolated value
  (e.g. `a=0.5, v=50`: `f = -6,245,001`). For non-integer `p` (`a ∈ {0.3, 0.7}`) the identical
  line instead raises `RuntimeWarning` and returns `NaN`. **Whether this is silent or loud is
  an arithmetic coincidence in `a`, not a property of whether the input was valid.**
- **`H`** alone reliably goes non-finite via its `log(v/(1-v))` term, regardless of the parity
  of `p` — the one field of the three that flags the violation every time.

All 6 `a` values tested produce at least one silently-wrong field.

### The controls, recorded as loudly as the failures (0/10 unexpected)

`a = 0.0` → `ZeroDivisionError`. `K = 0` → `IndexError`. `K = -3` → `ValueError`. `N = 0` →
`ZeroDivisionError`, both via `cheb_quad(0)` directly and via the `FiniteSupportProfile`
constructor. `max_iter = 0` → `IndexError` (inelegant, but loud). `a ∈ {-0.5, NaN, +Inf, -Inf}`
propagates NaN through every downstream field and reports `converged: False` at every one —
never a false success. All ten controls behaved exactly as a correctly-flagged input should.

## What is banked, and what a repair should do

- `test_finite_support_adversarial.py` — 13 permanent checks, 6 marked `PIN:` (F1's two false-
  convergence pins, F2's collapse and boundary-sharpness pins, F3's `U`-clamp and `f`-parity
  pins), 7 controls. **The PIN checks will start FAILING when a repair lands** — that is the
  intended signal, per leg 66/120's convention, and the pin should be updated in the same
  commit as the repair.
- The repair itself is **not this leg's to make** (read-only territory under every outcome; the
  module is also already superseded, so any repair effort is a judgement call for whoever picks
  this up, not an obligation this leg creates): `solve()` could refuse or flag whenever the
  collocation node count (`K - 1`) is too small relative to the free parameters to constrain the
  physics at all, or could cross-check its own residual against held-out points before reporting
  `converged`; the free-boundary condition could reject or flag `Xc` collapsing below some floor
  relative to the requested scale; and `FiniteSupportOps.__init__` could validate `v_eval ∈
  [0,1]` once, centrally, rather than leaving three downstream fields to handle (or not handle)
  the violation independently and inconsistently.

## Honest limits

- Every number here is a statement about **code behaviour** in a file the module's own docstring

  repo-wide import grep returning zero hits is not a inference, it was run and its output

- F1/F2's severity is a statement about what this code DOES, not about how likely a caller is to

  active, the same shape as legs 79, 92, 99, 103, 120.
- F3's `f`-silent-iff-integer-`p` finding depends on `a` landing on a reciprocal integer; this
  was tested at four such values (`0.5, 1.0, 0.25, 1/3`) and two non-integer values (`0.3,
  0.7`), not swept continuously — the boundary between "silent" and "loud" is the arithmetic
  fact "is `1/a` an integer", not a numerical threshold that could shift under refinement.
- The K1/K2/K4 false-convergence finding does not contest that collocation methods only check
  their own nodes (Q1/Q2 of the novelty pass settle that this is the method's own contract, not
  a fault); what is pinned is narrower and specific to this file — that `solve()`'s own
  `converged` flag does not distinguish an under-determined system from a solved one.
