## 1. The methodological finding, which came from the novelty pass and not from the numbers

The bench repair **edited leg 107's own runner in place** (61 lines of
`experiments/p2_route_fia_v1_adversarial.py`), threading the explicit legacy policies
`on_outside="extrapolate"` / `on_nonfinite="drop"` through every call that leaves the
support, plus a module-level `warnings.simplefilter("ignore", FirstIntegralGuardWarning)`.

That is a defensible choice — it is *why* leg 107's escalated numbers still reproduce —
but the consequence is precise and it is the reason this leg exists:

> **The runner now on `main` cannot detect the repair.** It asks the repaired module for
> the pre-repair arithmetic, so it reports 96/96 fabricated and 397/400 absorbed whether
> or not the fix is present. Running it and finding leg 107's numbers proves nothing.

This is lesson 90 in a new place: a control that cannot come out differently. So "leg
107's original battery" is taken here to mean **literally leg 107's file, read out of git
at `5e03e13`**, executed unmodified, with every call going through the module's **default**
policy path — the path every real caller takes. It is bound to a module by substituting
`sys.modules["solver.first_integral"]`, so one battery source runs against both modules in
one process. `main()` is never called: it would write leg 107's JSON, which is leg 107's
territory.

**The harness's own honesty check** (`test_2` of the banked suite): the same battery bound
to the pre-repair module must still report 96. It does, exactly, with the largest
fabricated value `|Ω| = 300.3747299832893` reproduced to every digit. If that control ever
stops firing, this suite has gone vacuous.

## 3. Clause (b) — bit-for-bit, and why never against a banked JSON

Pre-registered in `writeup/novelty/leg_135.md` §3(i) **before any number was seen**: leg
107's runner already documents that the *pre-repair* module gives
`X_c = 18.715770556159065` at `OMP_NUM_THREADS=1` and `18.71577055615906` at 4 threads — a
last-ULP Newton difference propagating into everything derived from `b`. A JSON diff
therefore measures the BLAS thread count. (Leg 105 hit the identical trap at `Y_0 ~ 3e-17`
and named it; this is its second independent occurrence, on a different module.) So every
comparison here loads both modules into **one interpreter** and runs them back to back.

**In-support surfaces, on grids deliberately disjoint from the bench check's own**
(`a ∈ {0.2, 0.35, 0.45, 0.6, 0.75}` vs the bench's `{0.25, 0.3, 0.5, 0.8}`;
`K ∈ {32, 56}` vs `{48, 64, 96}`), 15 surfaces per `(a, K)`: `solve.b`, `solve.Xc`,
`solve.residual`, `omega_of` on the graded nodes, `omega_of` and `e_of` on
`linspace(0,1,401)`, `even_cheb`'s `T` and `dT` on 997 Chebyshev points, `residual`,
`jacobian`, `mass`, `edge_amplitude`, `operator_norm`, `predicted_radius`,
`outer_velocity`.

> **916,440 values compared. 0 bit-differences. 0 spurious warnings.**

Comparison is on the `uint64` bit pattern, so `-0.0 ≠ +0.0` and `NaN == NaN` — which
matters, because `linspace(0,1,401)` **hits `v = 1` exactly** and `omega_of(1)` is `-0.0`.
The signed zero at the support edge is bit-preserved. This is an independent measurement
of the same quantity the repair self-reported as 860,200 values over 19 surfaces at 5
values of `a`; it is not the same measurement, and it agrees.

The clean `first_integral_defect` on 400 finite points: `6.217248937900877e-15` on both
modules, 0 bit-differences, 0 warnings.

**Module gates (part D).** `test_first_integral.py` on current `main`: **11/11 checks over

## 4. The surface the repair's own driver never ran, and what it turned out to be

The novelty pass registered a falsifiable prediction (§3(ii)) before measuring:
`solver/reduced_certificate.py` is the one *other solver module* consuming the guarded
API, and the bench check's A/B enumerates only the `p2_route_d_v14` call sites. Both
`even_cheb` and `e_of` had their **default** changed to return `NaN` outside the support,
so any site handed `|v| > 1` would silently turn a finite certificate number into `NaN`,
and nothing on `main` would catch it.

Measured, by instrumenting the current module and running `rehearsal(a, K=48)` for
`a = 0.3, 0.5`:

* **16 calls** — `even_cheb` ×10, `e_of` ×6.
* **Largest `|v|` ever presented: `even_cheb` `1.0` exactly; `e_of` `0.9999999999`.**
* **0 guard warnings raised. 0 of 16 compared fields differ by a bit** — `Xc_over_c`,
  `newton_residual`, `Y0_interpolant_defect`, `Z0`, `opnorm`, and the 3-rung
  `N2_sup_by_cutoff` ladder, at both `a`. `Y_0 = 9.140636e-08` / `1.931983e-08` and
  `‖A‖ = 4.513295211` / `2.212671574`, pre and post identical.

**The prediction resolves clean — but with zero margin, and that is the finding.**
`reduced_certificate.py`'s largest argument is `v = 1.0` **exactly**: it sits *on* the
boundary, not comfortably inside it. The repair's guard fires at `|v| > 1 + 4ε` and its
commit message records the reason — "`e == 0` is the support EDGE and stays inside, so the
sign of the zero at `v = 1` (which one banked call site hits exactly) is untouched". That
decision, made for a `p2_route_d_v14` call site, is what keeps a **second, unexamined
module** finite: a guard written as `|v| >= 1` would have turned `reduced_certificate`'s
`Y_0` into `NaN`, and the repair's own A/B would not have seen it. The margin is `4ε ≈
8.9e-16`. Recorded, not patched — the repair is correct as written; what is worth banking
is that its correctness at this call site was not *demonstrated* by anything before now.
