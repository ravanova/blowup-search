# Leg 118 — Route-TPA: adversarial audit of `solver/turning_point.py`

**Date:** 2026-08-06. **Branch:** `leg/118-tpa-v1`. **Module under test:**
`solver/turning_point.py`, **READ-ONLY — byte-identical to `origin/main` on this branch.**

**Gate, verbatim from `DIRECTION.md` §118:**

> **Gate.** Under an adversarial battery (degenerate branches, poisoned derivatives), does
> solver/turning_point.py ever silently return a wrong classification instead of flagging the
> input?
>   yes -> Silent-corruption gap; report the exact failing case; escalate, do not patch.
>   no  -> Confirmed robust; bank the battery as a permanent regression test.

## GATE ANSWER: **YES** — a silent-corruption gap, on two independent sites. **ESCALATED, NOT PATCHED.**

Runner `experiments/p2_route_tpa_v1_adversarial.py`; every case in
`writeup/data/p2_route_tpa_v1_adversarial.json`; battery banked as
`test_turning_point_adversarial.py` (**8/8**). Both branches of the gate were live: three of
the six declared hazards did not fire, and they are reported below with the two that did.

## 1. The headline, in one sentence

`source_of_the_row` computes `X_c` with no `isfinite` guard and then classifies a node as
"near the turning point" by `|X_j − X_c| ≤ 0.1·X_c` — so when there is **no turning point**
and `X_c = inf`, the test becomes `inf ≤ inf`, which is **True** in IEEE-754, every node is
classified as near a turning point that does not exist, and the module returns a finite,
stable, unwarned attribution fraction of **0.7177** where the honest answer is *"this quantity
has no referent"*.

**And the fabricated number outranks the real ones.** At `a = 0.2`, where the turning point is
real and correctly located at `X_c = 17.19`, the honest fraction is **0.4533** — which
**fails** the module's own attribution criterion (`test_turning_point.py:96`,
`assert src["near_Xc_fraction"] > 0.5`). At `a = 0`, where no turning point exists at all, the
fabricated **0.7177 passes** it. Ranked by the module's own headline number, the profile with
**no** turning point looks **more** turning-point-driven than one that has one.

## 2. Finding 1 — the missing guard (hazard H1, declared before construction)

`critical_radius` is consumed at **three** sites in the module (lines 100, 126, 187). Exactly
**one** carries the guard:

```
solver/turning_point.py:100-102   homogeneous_far_field        GUARDED
    Xc = critical_radius(...)
    if not np.isfinite(Xc):
        raise ValueError("no turning point: E does not change sign (a = 0?)")

solver/turning_point.py:126       inner_mode_exponent          unguarded
solver/turning_point.py:187       source_of_the_row            unguarded
```

### The positive control, and it can come out differently (lesson 90)

The whole finding rests on the guarded site, because it proves the module **can** flag this
input. On the identical `a = 0` profile, at every grid tested:

| consumer | `J = 120` | `J = 200` | `J = 400` |
|---|---|---|---|
| `homogeneous_far_field` (guarded) | `ValueError` | `ValueError` | `ValueError` |
| `inner_mode_exponent` (unguarded) | `LinAlgError` | `LinAlgError` | `LinAlgError` |
| **`source_of_the_row` (unguarded)** | **0.719430** | **0.718444** | **0.717698** |

`E = c + 0·U = 0.5` exactly, at every node, with **0 sign changes** — the truth is not a
matter of tolerance. Warnings emitted while fabricating the number: **0**. The three values
agree to 3 significant figures across a 3.3× refinement, so this is **structural, not a
discretization artifact** — the module returns the same wrong answer more precisely as you
refine.

**Where the pre-committed prediction was wrong, and why it matters.** §1 of the novelty log
predicted this fraction would come back at "≈ 1.0", the strongest possible affirmation. It
comes back at **0.7177**, because the gauge slot (codomain index 0, whose `Xj` is `nan`) is
excluded by the `np.isfinite(Xj)` half of the same mask and carries the other 28%. The
prediction was right in direction and wrong in magnitude — and the miss cuts *against* the
module, not for it: a returned 1.0 would look suspicious to a reader, where 0.7177 sits in the
same range as the genuine values (0.45–0.93) and is indistinguishable from one.

`inner_mode_exponent` is the second unguarded site and it does **not** fabricate: the
degenerate abscissa `linspace(inf, inf)` takes `polyfit` down with `LinAlgError` 3/3. The gap
is therefore **confined to one function**, which is worth saying precisely because it narrows
the repair.

### The inversion, measured across `a`

`near_Xc_fraction` at `J = 400`, `alpha = 1.4`:

| `a` | `X_c` exists? | `X_c` | `near_Xc_fraction` | passes module's own `> 0.5`? |
|---|---|---|---|---|
| **0.00** | **NO** | `inf` | **0.717698** | **YES** ← fabricated |
| 0.20 | yes | 17.179 | 0.453326 | **no** |
| 0.25 | yes | — | 0.700934 | yes |
| 0.30 | yes | — | 0.862989 | yes |
| 0.40 | yes | — | 0.929415 | yes |

Pairs in which the case with **no** `X_c` outscores a case with a **real** `X_c`: **2 of 4**
(it beats `a = 0.20` by 1.58× and `a = 0.25` by 1.02×). At `J = 120` the same comparison gives
**0.7194 vs 0.1932 — 3.72×**.

### The mitigation, stated because it is real

`source_of_the_row` **does** return `Xc: inf` in the same dict, beside the fabricated
fraction. So the module is not *wholly* silent: a caller who reads the `Xc` key can tell. What
makes this a corruption rather than a nuisance is that **nothing binds the two**: the module's
own test asserts on `near_Xc_fraction` and never reads `Xc`, and the prose quantity that gets
carried into a writeup is the fraction. The flag exists in a sibling key that nothing checks.

**This mitigation is also the finding's shape.** The same pattern recurs at every site in this
module — the diagnostic is returned, and the headline is not bound to it. `graded_norm_by_radius`
returns `cond` and `smin` beside a `by_cutoff` ladder that stays plausible when `cond` is
`2.25e16`; `log_growth_exponent` returns an exponent with no record of how many points it
fitted. The module reports its diagnostics in sibling keys and binds none of them to the
number a reader will quote.

## 3. Finding 2 — `log_growth_exponent` absorbs poison outside its fit window

`log_growth_exponent(X, h, Xc, tail=0.1)` fits only the outer 10% of the array
(`k = int(0.9·L.size)`). Everything below index `0.9n` is **not looked at**. So a corrupted
`h` produces a clean-looking exponent:

| poison, at index 500 of 1001 (the 50% point) | returned exponent | shift from clean |
|---|---|---|
| clean | 3.3305345431254723 | — |
| `NaN` | 3.3305345431254723 | **exactly 0.0** |
| `-1.0` (a negative amplitude, impossible for this mode) | 3.3305345431254723 | **exactly 0.0** |
| `inf` | 3.3305345431254723 | **exactly 0.0** |

**4 of 4 absorbed with a shift of exactly zero.** The positive control — the same `NaN` moved
*inside* the fitted window, at index 950 — returns `nan`, i.e. it is caught. So the mechanism
is isolated: it is the window, not a tolerance.

This is leg 107's mask-absorption failure mode (`397/400` NaN points absorbed by
`first_integral_defect`) reappearing in a different module by a different route — there a
NaN-blind comparison, here a fitted sub-window. Recorded as a second instance of the class,
not as a re-measurement of leg 107's.

## 4. Finding 3 — `log_growth_exponent` trusts the caller's `X_c` completely

`X_c` arrives as a caller argument and nothing checks it against the `h` it is labelling. The
module's own gate (`test_turning_point.py:52`) accepts the exponent if it is within **5%** of

| `X_c` passed | exponent | rel. shift | still passes the module's own 5% gate? |
|---|---|---|---|
| ×0.1 | 3.8167 | 14.59% | no |
| **×0.5** | **3.4770** | **4.39%** | **YES** |
| ×0.9 | 3.3529 | 0.67% | yes |
| ×1.0 (true) | 3.3307 | 0 | yes |
| ×1.1 | 3.3105 | 0.60% | yes |
| **×2.0** | **3.1843** | **4.39%** | **YES** |
| ×10 | 2.8445 | 14.60% | no |

**5 of 7 wrong-`X_c` calls still pass**, including `X_c` wrong by a **factor of two in either
direction**. Degenerate values (`inf`, `nan`, `0`, negative) all raise `LinAlgError` — those
are caught.

## 5. Finding 4 — the far-field integration steps over a pole with no signal (hazard H5)

`homogeneous_far_field` starts at `X_0 = 1.5·X_c` and integrates `f = H(Ω)/E` to `X = 1e8`.
`critical_radius` returns only the **first** sign change of `E`. Adding a Gaussian bump to the
profile puts a **second** zero of `E` inside the integration window — a pole of `f` — and the
trapezoid rule walks straight through it:

| bump amp | crossings of `E` | integration starts at | poles inside window | exponent returned | error vs `1/a = 3.3333` |
|---|---|---|---|---|---|
| **0.0 (control)** | 6.082 | 9.193 | **0** | 3.3307 | **0.08%** |
| 0.5 | 4.782, **29.947** | 7.248 | 1 | 3.6947 | 10.84% |
| 1.0 | 4.202, **26.793** | 6.399 | 1 | 3.6884 | 10.65% |
| 2.0 | 3.627, **26.793** | 5.479 | 1 | 3.7091 | 11.27% |
| 5.0 | 2.830, **26.793** | 4.284 | 1 | 3.7572 | 12.72% |
| 20.0 | 1.827, **26.793** | 2.749 | 1 | 3.8549 | 15.65% |

**5 of 6 constructions put a pole inside the window**, and in all 5 a finite, plausible
exponent came back with **no exception and no warning**. The `amp = 0` control has **0** poles
in the window and returns the right answer to 0.08% — so the control can, and does, come out
differently.

The honest scope limit: these are hand-built profiles, not Newton solutions, so this says the
*instrument* has no pole detection, not that the banked `a`-family has a second crossing.

## 6. What HELD — three declared hazards that did not fire

Reported because a battery that only lists its hits is not a battery.

* **Poisoned profiles are never absorbed.** 75 poison cases across 8 entry points
  (`NaN`/`inf` at the first, middle and last node of `Ω`; `NaN`/`inf` in scalar `c`;
  `NaN`/`inf` in `alpha`): **38 RAISED, 31 NONFINITE, 6 FINITE**, and **0** of the 6 is a
  fabrication — 4 are Finding 2's window absorption and 2 are `graded_norm_by_radius` with a
  poisoned `alpha`, which correctly propagates the poison into every `by_cutoff` entry
  (`NaN` for `alpha = nan`, `Infinity` for `alpha = inf`) while its scalar diagnostics stay
  finite. A single `NaN` node anywhere in `Ω` drives `source_of_the_row` to `NaN` in both
  `Xc` and `near_Xc_fraction` (1, 2 and 5 poisoned nodes, 3/3) — it is never partially
  absorbed the way `first_integral_defect` absorbed leg 107's.
* **`drop` is safe, if incidentally.** All 5 out-of-range values (`120, 125, −1, −120, 1e6`)
  raise `ValueError`, because `keep` then has the wrong length and the assignment fails on
  shape. Banked as a regression gate precisely *because* the guard is incidental — a refactor
  could remove it silently.
* **A cutoff below every node returns `nan`, not a number.** `graded_norm_by_radius` with
  `cutoffs = (1e-300, 0, −5, inf)` gives `nan` for the three empty ones and the correct
  `11013.15` for `inf`. The one place the module already does the right thing.

### A declared hypothesis that was REFUTED, kept rather than deleted

H1 had a predicted second reachability route: a grid whose outer radius ends **before** `X_c`
would give `X_c = inf` at `a > 0` with no poisoning at all. **This is false.** At `a = 0.2`
over `J = 20…400`, the grid's outer radius exceeds `X_c` at **8 of 8** grids (at `J = 20` the
grid reaches `X = 25.45` and `X_c = 19.43`). The route does not exist, and the `a = 0` anchor
remains the only way in.

The sweep did surface something else, which is kept because it was measured: at **fixed**
`a = 0.2`, `near_Xc_fraction` over `J = 20…400` ranges **0.000000 to 0.453326** and is
**exactly 0.0 at 4 of 8 grids**, with no monotone trend (0.0, 0.0, 0.208, 0.0, 0.0, 0.193,
0.184, 0.453). The attribution statistic is not grid-converged at this `a` — separate from the
`inf` bug and not claimed as one.

## 8. Recommended repair — for a later leg, NOT applied here

`solver/turning_point.py` is byte-identical to `origin/main` on this branch. The gate's
yes-branch says escalate, and this leg escalates. For whoever takes it:

1. **`source_of_the_row`, line 187.** Add the guard that already exists 87 lines above it:
   `if not np.isfinite(Xc): raise ValueError(...)`, or return `near_Xc_fraction = float("nan")`
   with an explicit `no_turning_point: True` field. The `inf ≤ inf` comparison should never be
   reached. The `target_norm.py` / `first_integral.py` warning-class template (the two prior

2. **`log_growth_exponent`.** Return the number of points fitted alongside the exponent, and

3. **`homogeneous_far_field`.** Check `E` for further sign changes in `[X_0, X_max]` before
   integrating, and refuse if there are any.

Item 1 is the one that matters; 2 and 3 are hygiene. **No repair should be merged without
re-pointing this leg's CHARACTERIZATION gates (B, C in `test_turning_point_adversarial.py`),
which assert the *current* wrong behaviour and are labelled to say so.**

## 9. An instrument error this leg made, and corrected

Stated because the repo's own discipline says a control that cannot come out differently is
not a control — and the first run of this battery had one.

The first scorer classified a call by whether **every** number in the returned dict was
finite. `source_of_the_row` at `a = 0` returns `{"Xc": inf, "near_Xc_fraction": 0.719, ...}`,
so the whole-dict verdict was `NONFINITE` — and the battery reported **`0/3` fabrications**,
hiding the exact finding the leg exists to measure. Two further probes were wrong the same
way: `s4_source`'s reachability check counted every occurrence of the name
`source_of_the_row` (including the `import` line) and so reported a control that does not
exist, and the `drop` probe scored a returned tuple as `NONFINITE`.

All three were fixed and the battery re-run in full. The scorer now scores a **named field**
and keeps the whole-dict verdict beside it under `status_whole_dict`, so both readings are on
the record. The general form: **when the module under test returns its flag and its
classification in the same container, an instrument that reduces the container to one verdict
will report the flag and miss the corruption.**
