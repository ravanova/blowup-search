## 4. S4 — known-answer-gate presence in the `validated` field

Each row's `validated` prose was classified into three exhaustive classes:

| class | count of 48 | meaning |
|---|---|---|
| **magnitude** | 33 | states a gate AND a number (`4.4e-16`, `2.1%`, `42x`, …) |
| **declared-absent** | 3 | says "no known-answer gate" plainly — the file's own header explicitly blesses this as an honest value |
| **prose-without-magnitude** | 12 | claims validation, names no number |

The 12 are `op_lower`, `decay_collocation`, `collocation_newton`, `reduced_certificate`,
`nk_fourier`, `nk_seminorm`, `turning_point`, `profile_newton`, `advection_scope`,
`target_selection`, `ga_search`, `finite_support`.

**This is a shape finding, not 12 defects.** Read individually, most of the 12 are
honest: `reduced_certificate` says "explicitly NOT a proof -- float64 throughout";
`nk_fourier` and `nk_seminorm` each say "no independent published known answer" in so
many words; `finite_support` says "nothing -- SUPERSEDED". What the count actually
measures is that **the index's own stated contract — `validated` is "the strongest
KNOWN-ANSWER gate it passes, with the magnitude, or 'no known-answer gate' said
plainly"** — is met by 36 of 48 rows in the letter (33 magnitude + 3 declared-absent)
and by the remaining 12 only in spirit. The honest headline is a **75% magnitude rate**,
not "12 stale rows", and this leg does not rewrite those 12: inventing magnitudes for
another leg's module from an audit chair is exactly the fabrication the `validated`
field exists to prevent.

## 5. S5 — RELEVANCE: does the cited test actually load the module citing it?

This is the axis leg 71 named in words and never systematised. Its own summary:

> It does not check that the cited test **runs, passes, or has anything to do with the
> module citing it**. Existence is checked; greenness and relevance are not.

Leg 71 closed the greenness half by hand and found the relevance half by accident, on
one row (`solver/ga_search.py` cited `test_ga.py`, which imports only the `ga/` package
and never touches the module). This leg makes it a standing, executable check: for each
row, the cited test's source — plus the source of any sibling helper it imports, one hop
— is scanned for `solver.<stem>` / `solver/<stem>.py` / `import <stem>`.

**Result: 1 of 48 rows fails S5.**

| row | cited test | occurrences of the module's name in it |
|---|---|---|
| `solver/finite_support.py` | `test_first_integral.py` | **0** |

Verified by hand rather than trusted to the scanner: `grep -n finite_support
test_first_integral.py` returns nothing at all. Meanwhile `test_finite_support_adversarial.py`
(leg 124) **exists on disk, does `from solver.finite_support import ...`, and was cited
by no row in the index**. So the index pointed the one superseded module at a test that
cannot fail when it breaks, while the test that actually exercises it sat unindexed.

That test was run alone at HEAD, under the same pinned environment: **rc = 0, green**.
Its gate S10 checks the exact property the row's `validated` field claims —
`zero importers, and the SUPERSEDED / DO NOT USE banner is intact` — so the corrected
pointer is not merely *a* test that loads the module, it is the test that re-checks the
sentence the row makes its claim in.

**Fix applied: `solver/finite_support.py`'s `test` field corrected to
`test_finite_support_adversarial.py`, with an inline comment recording why**, following
leg 71's `ga_search.py` precedent exactly. `validated` left frozen — this leg corrects
factual pointers, it does not re-word other legs' claims.

## 6. Negative controls that could have fired and did not

Per the standing discipline, controls that cannot fail are not controls.

1. **The `(N checks)` claims.** Three `validated` fields make a literally falsifiable

   `test_gclm_dedicated.py (14 checks)`, `test_spectral_utils_dedicated.py (10 checks)`.
   The runner counts `^def test_` in each and compares. **3 of 3 agree exactly.** Had a
   leg added a check without updating the row, this would have caught it; it did not
   fire, so the claim "these three counts are current" is measured, not assumed.
2. **The S5 scanner itself.** It returns a *positive* on 47 of 48 rows, including the
   non-obvious `solver/certificate_guards.py`, whose row cites
   `test_nk_bounds_adversarial.py` — a file named after a *different* module. Hand-checked:
   that file does `import solver.certificate_guards as cg`. So the scanner is not simply
   pattern-matching filename against module name; it distinguishes a genuinely relevant
   cross-named citation from an irrelevant same-family one.
3. **The drift detector after the edit.** `test_capabilities.py` re-run post-correction:
   all five tests pass, 48 distinct object keys, 1 superseded module correctly labelled.
