### 3a. The one red I caused myself, and how flake-diagnosis-before-belief resolved it

After repointing the `solver/finite_support.py` row, `test_finite_support_adversarial.py`
returned **rc = 1 in 30.1 s** — the same file that had returned rc = 0 when run by hand
minutes earlier, and the sole evidence the repair rests on. Per the brief and
`ORCHESTRATION.md` §9g it was re-run **alone, under low load, before being recorded as
red**. It failed identically, so it is not a flake, and the stored `stderr_tail` names the
cause without ambiguity:

```
AssertionError: ['capabilities.py:62: ...', 'capabilities.py:661: ...', 'capabilities.py:665: ...']
```

Leg 124's gate **S10** proves the SUPERSEDED module has zero importers by walking every
`*.py` in the tree and flagging any line containing both the module's stem and the
substring `import`. The explanatory comment **this leg had just written** — prose about
the fact that a test imports that module — matched on three lines. To a substring scan a
documentation comment and an import statement are the same object.

Reworded so no line outside leg 124's own two files carries both tokens; the test is
**green again at 33.4 s**, and the verified-green evidence under the repair is restored.

**State this plainly, because it is a finding in its own right: leg 124's S10 gate can be
turned red by prose anywhere in the repository.** Any `*.py` in the tree — a comment, a
docstring, a string literal in an unrelated experiment — that puts `finite_support` and
`import` on one line fails that assertion. That is a property of **the gate**, not of the
code it guards: `solver/finite_support.py` can be byte-identical and correct while the
gate is red. The gate is deliberately conservative (it is a soundness gate whose whole
job is to catch a real importer appearing), and the cost of that conservatism is that
`capabilities.py` cannot describe, in words, the relationship it is documenting.

Two consequences worth banking:

1. A **CAUTION** now sits beside the row in `capabilities.py`, because the next editor of
   that comment will otherwise rediscover this by a red test with no visible link to the
   edit. Diagnosis cost here: roughly one re-run plus one JSON read; without the note it
   is a cold debug of somebody else's soundness gate.
2. This is the audit's own premise firing on the auditor. The axes are executable, so an
   error introduced **by the audit itself** was caught by the audit's own sweep in the
   same run rather than shipped as a green-looking claim. A written-down check would have
   caught nothing.

The 12 are `op_lower`, `decay_collocation`, `collocation_newton`, `reduced_certificate`,

measures is that **the index's own stated contract — `validated` is "the strongest
KNOWN-ANSWER gate it passes, with the magnitude, or 'no known-answer gate' said
plainly"** — is met by 36 of 48 rows in the letter (33 magnitude + 3 declared-absent)
and by the remaining 12 only in spirit. The honest headline is a **75% magnitude rate**,
not "12 stale rows", and this leg does not rewrite those 12: inventing magnitudes for
another leg's module from an audit chair is exactly the fabrication the `validated`
field exists to prevent.

### 5.1 The actual finding: a correct flag that stayed open for ~220 legs, and why

**Leg 71 was right and could not fix it.** At its base `e203b52` (2026-08-05) *no test in
the repository imported `solver/finite_support.py`* — hence the honest flag
`S4_no_coverage` rather than a repair. There was nothing to repoint the row at.

Then `test_finite_support_adversarial.py` was created by **leg 124** (`1424da6`,
Route-FSA) — 53 legs later, 22.6 kB, opening with `from solver.finite_support import ...`.
**Leg 124 did not update the index row**, and nothing in the repository would have
noticed: the drift detector cannot see relevance, and leg 71's relevance check lived
inside leg 71's own runner rather than in the merge gate or the detector.

So the sequence is precise and datable:

1. leg 71 measures the gap correctly, flags it, cannot repair it (no such test exists);
2. leg 124 builds exactly the missing test — and the row still points elsewhere;
3. ~220 legs pass with the flag open, because **the check was run once, not standing**.

**The result of this leg is not the repair. It is that leg 124's fix sat on disk,
unnoticed, for roughly 220 legs.** The one-line correction to a `test` field is trivial
and would be worth nothing on its own; what the audit actually measured is the latency of
this repository's audit loop — the interval between a defect being correctly recorded and
anyone acting on it, when the fix was available for three quarters of that interval. That
is a fact about how the project re-reads its own findings, not a fact about
`capabilities.py`, and it does not get smaller because the repair succeeded.

This is banked lesson 68 — *a check that is not executable decays at the rate of memory*
— in a sharper form than usual: this check **was** executable. It simply was not
*re-run*. An audit that ships a runner and no standing hook has a half-life of one leg.

## 6. Negative controls that could have fired and did not

Per the standing discipline, controls that cannot fail are not controls.

1. **The `(N checks)` claims.** Three `validated` fields make a literally falsifiable
   arithmetic claim about a file on disk: `test_boussinesq_dedicated.py (17 checks)`,
   `test_gclm_dedicated.py (14 checks)`, `test_spectral_utils_dedicated.py (10 checks)`.
   The runner counts `^def test_` in each and compares. **3 of 3 agree exactly.** Had a
   leg added a check without updating the row, this would have caught it; it did not
   fire, so the claim "these three counts are current" is measured, not assumed.
2. **The S5 scanner itself.** It returns a *positive* on 47 of 48 rows, including the
   non-obvious `solver/certificate_guards.py`, whose row cites
   `test_nk_bounds_adversarial.py` — a file named after a *different* module. Hand-checked:
   that file does `import solver.certificate_guards as cg`. So the scanner is not simply
   pattern-matching filename against module name; it distinguishes a genuinely relevant
   cross-named citation from an irrelevant same-family one.
3. **The drift detector after the edit.** `test_capabilities.py` re-run post-correction:
   all five tests pass, 48 distinct object keys, 1 superseded module correctly labelled.
