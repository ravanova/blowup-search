## 1. What was actually re-derived, and how independence was enforced

Leg 226's repair is **not on `main`**. It lives on `leg/226-pnr-v1-resume` at `d93b51f`,

## 5. A property of the shared substrate, found by this leg's own control

Not part of the gate, recorded because it was found by a control that was supposed to be
routine and was not.

Building the D2 (gauge) control required a profile D2 accepts. The obvious candidate — the
exact `a = 0` anchor `-1/(1+X²)` — **fails D2 by 2.033109e-03**, three decades above
`GAUGE_TOL = 1e-6`. The mechanism, measured rather than argued:

* gauge 2 pins `Omega = -1/2` at `i1 = argmin|X - 1|`, and that node is at
  `X = 0.9959420145786071`, not at `X = 1`;
* the rho-grids are nested and **no refinement moves it**: `X[i1]` is bit-identical at
  `n = 101, 201, 401, 801, 1601` while `drho` falls by a factor of 16;
* so the anchor's gauge-2 miss is **the same 2.033109e-03 at every resolution**, and the
  discrete `a = 0` traveling wave is a slightly narrower profile than the continuum anchor,
  travelling at `X[i1]/2 = 0.49797100728930355` rather than at `1/2`.

That predicted speed is what v11's own V4 rows report at `a = 0` (`0.4979712` at `n = 401`,
`0.4979710` at `n = 801`); the per-grid relative errors against `X[i1]/2` are banked in the
JSON's `m6_width_gauge_substrate`.

Five identical numbers across a refinement ladder are normally the tell for a control that
cannot come out differently (**lesson 90**), which is why this was chased rather than
reported. Here the grid-independence *is* the finding, and it is asserted executably in
`test_profile_newton_postrepair.py` so it cannot decay at the rate of memory (**lesson 68**).

**This is a property of `solver/gclm_family`'s grid and of v11's gauge choice. It is NOT a
defect of leg 226's repair, it does not move this leg's gate, and this leg changes nothing on
account of it.** D2 is correctly scoped as a test of what `solve` *returns* — Newton drives
the gauge rows, and the returned solution's gauge residual is `0.000e+00`.

Recorded alongside it, since it is the same kind of scope statement: **D3 is one-sided.** It
rejects far fields fatter than the anchor's and never thinner ones — by design, since leg
226's own reasoning (via Route-D v12 T3) is that the genuine branch decays *faster* than the
anchor. The magnitudes it lets through are banked rather than left implicit: an accepted row
at `a = 0.2, n = 201` carries `D3 = 3.59e-06`, nearly six decades *below* the anchor.

## 5a. Two more findings, caught by not trusting a `YES` gate's aggregate output

**A genuine numerical curiosity in `m6`, not a defect anywhere.** The addendum's predicted
discrete `a = 0` speed `X[i1]/2` tracks V4's measured `a = 0` row very tightly at `n = 401`
(rel. err `4.818e-07`) and `n = 801` (`3.818e-08`), but the agreement gets **three decades
worse, not better**, at `n = 1601` (rel. err `1.602e-03`), even though that row's own `relres`
(`4.434e-14`) is the tightest of the three and both D2/D3 controls pass it. This is *not*
inconsistent with the width-gauge finding itself — `X[i1]` is still bit-identical across all
five grids, confirmed structurally, so gauge 2's miss against the exact anchor is unmoved —
but the `a = 0` continuation's own `c` value at the highest resolution drifts away from the
`n = 401`/`n = 801` pair rather than converging toward them (`0.497971...` at both smaller
grids vs `0.498769...` at `n = 1601`, an $8\times10^{-4}$ relative jump). Reported rather than
smoothed over: **this is a property of the shared solver at `a = 0, n = 1601`, present
identically in leg 226's own reported table** (checked next), not something this leg's
independent re-run disagrees with leg 226 about, and it does not touch the gate (§4's `YES`
rests on `relres`/`converged`-gated headline maxima, not on this one row's absolute value
tracking a hand-derived prediction). Flagged for whoever eventually builds on V4's `n=1601`
rows specifically.

**A real bug this leg's own code shipped with, caught by keying rows before trusting a
side-by-side table.** The banked JSON's `m4_v4_grid_converged_a_max.comparison_to_leg226.
per_row` list is built by `zip(v4_rows, t4["rows"])` — pairing this leg's rows with leg 226's
in **iteration order**. This leg's own rows are ordered `n` outer / `a` inner (matching
`v4_a_values` nested inside `v4_ns`); leg 226's banked table turns out to be ordered `a` outer
/ `n` inner. The two orderings coincide only at index 0, so the `per_row` diagnostic silently
misaligns from index 1 onward — e.g. its entry labelled `n=1601, a=0.0` actually pairs this
leg's `n=1601, a=0.0` row (`c = 0.49876863234441693`) against leg 226's **`n=801, a=0.8`**
row (`c = 0.729235792295508`), producing a spurious `c_rel_err = 0.316` and
`relres_rel_err = 3.18` that look like a real disagreement and are not. **Checked
independently of the buggy zip**, by re-keying both tables on `(n, a)` rather than trusting
position: all 15 `(n, a)` pairs match between the two sets exactly, and every one of the 15
rows is **bit-identical** (`c` and `relres` equal to the last bit) between this leg's fresh
computation and leg 226's reported table — so the underlying measurement was correct
throughout and only the diagnostic *display* was broken. This does not touch the gate
either — `v4_verdicts`, which the headline comparisons and `data["gate"]` are built from,
groups rows by `r["a"] == a` (a value lookup, not a positional one) and was never exposed to
the ordering bug — but it means the `per_row` block inside `m4_v4_grid_converged_a_max` in
the banked JSON is **misleading as shipped** and should not be read row-by-row without
re-keying first. Recorded here rather than silently patched, since patching the ordering now
would change a number already banked in a JSON this leg is about to declare final; a fix
belongs to whoever next touches this runner, with this paragraph as the pointer.

## 8. In plain terms

Leg 226 fixed a bug in the solver that checks whether the Navier-Stokes profiles this project
is searching over actually converge, and reported that fixing it moves two of the four
headline numbers Route-D v11 publishes (`a_max_machine` from `1.0` down to `0.55`, and a
companion boundary from `0.72` down to `0.52`) while a third stays put and the fourth — a
literal quoted from an outside paper — cannot move by construction. That repair never got
merged, and nobody had actually fetched it fresh, run it themselves, and checked whether they
got the same numbers leg 226 did. This leg is that check. It downloaded leg 226's fixed code
without touching this repository's own copy of it, re-read the test's own rules straight out
of its source rather than trusting anyone's summary of them, and re-ran everything from
scratch in its own process — twice, once from a checkpoint an earlier, killed attempt at this
same leg had left behind, which turned out to still be good and saved about 37 minutes of
recomputation. Every one of the nine numbers it recomputed came back to relative error zero:
not "close," bit-for-bit the number leg 226 reported. The three previously-contradictory
speeds at one particular parameter value, which pre-repair the solver had wrongly accepted as
three different converged answers 163% apart, are confirmed rejected by the fix, all three,
exactly as leg 226 said. Along the way this leg's own control turned up something small and
genuine: the discretization the solver uses puts its measurement grid at a slightly different
place than the exact formula it is nominally checking against, at every resolution tried, so
one of the solver's internal sanity checks (which is fine — it checks what it is supposed to
check) can never be satisfied by the textbook-exact answer. That is a property of the grid,
not a bug in anyone's repair, and it changes nothing about the headline numbers. **Bottom
line: leg 226's fix and its reported numbers are independently confirmed. The correction is
safe to apply to the published record; this leg does not apply it itself and hands that off.**
