## 2. Locating leg 221's exact finding

Read `experiments/journal/leg_221.md` and `writeup/data/p2_route_bvrr_v1_repair.json` directly.
The `p2_route_bvrr_v1_repair.json`'s `clause_b.banked_runs` entry for `spike1_stepC_gate` carries
the deciding line:

```python
dict(key="spike1_stepC_gate", artifact="writeup/data/spike1_stepC_gate.json",
     script="experiments/spike1_stepC_gate.py", argv=["--logged"], slow=True,
     calls="RescaledBoussinesq.run(renorm=True), 4 resolution rungs"),
```

`argv=["--logged"]` — no `--steps`. The banked `writeup/data/spike1_stepC_gate.json`'s own
`runs[i].steps` field reads `2500` in all four resolution rungs, while
`experiments/spike1_stepC_gate.py`'s CLI default is `ap.add_argument("--steps", type=int,
default=400)`. The mismatch between the banked artifact's recorded step count and the
regeneration harness's actual argv was visible from these two files alone, before any new
computation — this was the working hypothesis going in, then tested rather than assumed.

## 3. Environment / commit / dependency / seed sweep

* **Commit history since `51b63b2`** (when the artifact was banked) touching the two solver
  files on this gate's call path:
  - `solver/boussinesq_rescaled.py`: only leg 221's own repair to `odd_field_x_slope` (two
    guards), independently measured by leg 221 as `0` of `256 233` calls moved — a control this
    leg trusts rather than re-runs, since leg 221's own repair-off/repair-on comparison already
    isolated it.
  - `solver/boussinesq_velocity.py`: commit `26e6bd3` adds raise-guards in `u_x_at_origin` and
    `PolarGrid.__init__` for empty/rank-deficient windows and reversed intervals. Read directly:
    these guards only fire when `r_min` falls inside or past the local averaging window; this
    gate's four configs all use `r_min=1e-3 ≪ r_window=0.1`, so the guards are dead code on this
    call path and change no numeric output.
  - No other file on the call path (`experiments/spike1_stepC_gate.py` itself, `PolarGrid`,
    `profile_ansatz`, `radial_exponent`, `shape_metrics`) has moved since `51b63b2`.
  → **No code-drift candidate.**

* **Dependency drift.** `requirements.txt` pins `numpy>=2.0` (unbounded) — a real risk factor in
  principle. Today's environment: numpy 2.5.1 on scipy-openblas. Controlled for directly by
  re-running the gate today and comparing against the banked artifact (§4) rather than trying to
  pin numpy back to whatever built the original artifact, since the banked JSON records no numpy
  version to reproduce against. The re-run's float64-level agreement (§4) makes this moot: if
  numpy/BLAS drift had changed the numerics, the correctly-configured re-run would not match to
  13+ significant digits.

* **Seed / RNG.** `RescaledBoussinesq.run()` and `profile_ansatz()` are deterministic — no RNG
  anywhere on this call path (confirmed by reading both). Not a candidate.

* **BLAS-thread count**, the one live environment-sensitivity candidate with in-repo precedent
  (`experiments/leg_0_bench_newton_threads.sh`, a different module/symptom but the same class of
  hypothesis): swept `OMP_NUM_THREADS`/`OPENBLAS_NUM_THREADS`/`MKL_NUM_THREADS` in `{1, 2, 4}` on
  config 0 at the banked step count (2500), three separate subprocess invocations so the env vars
  are read fresh by OpenBLAS at process start. Result: `alpha` moves by `1.55e-15` across the
  sweep — **no thread sensitivity**.

## 4. Re-derivation: reproducing leg 221's number, then reproducing the banked artifact

`experiments/p2_route_s1gr_v1.py` (this leg's diagnostic) does both, independently:

**Step 1 — confirm the cause.** Config 0 (`n_r=300, n_beta=48, r_min=1e-3, r_max=1e5,
renorm=True, tol=1e-9`) run at `max_steps=400` — the harness's actual, un-overridden argv —
gives `alpha = -0.37935637310385306`, matching leg 221's reported regenerated value
`-0.3793563731` to `rel_diff = 1.0157e-11` (agreement limited by leg 221's own printed precision,
not by any discrepancy). This is not a coincidence of a similar-looking number: it is the same
computation, run at the same (wrong) step count leg 221's harness actually used.

**Step 2 — reproduce the banked artifact.** All four resolution rungs, run at
`max_steps = banked_runs[i]["steps"]` (which is `2500` for every rung), reproduce every banked
`alpha` to float64 precision:

| run | config | banked `alpha` | rerun `alpha` | `rel_diff` |
|---|---|---|---|---|
| 0 | `n_r=300, r_max=1e5` | `-0.3350763095343765` | `-0.33507630953437806` | `4.64e-15` |
| 1 | `n_r=450, r_max=1e5` | `-0.33396053473198634` | `-0.33396053473198667` | `9.97e-16` |
| 2 | `n_r=600, r_max=1e5` | `-0.3367555909794855` | `-0.3367555909794855` | `0.0` (exact) |
| 3 | `n_r=450, r_max=1e6` | `-0.33619163643975625` | `-0.33619163643975647` | `6.60e-16` |

`c_l`, `c_omega`, and `residual` agree to comparable precision on all four rungs (see
`writeup/data/p2_route_s1gr_v1.json`, `reruns_at_banked_step_count`). This is today's numpy
2.5.1 / OpenBLAS environment against a 2026-07-25 banked artifact, agreeing to the limit of
float64 arithmetic.

**Step 3 — thread control.** See §3 above; `1.55e-15` spread, no sensitivity.

**Step 4 — predicate re-evaluation.** `evaluate_predicate()` (imported unmodified from
`experiments/spike1_stepC_gate.py`) run against the four correctly-reproduced rungs gives
`checks = {1_alpha_within_5pct: true, 2_alpha_far_within_10pct: false,
3_anisotropy_below_0p23: true, 4_resolution_stable_alpha: true}` — **identical to the banked
`predicate_checks`, in all four fields.** `0` of `4` predicates actually differ. The two flips
leg 221 reported (`1_alpha_within_5pct`, `4_resolution_stable_alpha`) are artifacts of running at
`max_steps=400` instead of `2500`; against a correctly re-run gate, neither predicate moves.

## 5. Adjudication

**REPRODUCIBLE_AS_BANKED.** Named mechanism, with deciding evidence: `experiments/
p2_route_bvrr_v1_repair.py`'s `BANKED` registry entry for `spike1_stepC_gate` reads
`argv=["--logged"]`, omitting the `--steps 2500` flag the banked artifact's own `runs[*].steps`
field proves was used to generate it (script default `400`). This is a harness bug in the
regeneration `argv` list, not staleness in the banked JSON and not environment sensitivity in the
code or dependencies. `writeup/data/spike1_stepC_gate.json` is left untouched — it needs no
correction. `writeup/CORRECTIONS.md` §23 records this (append-only, banked JSON never edited).
