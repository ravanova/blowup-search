## 2. THE NUMERICAL WALL — real, diagnosed, and fixed

The killed leg's last in-flight thought (per the dispatch brief) was that it might be hitting
"a numerical wall in leg 350's enriched basis reused as a differentiation matrix." Running the
preserved script unmodified crashes immediately:

```
numpy.linalg.LinAlgError: Array must not contain infs or NaNs
```
in `reduced_eig_ell_v` at `N=60`, `ell=1` — i.e. at the FIRST call, not only at high
resolution. **The lead was real, and worse than "eventually, at high N": it was already firing
at the leg's own coarsest tested resolution.**

**Root cause, pinned down by direct inspection of the intermediate arrays** (not guessed):
Chebyshev-Lobatto nodes cluster QUADRATICALLY near each endpoint — node `k` near `v=1` has
`1-v ~ (pi*k/N)^2 / 4`. leg 350's map is `u = L*v/(1-v)` (`L=16`), so at `N=60` the first six
nodes already have

```
u = [inf, 23334, 5825, 2583, 1448, 923, 638, ...]
```
— every one past float64's `exp()` underflow threshold (`u > ~745`). `onemX = exp(-u)` hard-
underflows to an exact `0.0` at those nodes (not merely a tiny number). The preserved script
then computed `dv/dX = 1/(dX/dv) = (1-v)^2 / (L * onemX)`, i.e. it divided by that exact zero,
producing `inf`; `d2v/dX2` similarly divided by `(dX/dv)^3`. IEEE arithmetic cannot recover
`0 * inf = 0` once an intermediate step has already materialised a literal `inf`/`nan` — so
even though the FINAL, physically-correct operator entry at those nodes is genuinely
`~onemX^4 * (something huge) -> 0` (the operator's own `(1-X)^4` damping kills exactly those
rows), the naive per-step computation poisons the whole row before that cancellation can
happen.

**Fix: derive the WEIGHTED combinations in closed form so the reciprocal of the hard-
underflowed quantity is never formed.** Substituting `dX/dv = L*onemX/(1-v)^2` algebraically
before, not after, taking the reciprocal gives

```
onemX^4 * dv/dX        = onemX^3 * (1-v)^2 / L
onemX   * dv/dX        =           (1-v)^2 / L        (onemX cancels exactly)
onemX^4 * (dv/dX)^2    = onemX^2 * (1-v)^4 / L^2
onemX^4 * d2v/dX2      = -onemX^2 * (2*(1-v)^3 - L*(1-v)^2) / L^2
```
each of which is bounded and decays SMOOTHLY to `0.0` in the region where the naive formula
overflowed — which is the correct physical limit, not a patch. **Verified numerically before
trusting it**: at every node where the naive `dv/dX`-based formula is still finite (e.g. node
40 of a `N=200` grid), the closed form agrees with it to >= 14 significant digits (machine
precision); in the region where the naive formula blows up, the closed form degrades smoothly
to exactly the value the operator's own damping factor requires. `build_L_ell_v` was rewritten
around these closed forms (the plain, unweighted `dv/dX` is still needed at exactly one place —
row `N`, i.e. `v=0`/`X=0`/`r=0`, the Neumann boundary used by the Schur complement — where
`dv/dX` is perfectly finite, `u=0`, no reciprocal-of-underflow issue arises there at all).

**Verdict on the lead: REAL, not a red herring, not a bug in the sense of "wrong math" — a
genuine floating-point-underflow interaction between a compactifying map built for VALUE
evaluation (leg 350's own stated use case: Chebyshev coefficient/tail-truncation counting) and
a chain-rule DIFFERENTIATION MATRIX built on top of it, which needs derivatives of the map, not
just its values.** leg 350's own module never needed this (it only ever evaluates
`boundary_block_v` and takes Chebyshev coefficients of VALUES); this leg is the first to reuse
the map for a differentiation matrix, and that reuse is what exposed the wall.
