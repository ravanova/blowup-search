# Leg 122 — Route-ASA: adversarial soundness audit of `solver/advection_scope.py`

**Gate.** "Under an adversarial battery of degenerate or poisoned inputs, does
`solver/advection_scope.py` ever silently return a wrong result instead of flagging the
input?"

**Answer: YES.** 12 gate-deciding violations across two independent mechanisms, both rooted
in one unvalidated array-order precondition.
**Escalated, not patched — `solver/advection_scope.py` is byte-identical to what this leg
found.**

## The two mechanisms, precisely

**(T) `profile_mass` inherits `numpy.trapezoid`'s documented order-sensitivity, uncaught.**
`_trapz` is a two-line wrapper with no sorting, no monotonicity check, and no docstring
mention of order; `profile_mass`'s own docstring — `"M = int Omega dX"` — promises a
mathematical, order-independent integral. NumPy's manual states the actual contract: **"If x
is provided, the integration happens in sequence along its elements — they are not sorted"**,
and its own worked example is exactly this leg's mechanism:
`np.trapezoid([1,2,3], x=[8,6,4]) == -8.0` against `np.trapezoid([1,2,3], x=[4,6,8]) == 8.0`.
Measured on the module's own `a=0` anchor `Omega = -1/(1+X^2)` against the closed-form
reference `int_{-L}^{L} Omega dX = -2 atan(L)` (`L=1000`, exact reference `-3.139592654...`):

| perturbation | returned | vs. exact reference |
|---|---|---|
| ascending (control) | -3.1396145659 | 7.0e-06 rel err |
| **exact reversal** | **+3.1396145659** | **exact bit-identical negation of the ascending value** |
| permutation, seed 0 | 31.04 | 10.9x |
| permutation, seed 1 | 282.2 | 90.9x |
| permutation, seed 2 | 73.07 | 24.3x |
| permutation, seed 3 | 524.5 | 168.1x |
| permutation, seed 4 | 1122.7 | 358.6x |
| **single adjacent-pair swap** (2 of 4001 entries) | -3.0146 | **3.98%** |

No warning, no exception, in any of the six rows below the control. **This propagates
directly into `velocity_log_rate`**: its `mass`/`mass_window`/`predicted` fields are built
from the same unsorted `_trapz` call and move by **10.9x relative** under the identical
permutation that leaves its OTHER field, `measured` (a `np.polyfit` slope, which is
order-independent by construction), unchanged to **1e-15 relative**. The function returns
this internally-inconsistent pair — one field correct, the other corrupted — as a single
dict, with no flag distinguishing them.

**(S) `stagnation_point` finds the smallest ARRAY INDEX, not the smallest coordinate.** The
docstring promises "Smallest X > 0 where the effective speed ... changes sign" — a claim
about physical position. The implementation runs `np.diff(np.sign(eff)) != 0` and takes
`idx[0]` over the array **as given**; this equals the smallest coordinate value only if the
caller's `X` happens to already be sorted ascending, a precondition never checked. Built
`eff(X) = tanh(X - 5)`, an odd, strictly monotone function whose only positive root is
exactly `X = 5`:

| | returned | true root | abs. error |
|---|---|---|---|
| sorted (control) | 4.999999999876372 | 5.0 | 1.2e-10 |
| shuffle seed 0 | 5.897824448 | 5.0 | **0.898** |
| shuffle seed 1 | 4.987643548 | 5.0 | 0.012 |
| shuffle seed 2 | 5.447247951 | 5.0 | **0.447** |
| shuffle seed 3 | 9.192779371 | 5.0 | **4.193** |
| shuffle seed 4 | 4.234668785 | 5.0 | **0.765** |

Every entry in every shuffled array is the SAME physically-correct `(X, eff(X))` pair as the
sorted case — only the storage order changed — yet 5/5 shuffles return a wrong, finite,
plausible-looking crossing, none of them flagged. A second construction with **two** real
crossings (`~5` and `~12`) shows the failure is not merely "reports the wrong one of two real
roots": **3 of 5 shuffles return a value matching NEITHER** true crossing (e.g. `3.744` and
`12.318`, both more than 0.5 from either root) — the scan interpolates between whatever two
array-adjacent (not coordinate-adjacent) samples it happens to encounter first, fabricating a
crossing that does not correspond to any place the effective speed actually changes sign.

## What held up

- **NaN never produces a plausible number, even where order also matters.** A NaN placed
  strictly before the true crossing, in an otherwise correctly-sorted array, returns exactly
  `nan` — never a finite value. This is the same "NaN is the safe direction" pattern legs
  101 and 120 found in their own modules, and it holds here too: the module's failure mode is
  about *order*, not about *non-finite poisoning*, and the two are cleanly separable.
- **Scale alone does not corrupt anything.** `profile_mass` on a correctly-sorted grid with
  entries at `1e150` returns the expected product to 1.5e-16 relative — the extreme-scale
  axis that broke other modules' arithmetic (legs 100, 101) is clean here; the defect is
  specifically about array order, not about float range.
- **Every loud-failure control fires as it should.** Mismatched shapes raise `ValueError`; an
  unknown `grading=` key raises `KeyError`; `nan`/`inf` passed as the scalars `a` or `c` to
  `stagnation_point` propagate to a `nan` output; a window with fewer than 8 points returns
  the module's own documented `nan` rather than fabricating a slope; the `a=0` no-crossing
  invariant survives an adversarial array shuffle.
- **A complex-valued profile array is a weaker, but real, flag.** Casting a complex `om` to
  float inside `_trapz` fires a Python `ComplexWarning` and silently discards the imaginary
  part — a signal that fires, unlike (T) and (S) above, but one that any caller not
  inspecting `warnings` will never see. Graded as its own category (`WARNED_NOT_SILENT`), not
  a gate violation, and not folded into the two mechanisms above.

## Downstream exposure — measured, not assumed

`profile_mass`, `velocity_log_rate`, and `stagnation_point` have exactly **one** caller
anywhere in the repository: `test_advection_scope.py`, and every one of its calls goes
through `TwoScaleNewton(...).solve()` → `GCLMResidual` → `solver.gclm_rescaled.sinh_grid`,
which builds `X = c * sinh(rho)` on an ascending `rho` grid with `c > 0` — **strictly
increasing by construction**, for every `n`, `rho_max` this project has ever run. No real
call site has ever passed unsorted, shuffled, or otherwise mis-ordered data into this module.

> **BANKED NUMBERS AT RISK: 0.** Both mechanisms are LATENT — exactly the severity shape of
> legs 66, 69, 79, 100, 101 and 120: the code path exists and is now measured, but nothing the
> repository has ever run has walked it. `capabilities.py`'s validated-clause for this module
> ("agrees with the analytic small-a and large-a limits of the advection coefficient") is a
> statement about physics and is untouched by this finding; what is untouched is the *code's*
> untested claim to be robust to a call it has simply never received.

## What this leg did NOT do

No physics claim was re-derived or contested, no advection-term scope conclusion was revised,
and `solver/advection_scope.py` was read and never edited, under the yes-branch exactly as it
would have been under the no-branch. The audit can only withdraw confidence or bank a test;
it adds no mathematical result. `capabilities.py` is outside this leg's declared territory and
was read only — no wording change is proposed here, since the module's validated-clause is
about the physics limits, which this leg does not touch.

## For the orchestrator, if a repair is ever cut

Both mechanisms share one root cause and one plausible fix shape: `profile_mass`/`_trapz`
should validate (or explicitly re-sort) `X` before integrating, and `stagnation_point` should
either validate that `X` is sorted or explicitly sort `(X, eff)` together before scanning for
a sign change. Neither fix would touch the module's physics content (the `a=0`/`a!=0` scoping
argument in the module's own docstring never varies array order). `test_advection_scope_
adversarial.py`'s six `PIN:` checks name the exact current numbers a repair should move away
from, in the same way legs 101's and 120's pins did for their own modules.
