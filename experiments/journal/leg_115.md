## What the novelty pass changed about the leg

It gave all three families a citable boundary before a line of the battery was written, exactly
the discipline legs 116/120 modeled.

**(1) G1's target came from a published paper about the exact technique the module implements,
not an invented smallness threshold.** Driscoll & Hale (IMA J. Numer. Anal. 36 (2016) 108–132,
*Rectangular spectral collocation*) name "the classical row deletion method" — delete a row of
the discretized differential operator, replace it with a boundary/gauge condition row — as the
standard way spectral collocation methods impose extra conditions, and their own abstract states
it "carries ambiguities... outside of two-point scalar boundary-value problems." `gauged_jacobian`
is exactly this method (`drop` removes a row of `jacobian_matrix`; `GAUGES[gauge](col)` replaces
it), applied to an operator that is neither two-point nor scalar — it is nonlinear and non-local
via the Hilbert transform `H`. Combined with a fact already banked in this repository
(`writeup/4_p2_lottery/TECHNICAL_P2_ROUTED.md` §4: singular-value ablation *measures* that
**exactly two** scalar gauge conditions are needed to remove the profile's 2-parameter symmetry
kernel — one for `c`, one for the origin normalization) and the module's own docstring naming
the same two conditions, the leg had a precise, non-invented question before writing any code:
*what happens when the grid is too small to leave room for both the required gauge row and at
least one row of the actual operator?* `J = 1` is the exact point where that count first hits
zero, and it was found by asking that question, not by randomly sweeping small `J`.

**(2) G2 and G3 came from reading the two library conventions the module leans on without
guarding, rather than from poking at the code and hoping something breaks.** NumPy's own
documentation states unconditionally that `atleast_2d` turns a 1-D array of shape `(N,)` into
shape `(1, N)` — a row, never a column — which is a real, citable ambiguity given that
`sup_op_norm`'s own docstring states an axis convention it never checks a 1-D input against.
NumPy's own documentation for `ComplexWarning` states that casting complex to real is a silent
(warning, not exception) truncation — a strictly looser contract than Python's own `float()`,
which the pass verified directly against the running interpreter raises `TypeError`
unconditionally on a complex argument. Both gave the battery an exact, pre-registered
input class (a 1-D array with mismatched domain/codomain lengths; a complex-valued `alpha`)
instead of an open-ended fuzz.

**(3) It ruled out re-finding anything.** This module has never been audited before this leg —
unlike legs 120 (which explicitly avoided re-finding leg 66/69's fix) and 116 (which explicitly
distinguished itself from legs 79/98), there is no prior finding here to avoid duplicating. That
absence was checked, not assumed: `writeup/novelty/`, `experiments/journal/`, and
`writeup/data/*decay_collocation*` all had no prior `dca`/`decay_collocation`-adversarial
artifact before this leg's own commits.

## What was measured

Four battery families, `experiments/p2_route_dca_v1_adversarial.py`, all numbers banked in
`writeup/data/p2_route_dca_v1_adversarial.json`. Deterministic, fixed seed 20260806, no solver
run — every case is a direct call into `solver/decay_collocation.py`'s public API.

### G1 — grid-size collapse at `J = 1` (the headline)

`gauged_jacobian`'s retained-row count is exactly `J - 1` for every `J` from 1 to 5 (measured,
not assumed) — **zero at `J = 1`**. With zero real collocation rows, `M` is *purely* the gauge
row, which by construction (`GAUGES["origin"]`/`GAUGES["a0"]` read only `col.to_coef`) depends on
neither `om` nor `c`. Measured consequences, all at `J = 1`, `alpha = 1.5`:

* **`graded_inverse_norm(col, alpha, c=c)` is bit-identical across nine values of `c`** —
  `{0.0, 0.5, 1.0, 100.0, -50.0, 1e6, nan, +inf, -inf}` — every one giving
  `1.681792830507429`, which is exactly `2^(alpha/2) = (1+X_0^2)^(alpha/2)` at the grid's single
  node `X_0 = 1.0`. **No exception. No NaN in the output**, even for the two poisoned values of
  `c`.
* **The same holds for a NaN/Inf-poisoned nodal field `om`.** `graded_inverse_norm`'s public
  signature computes `om` internally, so this reconstructs its exact pipeline
  (`gauged_jacobian` → `np.linalg.inv` → `sup_op_norm`) with a poisoned `om` substituted. All
  three poisons (`nan`, `+inf`, `-inf`), applied to *both* `om` and `c` simultaneously, return
  the identical clean value `1.681792830507429`. **NumPy raises `RuntimeWarning: invalid value
  encountered in matmul/multiply` while building the poisoned `jacobian_matrix` internally** —
  the computation genuinely tries to propagate the poison — and that entire NaN-filled matrix is
  then thrown away by the row-selection slice before the caller ever sees it.
* **The collapse is insensitive to `drop` and `gauge`.** Every `drop` value tried (`0, 1, -1, 5,
  100` — both in- and out-of-range) and both gauge choices (`"origin"`, `"a0"`) return the same
  `1.681792830507429`: `M[1:, :]` is the empty `(0, 1)` slice regardless of which `rows` list is
  computed, so the assignment into it is *always* a silent no-op — this is not a `drop=0`-only
  artifact.
* **CONTROL (a PASS): at `J >= 2` (tested at 2, 3, 4, 8, 16), poisoning `c` correctly makes the
  result `nan`, and varying `c` between ordinary values correctly changes the answer.** `J = 1`
  is a sharp, exact boundary, not "small `J` is generally unreliable."
* **CONTROL (a PASS): `J <= 0` raises** — `ZeroDivisionError` at `J = 0`, `ValueError` at
  negative `J` — and **an out-of-range `drop` or invalid `gauge` at an ordinary grid size
  (`J = 8`) raises `ValueError`/`KeyError`.** The module does refuse some degenerate input; the
  `J = 1` collapse is a distinct failure mode from these, not a symptom of the same guard simply
  missing everywhere.
* **Downstream exposure, grepped rather than assumed:** every in-repo caller of
  `Collocation`/`graded_inverse_norm` — `test_decay_collocation.py`, ten
  `experiments/p2_route_d_v*.py` drivers, `test_op_lower.py`, `test_nk_bounds.py`,
  `test_nk_seminorm.py`, `test_holder_norms.py`, `solver/turning_point.py`,
  `test_first_integral.py` — uses `J` of 8 or larger, with `J_LADDER = [125, 250, 500, 1000,
  2000]` typical. **No banked run has ever reached `J = 1`, or anything close to it.** LATENT,
  the same severity shape as legs 66, 69, 79 and 120.

### G2 — `sup_op_norm`'s shape ambiguity

NumPy's `atleast_2d` turns a 1-D array of shape `(N,)` into `(1, N)` unconditionally.
`sup_op_norm`'s own docstring states "rows of A are domain slots, columns codomain slots" but
never checks a 1-D input against that convention before reshaping it. Worked example: `A_flat =
[10.0, 1.0, 1.0]`, intended as a `(3, 1)` column (3 domain slots into 1 codomain slot,
`w_dom = [1,1,1]`, `w_cod = [1]`) — the flat call returns **12.0**; the explicit `(3, 1)`
interpretation (the one the caller intended) returns the correct **10.0**. Randomized battery,
30 cases, `n` domain slots drawn uniformly from `{2,...,6}`, one codomain slot, random positive
entries: **30/30 mismatch** between the ambiguous flat call and the explicit-column call — a
100% rate given the shapes, not a rare edge case, since the axis swap is deterministic whenever
`len(w_dom) != len(w_cod)`. **CONTROL (a PASS): 10/10 randomized explicitly-2-D cases show
`atleast_2d` is a complete no-op**, confirming the hazard is specific to 1-D input.
**Exposure: `sup_op_norm`'s only in-repo call site is inside `graded_inverse_norm` itself, which
always passes a `(J, J)` matrix from `np.linalg.inv` — never 1-D.** LATENT as a public-API
hazard: the function is exported and undocumented against this input shape, but no banked call
reaches it.

### G3 — type-degenerate `alpha`

NumPy's `numpy.exceptions.ComplexWarning` documents that casting complex to a real dtype
"discards the imaginary part" and is a non-fatal `Warning`. Verified directly against the running
interpreter (not asserted from memory) that Python's own built-in `float()` raises
`TypeError: must be a string or a real number, not 'complex'` on the identical input — the two
have different contracts. `norm_domain`/`norm_codomain` end in `float(np.max(...))`. Measured: of
six complex-valued `alpha` probed, the **4** with an imaginary part large enough to matter
numerically (`1.5+0.1j`, `1.5+1.0j`, `1j`, `-1+2j`) each return a value that **silently diverges**
from the real-part-only computation — no exception, `ComplexWarning` fired but not elevated by
default. The full pipeline (`graded_inverse_norm(col, 1.5+0.3j)`) runs to completion and returns
an ordinary finite `float` with zero signal in the return value that `alpha` was never the real
exponent the docstring's `(1+X^2)^{alpha/2}` requires. **Exposure: no in-repo caller ever passes
a complex `alpha`.** LATENT.

### The passes, recorded as loudly as the failures

At an ordinary grid size (`J = 16`), NaN/Inf poisoning a single entry of `om` or poisoning `c`
propagates to a non-finite result through **every one of 12 checked paths** — `residual`,
`jacobian_matrix`, `norm_domain`, and `graded_inverse_norm` — **0 absorbed**. `alpha = 2` (the
far-field *model* operator's singular point, `2/|alpha-2|`, a property the module's own docstring
attributes to a *different, simpler* operator it does not itself compute) causes no blow-up or
misbehaviour in the full operator this module actually discretizes, confirmed at three values
straddling `alpha = 2` on a `J = 32` grid.

## What was NOT patched, and what a repair would have to do

`solver/decay_collocation.py` is untouched — confirmed by `git diff --stat` at every checkpoint.
`test_decay_collocation_adversarial.py` carries **15 permanent checks**, **7 of which PIN
current, defective behaviour** (marked `PIN:`, each stating the correct behaviour beside it) and
**8 of which are CONTROL/PASS checks** that must keep holding. A repair would need to:
`gauged_jacobian`/`graded_inverse_norm` should raise (or otherwise flag) when `rows` is empty
(i.e. `J <= 1`) rather than silently proceeding with a gauge-only system; `sup_op_norm` should
validate that a 1-D `A`'s length matches exactly one of `{len(w_dom), len(w_cod)}` unambiguously,
or simply require 2-D input; `norm_domain`/`norm_codomain`/`graded_inverse_norm` should reject or
warn loudly (not merely via NumPy's default-suppressed `ComplexWarning`) on a non-real `alpha`.
None of this is applied here — leg 115's pre-committed yes-branch is escalate, not patch.

## Honest limits

* Every number here is a statement about **code behaviour under degenerate or poisoned input**.
  None is a physics measurement; none contests any banked Route-D result; no link of the
  `L1 → L4` chain moved.
* All three findings are LATENT under the repository's current usage — a statement about the
  grid sizes and parameter types in use today, not a property of the code that would survive
  someone calling `Collocation(1)`, passing a 1-D array to `sup_op_norm`, or computing `alpha`
  as a complex number (which nothing anywhere currently does, but nothing prevents either).
* G1's `1e6` and other large finite `c` values were included in the identical-value list not
  because they are adversarial in the usual sense, but because they demonstrate the *same*
  insensitivity for ordinary-looking input, not only for NaN/Inf — the collapse has nothing
  specifically to do with non-finite values; it is purely a row-count degeneracy that NaN/Inf
  poisoning happens to make maximally vivid.
* G3's `n_silently_diverging = 4/6` (not 6/6) is reported honestly: `1.0+0.0j` trivially matches
  the real-part-only answer (zero imaginary part), and `1.5+1e-10j`'s imaginary part is too small
  to move the float64 result at the tested precision — both are recorded as non-divergent cases
  rather than rounded up to strengthen the headline.
