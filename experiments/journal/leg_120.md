## What the novelty pass changed about the leg

Two published references reshaped the battery before a line of it was written, and without
them two of the findings would have been assertions of taste rather than measurements against
a standard.

**(1) It made the dealiasing boundary a published inequality instead of a preference.** The
loose form of the 2/3 rule that most of the corpus states — "keep the first 2/3 of the modes"
— cannot distinguish `k <= n/3` from `k < n/3`, and for the power-of-two `n` that nearly every
code uses, `n/3` is never an integer so the distinction is invisible. **Bowman 2013** (*How
Important is Dealiasing for Turbulence Simulations?*, U. Alberta, p.29, *Centered
Convolutions*) states it exactly, and names the failure mechanism:

> "one needs to pad to `N >= 3m - 2` to prevent **mode `m - 1` from beating with itself to
> contaminate the most negative (first) mode**, corresponding to wavenumber `-m + 1`."

With `K = m - 1` the largest retained wavenumber this is `N >= 3K + 1`, i.e. **`K < N/3`,
strictly**. `dealias_mask` keeps `k <= n/3`. The two agree for every `n` not divisible by 3
(`floor(n/3) < n/3`) and differ by exactly one mode when `3 | n`. Better still, Bowman names
the experiment: *put the field on mode `K`, let it beat with itself, and look at what lands
back in the band.* Battery S1 is that experiment and nothing else.

**(2) It ruled out the leg's biggest false-positive risk, and turned it into the sharper
finding.** The obvious thing to flag in `derivative_hat` is the line `d[-1] = 0.0`. **Johnson
(MIT)**, *Notes on FFT-based differentiation*, Algorithm 1 step 2, settles that it is correct:

> "Multiply `Y_k` by `2πi/L k` for `k < N/2`, by `2πi/L (k - N)` for `k > N/2`, and by **zero**
> for `k = N/2` (if `N` is even)"

— with a footnote confirming the odd case has no such term. So the even/odd split is the
published algorithm, and this leg **confirms** it rather than contesting it. But the published
prescription is a *multiplication* by zero and the module performs an *assignment*. On finite
input they are identical; on non-finite input they are not, because `0.0 * nan = nan` and
`0.0 * inf = nan`. That is a one-line, literature-anchored target, and battery S4 instruments
it directly instead of poisoning arrays at random.

A third thing the pass did was negative and worth recording: **query Q4 found nothing** on
"a spectral filter overwrote a NaN and returned a clean result". The absence is expected —
papers report methods, not their own defects — and it is written down so that **no novelty
claim attaches to finding one here.** The vocabulary for the failure mode is inherited from
leg 91's pass (*NaN-Propagation*, arXiv:2507.23186: *"a more serious false-negative failure
mode can occur if the program actively overwrites NaN outputs without raising an error"*),
cited rather than re-derived.

## What was measured

Eight batteries, `experiments/p2_route_sua_v1_adversarial.py`, all numbers in
`writeup/data/p2_route_sua_v1_adversarial.json`. Deterministic, fixed seed, no solver run.

### D1 — `dealias_mask` retains one mode too many when `3 | n`

Bowman's experiment at 23 grid sizes. Field placed on the top retained mode `K`, squared, and
mode `K` read back; the 2/3 rule guarantees that coefficient is **exactly zero**.

| | grids | spurious coefficient at `k = K` | true value |
|---|---|---|---|
| `3 ∤ n` (12 sizes) | 10, 16, 20, 32, 40, 50, 64, 100, 128, 200, 256, 512 | ≤ **4.83e-16** | 0 |
| `3 \| n` (11 sizes) | 6, 9, 12, 24, 27, 48, 81, 96, 192, 384, 768 | **2.500e-01**, identical at every one | 0 |

Contaminated at **11/23** sizes — precisely the eleven with `3 | n`, and at no other. The
correspondence with Bowman's inequality is exact: `K < n/3` holds iff `3 ∤ n`.

### D2 — the consequence in a shipped diagnostic

`energy_production` is documented as *"Exact rate `d/dt E` for gCLM"* and is the quantity
`solver/gclm.py` (lines 196, 250) accumulates into the per-run **energy-balance residual**,
the artifact guard of `LOGGING.md`. It evaluates a *cubic* product on the grid, so D1's band
admits the triad `K + K + K = n`. Measured against an alias-free 6× refined evaluation of the
same integral:

- worst relative error with `3 | n`: **1.6621e-01** at `n = 81` (also 8.80e-02 at 27,
  7.03e-02 at 192, 6.66e-02 at 48, 1.77e-02 at 24, 1.61e-02 at 384, 1.59e-02 at 768)
- worst relative error with `3 ∤ n`: **2.4651e-14** at `n = 256`
- **12.8 decades of separation.**

This is the finding's teeth. D1 alone is a property of a mask that a reader could dismiss as a
convention choice; D2 is a wrong number in a guard the solver logs on every run.

### D3 — `derivative_hat` erases a non-finite Nyquist coefficient

12 cases (`n ∈ {8,16,64,256}` × `{nan, +inf, -inf}` at the Nyquist slot). **12/12** returned a
fully finite spectrum *and* a fully finite physical-space derivative with `max|w_x| = 1.0000`,
indistinguishable from clean input. The published multiply-by-zero form would have propagated
all 12. Sharper still: for the six `±inf` cases numpy **did** raise a `RuntimeWarning` inside
the multiply — the complex product `(0 + ik)(inf + 0i)` is already `nan` — and the assignment
then discarded exactly the value that warning was about.

Controls, both passes: poison at any non-Nyquist slot propagates (**18/18**); poison at the top
mode of an odd grid propagates (`n = 17, 65, 129`), and the odd-`n` derivative is still exact
(rel err 5.8e-15, 1.5e-14, 4.4e-14) — **leg 69's fix is intact and is not re-found here.**

### D4–D7 — the rest of the map

- **D4** `velocity_hat` erases a poisoned mean mode: `np.zeros_like` leaves index 0 at exactly
  0 whatever came in. 3/3 erased. The *value* is the intended zero-mean convention, so this is
  not a wrong velocity — what is lost is the corruption signal.
- **D5** `velocity_hat` silently truncates integer input (dtype inherited from `zeros_like`,
  float quotient unsafe-cast on assignment): worst relative error **1.0000** at int scale 1
  and 3 over 200 draws. `derivative_hat` and `hilbert_hat` both promote to `complex128` on the
  same input; `velocity_hat` is the only one of the three that does not.
- **D6** malformed `k` accepted silently in **8/15** cases; worst relative sup error **2.0000**
  (`hilbert_hat` with scalar `k = -1.0`, which returns the sign-flipped transform), and
  **1.0000** with `k = 0.0`, which annihilates the transform entirely. `derivative_hat`
  validates `len(w_hat)` against `n` but never validates `k`. `velocity_hat` refuses all five.
  The module is internally inconsistent about one caller error.
- **D7** `grid(0)` and `grid(-8)` return empty arrays with no error while `wavenumbers(0)` and
  `dealias_mask(0)` raise `ZeroDivisionError`. `dealias_mask(1)` and `dealias_mask(2)` retain
  **zero** non-mean modes — the exact condition leg 89 made a hard `ValueError` in the 2D
  solver (`solver/boussinesq.py:349`); the 1D path has no equivalent guard.

### The passes, recorded as loudly as the failures

`integral`, `l1_norm` and `energy` **never** absorb poison: **0/8** adversarial cases returned
a clean finite number, `nan`/`±inf` propagate correctly, and the empty grid returns `nan` with
3 `RuntimeWarning`s rather than inventing a value. `derivative_hat`'s length guard fires on
exactly the wrong-length coefficient arrays (8/8 cases correct). The repository's spectral
conventions re-derive exactly: `H(sin) = -cos` (4.4e-16), `H(cos) = sin` (6.1e-16),
`integral(1) = 2π` (0.0), `energy(sin) = π/2` (0.0).

*(One correction made during the leg and recorded because it was mine, not the module's: the
first draft of that last check compared `energy(sin)` against `π`. The correct value is `π/2`.
The module was right and the check was wrong; it was fixed before anything was banked.)*

## What is banked, and what a repair should do

- `test_spectral_utils_adversarial.py` — 11 permanent checks. **Seven of them PIN CURRENT,
  DEFECTIVE BEHAVIOUR**, each marked `PIN:` with the correct behaviour stated beside it. This
  is leg 66's own precedent: a leg read-only on `solver/` pins defects rather than fixing them
  silently, so they cannot drift and so the repair has an exact target. **These checks will
  start FAILING when the repair lands — that is the intended signal, and the pin should be
  updated in the same commit as the repair.**
- The repair itself is small and is **not** this leg's to make: `dealias_mask` should return
  `wavenumbers(n) <= (n - 1) // 3` (equivalently `< n/3`), which is a no-op at every grid size
  the repository has ever run and closes the boundary; `derivative_hat` should multiply the
  Nyquist entry by zero rather than assign it, per Johnson Algorithm 1; `velocity_hat` should
  build its output as complex rather than inherit the input dtype; `hilbert_hat` and
  `derivative_hat` should validate `k` the way `velocity_hat` effectively does. Note that
  `test_spectral_utils_dedicated.py:121–122` asserts `dealias_mask(96)[32] is True` with the
  comment *"k = n/3 must be retained (<=, not <)"* — that assertion encodes the defect and must
  be inverted by the same repair. It is not this leg's file to edit.

## Honest limits

- Every number here is a statement about **code behaviour**. None is a physics measurement, and
  none contests any banked result.
- D1/D2's severity is latent **as the repository is currently configured**. That is a statement
  about the grid sizes in use today, not a property of the code — it does not survive anyone
  choosing a different resolution.
- D4 is the weakest of the seven: the erased value is the intended convention, and only the
  loss of the corruption signal is a defect. It is reported at that strength and no higher.
- The alias-free reference in D2 is a 6× grid refinement, not an analytic value. Its own
  convergence is evidenced by the `3 ∤ n` column agreeing with `energy_production` to 2.5e-14.
