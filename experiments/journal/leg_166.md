## 3. Clause (a): the exact failing case

`experiments/p2_route_cna_v1_adversarial.py` line 303 constructs leg 114's `pure_sign_noise`
case verbatim:

```
Xg = np.linspace(0.01, 40.0, 800)          # line 285
critical_radius(Xg, (-1.0) ** np.arange(Xg.size))
```

| | value |
| --- | --- |
| leg 114's recorded pre-repair `Xc` | `0.03502503128911139` |
| **post-repair `Xc`, module on disk** | **`0.03502503128911139`** |
| `min_rel_depth=0.0` (the pre-repair path) | `0.03502503128911139` |
| the truth | `undefined` — the field has no crossing to find |

**Bit-identical to the pre-repair answer.** The repair moves this case by exactly zero.

### Why — and it is a predicate-class ceiling, not a threshold

Leg 150's landed guard accepts a crossing when the constant-sign excursion on **each** side
reaches `min_rel_depth · max|E|`. That test is **scale-invariant**, and this field has no scale:
every constant-sign run is one node long with `|E| = 1`, which is *also* `max|E|`. So the
excursion ratio on both sides is exactly **1.0** — the largest value the test can ever observe. A
relative-depth test cannot reject a field whose noise **is** its own maximum.

The threshold ladder (arm F), the control that could have reported the other answer:

| `min_rel_depth` | sign noise rejected? | real crossings surviving |
| --- | --- | --- |
| 0.0 … 0.999 | no | 8 / 8 |
| **1.0** | **no** | **0 / 8** |
| 1.5, 2.0 | yes | **0 / 8** |

**0 of 15 thresholds do both.** The moment the threshold is large enough to reject the sign noise
(`> 1.0`) it has already rejected every real crossing — measured on the a-family fields at
a ∈ {0.15 … 0.5}, whose radii at the shipped default are 51.845551, 17.609366, 6.148257,
3.493167, 2.418469. So this is not a tuning slip in leg 150's number; **no member of the
predicate class it chose covers this case**, and a repair must add a different predicate (an
absolute floor, or a resolution/sampling condition) rather than move a constant.

### Reachability — latent, not live, and reported that way

In leg 114's own discipline. A pure alternating-sign `E` is not a field this module produces:
across a ∈ {0 … 0.5} the real `E` on the collocation grid carries **0** non-finite entries and a
well-separated crossing, and `solver/turning_point.py` feeds `critical_radius` only `col.X` at all
three of its call sites (lines 100, 126, 187). Arm B measured `critical_radius` **11/11**
identical to pre-repair on real fields and arm D **5/5** at the consumer sites. The gap is a
degenerate-input gap, exactly as M3 was before the repair.

## 6. Beyond the gate: a second, smaller residual gap in the same guard (arm E)

Reported as a magnitude, not folded into the gate answer. `critical_radius` computes
`thresh = min_rel_depth · max|E|` and applies the magnitude test only `if thresh > 0.0`; and
`_run_extent` returns `None` — *"this leg cannot judge the magnitude here"* — for any
constant-sign run containing a non-finite value, which the caller treats as **accept**. Both
routes mean **a single non-finite entry anywhere in `E` turns the whole guard off**:

| leg 114's M3 adversary, plus… | `Xc` post-repair | = pre-repair? |
| --- | --- | --- |
| nothing | `inf` (correct) | no — repaired |
| one `NaN` | `nan` | yes |
| **one `+Inf`** | **finite, bogus** | **yes — guard fully bypassed** |
| **one `−Inf`** | **finite, bogus** | **yes — guard fully bypassed** |

**2 of 4 probes bypass the repair back to exactly pre-repair behaviour.** Reachability, measured:
real `E` on the collocation grid has **0** non-finite entries at every a; the off-grid log grid
stays finite to `X_max = 1e6` and first goes non-finite at **`X_max ≈ 1e12`** (276 of 2000
entries), where `max|E|` becomes `nan` and the guard silently switches off. The one consumer that
builds such a grid, `turning_point.homogeneous_far_field`, defaults to **`X_max = 1e8`** — below
onset — and does not feed it to `critical_radius` anyway. **Latent, not live**, same status leg
114 measured for M3 itself. This is a *note for the repair leg*, not a second gate answer.

## 8. One reproducibility note (about the machine, not the module)

Arm B's 200 pre/post solves ran ~50 minutes on the first attempts and ~4 on the last. The cause
is BLAS thread oversubscription, not the module: profiled, `np.linalg.solve` on the J = 160
gauged matrix cost **1.706 s per call** (60 calls = 102 s for one solve) unpinned, against
**0.97 s for the whole 60-iteration solve** with `OMP_NUM_THREADS=OPENBLAS_NUM_THREADS=
MKL_NUM_THREADS=1`. A ~100× difference on a 160×160 dense solve. **Run the runner with those
variables set.** The bit-identity result is unaffected either way: arm B imports the pre-repair
and post-repair modules into the *same process* and compares them under identical thread
settings, so the differential is apples-to-apples, and every value arm A compares against leg
114's record (`critical_radius`, `zero_order`) is pure-NumPy with no BLAS call in it.
