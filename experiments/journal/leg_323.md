## Part 1 — the check that found it: re-derive every row's query from its own URL

A recorded row has two fields that claim to say what was asked: the `query` string the runner
wrote, and the `url` it actually requested. Only the second one cannot lie, because it is the
bytes that went to arXiv. Re-deriving `search_query` out of each committed row's URL and
comparing it against the query that row is *labelled* with gives, on the pre-kill artifact:

| step | rows | label matches the URL and status OK | label does not match, or refused |
|---|---|---|---|
| `step_a` | 29 | **29** | 0 |
| `step_b` | 70 | **29** | **41** |
| `step_c` | 15 | 13 | 2 |

**41 of 70 Step B rows could not be believed.** Step A survived intact and is carried forward
rather than re-spent.

## Part 2 — the two defects, with their mechanism, not just their effect

**D1 — job-id/payload confusion.** `run_step_b()` built each variant job's *identifier* out of
the BASE query string while submitting the VARIANT string as the payload:

```python
variant_jobs = [((chan, "variant", q), substitute_variant(q, "double_hyphen")) ...]
#                             ^ base q in the id            ^ variant in the payload
...
for (chan, _, q), (chan2, _, vq) in zip(...):      # vq is the id's third element = BASE q
    rows.append({"pass": "double_hyphen_variant", "query": vq, ...})   # writes the BASE string
```

`substitute_variant` itself is correct — called directly it returns
`abs:"computer--assisted" AND abs:"self--similar" AND abs:blowup` for the first base query.
The defect is purely in what got *recorded*: every double-hyphen row in the artifact was
labelled with a query it had not run. On its own D1 is a labelling bug and the measurement
would still have been right.

**D2 — the retry re-sent the mislabel, and that is what corrupted the data.** The first pass
took 18 HTTP 429s in Step B. The recovery pass, `--retry-unavailable`, re-queried
`r.get("query_string") or r.get("query")` — i.e. D1's mislabel, the **baseline** — and on
success wrote the baseline's `n`, `links` and `url` back into a row still labelled
`double_hyphen_variant`.

The measured damage, counted off the URLs: of 35 variant rows, only **8** ever carried a `--`
in the string actually sent, and **all 8 of those were the rows still sitting at 429** —
every single successfully-recorded "variant" row was a baseline query wearing a variant
label. (4 further rows — e.g. `abs:"blowup" AND abs:"viscous" AND abs:"rigorous" AND
abs:"continuation"` — contain no hyphenated term at all, so variant and baseline coincide
legitimately; those are marked `variant_identical_to_baseline` in the new JSON rather than
left to look like a finding.)

**Why the corrupted artifact looked healthy: it reported 35 deltas and every one was empty.**
That is lesson 90 in its exact stated form — *a control that cannot come out differently is
not a control, and the tell is that its numbers are identical.* Both arms of every pair were
the same URL, so the delta was `set(X) - set(X)` and could not have been anything but empty.
The pre-kill `gate_answer: NO` was computed from 35 tautologies.

**The fix is structural, not a patch.** Every row now carries `query_sent`, parsed back out of
the URL it requested; `verify_rows()` re-derives every row's intended query from the plan and
**refuses to curate** if any row's sent string differs. The new JSON carries
`instrument_verification.n_problems`, which is **0**, and would have been 41 on the pre-kill
data. A retry now re-sends `query_sent`, so D2 cannot recur even if D1 did.

## Part 3 — assessing the runtime before running it, and the environment fact that set it

The pre-kill note estimated ~7.5–11 min for 135 calls at 3.2 s spacing and measured 7–38 s of
API latency instead. I re-measured rather than inheriting either number, and got a third
answer:

- a single `all:electron` over https: **HTTP 200 in 0.12 s** (curl) and **0.1 s** (urllib);
- a **6-query burst at 3.2 s spacing**: every one failed, each hanging ~46 s before
  **HTTP 503, `Retry-After: 0`**;
- immediately after that burst, `all:electron` — which had just returned in 0.1 s —
  **also returned 503 in 46.5 s**;
- after ~20 s of quiet, the same compound query returned **200, n=7, in 33.8 s**, and one call
  later `all:electron` was back to **0.4 s**.

So the 7–38 s "latency" is not latency: it is a **client-level throttle**, and the 46 s is
that throttle's hang-then-503. This is an environment fact, not a property of any query, and
it is what fixes this leg's cost: the binding constraint is a politeness floor, not compute.
Concurrency was removed for the same reason — the pre-kill runner's 5-worker pool is what
bought its 20 refusals, so parallelism here makes the run *slower*, not faster.

**Estimate before launching:** ~75 calls at 8 s spacing plus ~1 s median response ≈ **11–13
min**, with a 45/90/150/240 s backoff ladder as insurance. **Achieved: 31.2 min** for 87 live
requests (21:26:37Z→21:57:49Z), plus 1.1 min for the 9-query Step C2 addendum added mid-leg
(Part 5) — **32.8 min total, 94 requests, median response 0.5 s, max 75.1 s (one timeout, which
the backoff recovered), and 0 refusals to measure in the final artifact.** The overrun against
the estimate is Step B: 41 requests in 17.4 min, i.e. 25 s/request against a modelled 9 s,
because throttle events cost a backoff each. This exceeds the ~10 min assessment threshold and
the reason is stated rather than hidden: the work is 94 external HTTP requests against a
rate-limited third-party endpoint and there is no cheaper form of it that still answers the
gate. Nothing was trimmed to make the number smaller.

## Part 4 — the measurement, and what it says about MF1

**Controls, both directions, all five pass** (`controls_pass: true`):

| control | sent | n | reading |
|---|---|---|---|
| positive, environment | `all:electron` | 60 | endpoint alive |
| positive, two ANDed quoted phrases | `abs:"self-similar" AND abs:"blow-up"` | **60** | a **third** independent refutation of the struck MF3 clause (legs 314, 326 are the other two) |
| negative, nonsense phrase | `abs:"quixotic hyperviscous marmalade"` | **0** | phrase matching is real, so a zero can mean something |
| positive, author conjunction | `au:"Cao-Labora" AND au:"Gomez-Serrano"` | **6** | `au:` AND works on a known co-authored pair |
| negative, author conjunction | `au:"Cao-Labora" AND au:"Silantyev"` | **0** | ...and is not being silently ignored |

The last two exist because a bare author-AND has produced a false negative in this repo before
(leg 326, "Chae Tsai"). Each control can come out the other way, and the fourth and fifth
differ from each other by one author, so neither is a tautology of the code.

**Step A — is the `abs:` retrieval layer dash-sensitive?** 22 same-session comparisons, each a
variant form against that term's own freshly-queried single-hyphen baseline:

| form | comparisons | identical id set |
|---|---|---|
| double hyphen `--` | 4 | **4/4** |
| en dash `–` | 4 | **4/4** |
| em dash `—` | 4 | **4/4** |
| spaced hyphen ` - ` | 4 | **4/4** |
| unhyphenated (joined) | 4 | **0/4** |
| De Gregorio: `de Gregorio` | 1 | 1/1 |
| De Gregorio: `DeGregorio` | 1 | 0/1 |

**All 5 of the 22 comparisons that moved are the word-joining form; none is a dash form.**
With magnitudes: `abs:"Navier-Stokes"` 60 → `abs:"NavierStokes"` **5**;
`abs:"computer-assisted"` 60 → `abs:"computerassisted"` **2**; `abs:"De Gregorio"` 21 →
`abs:"DeGregorio"` **1**. `self-similar`/`blow-up` return 60 in both forms but on disjoint id
sets — `selfsimilar` and `blowup` are simply different tokens with their own literature.

**So MF1's practical content on the `abs:` field is the opposite of how it has been carried.**
The hyphen *shape* — `-`, `--`, `–`, `—`, ` - ` — is normalized away; a plain-hyphen query
already reaches a `Navier--Stokes` abstract, which is exactly what leg 303's own artifact
showed for `2604.09949` (that hit was found by two single-hyphen queries). What is **not**
normalized is deleting the hyphen. The one caveat, stated rather than buried: for these broad
single-term queries `n = 60` is `max_results`, so "identical id set" means *identical top 60 by
submission date*. The compound queries below are all far under the cap (largest **23**) and
carry no such caveat.

**Step B — the compound re-run, 35 pairs, now genuinely paired.** Every one of the 35 base
queries was re-run verbatim (the replication control) and again with **every** hyphenated or
proper-name term simultaneously double-hyphenated. **35/35 pairs interpretable; 0 refusals; 0
errors.** Result:

> **The total number of arXiv ids returned by a double-hyphen variant and not by its own
> single-hyphen baseline, summed over all 35 pairs, is 0.** Every pair matches in count as
> well as in membership: 2/2, 1/1, 3/3, 5/5, 7/7, 9/9, 23/23, …

This time that zero is a measurement and not an artifact of the code, and the check that
distinguishes the two is `instrument_verification.n_problems = 0`: the URLs prove the two arms
of each pair were genuinely different strings. `abs:"discretely self--similar" AND
abs:"Navier--Stokes"` returned the same 23 papers as its single-hyphen form; `abs:"Boussinesq"
AND abs:"computer--assisted"` the same 7.

**Zero audit — every zero, component-wise.** 26 of the 70 Step B rows returned zero. Each was
decomposed into its `AND` components and each component queried standalone (32 distinct
components, cached by string). **All 32 components returned non-empty** — the smallest is
`abs:"Hou-Luo"` at **6**, and `abs:"Hou--Luo"` also **6**, itself another dash-normalization
data point. With both positive controls and the negative control passing, all **26** zeros are
recorded as `REAL ABSENCE (every component individually non-empty)`. None is banked as an
absence on the strength of the compound query alone.

**Staleness re-check of the carried-over rows.** Six pre-kill rows that migration kept were
re-queried fresh, chosen deterministically to span the kinds that could rot differently — two
Step A dash forms, two Step B baselines with hits, one Step B baseline with **zero** hits, one
Step C author row:

| re-checked | pre-kill n | re-run n |
|---|---|---|
| `abs:"Navier--Stokes"` | 60 | 60 |
| `abs:"NavierStokes"` | 5 | 5 |
| `abs:"self-similar" AND abs:"Navier-Stokes" AND abs:"computer-assisted"` | 3 | 3 |
| `abs:"backward self-similar" AND abs:"Navier-Stokes"` | 7 | 7 |
| `abs:"radii polynomial" AND abs:"blow-up"` | 0 | 0 |
| `au:"Breden-Chu"` | 0 | 0 |

**6/6 agree.** The carried-over rows are not stale. They were mislabelled, which is a different
disease, and the URL check — not this re-check — is what found it.

## Part 5 — the finding the gate did not ask for: `au:` does not behave like `abs:`

The four-group author census was run in its pre-committed single-phrase form and then, because
one of its rows failed a sanity check, in an author-conjunction form as well (**Step C2**, 9
queries, added mid-leg and recorded here as added mid-leg).

**(a) The `au:` field is NOT dash-normalizing, where `abs:` is.** Same variant table, opposite
answer, on real compound surnames:

| sent | n |
|---|---|
| `au:"Gomez-Serrano"` | **47** |
| `au:"Gómez-Serrano"` | **47** (accent normalized) |
| `au:"Gomez--Serrano"` | **0** |
| `au:"GomezSerrano"` | **0** |
| `au:"Cao-Labora"` | **11** |
| `au:"Cao--Labora"` | **0** |
| `au:"CaoLabora"` | **0** |

A double-hyphen query on the author field silently returns **0 where the single hyphen returns
47**. This is MF1 with real teeth, on a field nobody had tested it on, and it is the reason the
NO above is stated with its realization attached rather than as "the census is dash-robust".
Accents, by contrast, *are* normalized in both directions (`au:"Dähne" AND au:"Figueras"` and
`au:"Dahne" AND au:"Figueras"` both return **1**).

**(b) A false-negative class in the census's own pre-committed form.** Three of the four groups
are named after **two different people**, not one compound surname, so querying the group name
as a single `au:` phrase can only ever return 0:

| group | single-phrase form | author conjunction | verdict |
|---|---|---|---|
| Breden–Chu | `au:"Breden-Chu"` → **0** | `au:"Breden" AND au:"Chu"` → **3** | FALSE NEGATIVE |
| Dähne–Figueras | `au:"Dahne-Figueras"` → **0** | `au:"Dahne" AND au:"Figueras"` → **1** | FALSE NEGATIVE |
| ALS | `au:"Ambrose Lushnikov Siegel Silantyev"` → **0** | `au:"Lushnikov" AND au:"Silantyev"` → **7** | FALSE NEGATIVE |
| BCG | (compound surnames, meaningful) → 11 / 47 | `au:"Cao-Labora" AND au:"Gomez-Serrano"` → **6** | both forms real |

This is the same shape as leg 326's "Chae Tsai" false negative, reproduced independently on a
different query and a different group. **A zero from a group-name author query is a broken
instrument, not an absence**, and the corrected form is banked so the next leg does not re-earn
it. Both forms are kept in the JSON; neither is deleted.

## Part 6 — screening the census hits against the pre-committed candidate criterion

Criterion (iv) of the pre-committed protocol applies to Step B **or C** rows, so the author
census's hits were screened too, not just Step B's. 58 distinct arXiv ids; **51** absent from
both `solver/viscous_novelty.py::PRECEDENTS` and leg 303's own result sets; of those, **33**
appear in no repo file at all.

**That "33" needed its own instrument check, and failed the first one.** An unfiltered
`git grep <id>` reported **51/51 already cited** — because this leg's own raw JSON is a tracked
file and now contains every id it saw. Excluding this leg's five artifacts gives 33. The count
is only meaningful with that exclusion, the exclusion is in the runner
(`OWN_FILES`), and both numbers are in the JSON so the correction is auditable.

Applying leg 303's four clauses at title level (a deliberately generous screen that
over-selects): **0 of 51 clear all four.** Two clear three of four:

- **`arXiv:2310.05325`** — *Non-radial implosion for compressible Euler and Navier–Stokes in
  T³ and R³* — clears blow-up, dissipative, fluid; already cited in **35** repo files. Known
  ground, and a useful consistency check that the census's strongest hit is inside the
  repository's existing net.
- **`arXiv:1504.02775`** — *Splash singularities for the free boundary Navier–Stokes
  equations* (Castro, Córdoba, Fefferman, Gancedo, Gómez-Serrano; v1 2015-04-10) — clears
  blow-up, dissipative, fluid, and **is cited in 0 repo files**. Read at abstract depth, as
  criterion (iv) requires: **clause (a), certificate, FAILS** — the abstract states a purely
  analytical existence proof and mentions no computer-assisted proof, no interval arithmetic,
  no validated numerics. Clause (b) is only partial: the breakdown is a **splash**, the free
  boundary self-intersecting in finite time, not a blow-up of a norm of the velocity field.
  **Verdict: mechanical near-miss. It does not answer the gate YES**, exactly as the
  pre-committed criterion says a mechanical near-miss must not. It is banked with its link and
  its adjudication so a later leg can contest the judgement without re-running the search.

The remaining 32 uncited ids are the census authors' non-target bibliography — opinion
dynamics, Muskat, water waves, SQG patches, Langmuir-wave plasma physics. This is
corroboration, not novelty: it is what "each group has either left the object or stayed and
left certification" looks like from the author side.
