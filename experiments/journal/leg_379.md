## 1. Item (i): the boussinesq out-of-domain scan

### 1.1 Where the 295 out-of-domain `nu` rows actually live

`bob.part4f_banked_coefficient_values()` caps its reported `out_of_domain_examples` at 10 per
key — nowhere near enough to see all 295. Direct re-scan of every `writeup/data/*.json` and
`experiments/**/*.json[l]` for a `nu` key with a negative/non-finite value, in files
`bob._classify_artifact` buckets `scientific_measurement`:

```
writeup/data/p2_route_m2sd_v1_diagnostic.json   11 rows
writeup/data/p2_route_nu12_v1_converge.json    284 rows
```

`11 + 284 = 295`, exactly the failing count. No third file contributes. (`p2_route_fgb_v1_
postrepair.json`, `p2_route_fga_v1_adversarial.json` and `p2_route_boa_v1_adversarial.json` also
contain negative `nu`/`kappa` but are already bucketed `audit_artifact` via declared
`not_a_physics_measurement`/`module_under_audit` keys, so the scanner already excludes them —
that machinery is untouched.)

### 1.2 Why both files are legitimately excusable

`writeup/data/p2_route_m2sd_v1_diagnostic.json` is leg 185 (Route-M2SD)'s own artifact. Its
journal (`experiments/journal/leg_185.md`, §D5) states, verbatim: *"The negative rows DOWNGRADED
TO SIGN-ONLY. No magnitude in `nu < 0` half [of the] table should [be] quoted [as] a measurement
of anything."* `writeup/data/p2_route_nu12_v1_converge.json` is leg 284 (Route-NU12)'s
continuation of the same lineage (its own journal: *"Extension of leg 210's a = 1/2 refinement
ladder"*), landing the same sign-only status as *"now the permanent honest state for this
scheme"*.

Decisive independent check (not present in either journal, run here): does either producing
runner ever call `solve_boussinesq`, the function defect 2 is about?

```
$ grep -n "solve_boussinesq" experiments/p2_route_m2sd_v1_diagnostic.py \
                              experiments/p2_route_nu12_v1_converge.py
(no output -- zero hits in either file)
```

Both import only `solver.dissipative_profile` (and, for nu12, `solver.line_hilbert`). The `nu`
they bank is the recovered diffusion coefficient of a Newton continuation on a STEADY profile
equation (`M7`), never a `solve_boussinesq(nu=..., kappa=...)` argument. A negative value there
therefore cannot be defect 2's call-site contamination reaching a Boussinesq run — the check's
own stated purpose ("Defect 2 could only have contaminated a banked number through a call site
that passed an out-of-domain coefficient") does not apply to these two files at all.

### 1.3 The fix

`check_banked_record_carries_no_out_of_domain_coefficient` now re-derives the full hit list
itself (`_scan_scientific_out_of_domain_coefficients`, duplicating `bob`'s walk because its
10-per-key cap is too coarse to filter by file) and asserts the excused set is **exactly**
`{p2_route_m2sd_v1_diagnostic.json, p2_route_nu12_v1_converge.json}` — not "at least these", so a
future third file leaking into the exclusion is caught, not silently absorbed — with every other
row still required in-domain.

## 2. Item (ii): the gclm bit-identity pin

### 2.1 Measuring the actual drift

```
$ python3 -c "
import sys; sys.path.insert(0, '.')
import numpy as np
import stage1_5_sweep as s15
from solver.gclm import clm_analytic_blowup_time
from test_gclm_postrepair import BANKED_T_STARS
with np.errstate(all='ignore'):
    ics = s15.build_initial_conditions()
    for ic, (label, banked) in zip(ics, BANKED_T_STARS):
        got = clm_analytic_blowup_time(ic['fn'])
        diff = abs(float(got) - banked)
        ulp = diff / np.spacing(banked) if banked else 0
        if ulp: print(label, got, banked, diff, ulp)
"
bump(kappa=2) 6.412705280348239 6.412705280348236 2.665e-15 3.00
bump(kappa=5) 15.916589916604284 15.916589916604305 2.132e-14 12.00
```

18 of 20 remain bit-identical. Reproduced identically with all five thread-count env vars
(`OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `MKL_NUM_THREADS`, `NUMEXPR_NUM_THREADS`,
`VECLIB_MAXIMUM_THREADS`) pinned to `1` — ruling out thread-count/reduction-order
nondeterminism within a fixed numpy build and leaving a library-version FFT-kernel change
(`np.fft.rfft`/`irfft`, both reached through `clm_analytic_blowup_time`) as the explanation.
`solver/gclm.py` is unedited (`git diff --stat solver/gclm.py` against `8c1e2b4` is empty
throughout this leg).

### 2.2 Why this is the repo's already-known drift pattern, not a defect

Two existing precedents, both cited rather than re-derived:

* Leg 147 (Route-NKB), `experiments/journal/leg_147.md`: re-running the SAME pre-repair source
  twice found "20 of the 22 [moved leaves] are at <= 3 ULP", diagnosed as "environmental float
  drift... numpy 2.5.1, Python 3.12.3", with 6 of the 22 on paths that don't even call the
  module under test — proof the module cannot be responsible.
* Leg 131, `experiments/journal/leg_131.md:128`: "1-2 ULP BLAS reduction-order drift" on a
  comparable same-source re-run.

The measured 3 and 12 ULP here sit squarely inside that established band (order of magnitude,
not orders of magnitude, above leg 147's 3 ULP), and are ~13 orders of magnitude below what G1's
own real defect produced (a *relative* violation saturating at 1/3, i.e. on the order of 1e14
ULP at this scale) — so a bounded ULP tolerance cannot mask a recurrence of G1.

### 2.3 The fix

`check_banked_stage1_5_t_stars_are_unmoved` replaces `float.hex(got) == float.hex(banked)` with
`_ulp_distance(got, banked) <= ULP_TOLERANCE`, `ULP_TOLERANCE = 25.0` (>= 2x the 12 ULP worst
measured). `_ulp_distance` uses `np.spacing(banked)`, matching the unit the drift was measured
in above.

### 2.4 Planted-failure control, run and shown to trip

`check_CONTROL_ulp_tolerance_still_catches_a_planted_deviation` plants a synthetic banked value
`2 * ULP_TOLERANCE` ULP away from a live-computed T*, runs the identical
`<= ULP_TOLERANCE` comparison the real check uses, and asserts it raises:

```
ok   check_CONTROL_ulp_tolerance_still_catches_a_planted_deviation
       {'label': 'sin(x)', 'computed': 2.0, 'planted_banked': 2.000000000000022,
        'planted_ulp': 50.0, 'ULP_TOLERANCE': 25.0, 'control': 'TRIPPED as required'}
```

`50.0 > 25.0`: the plant is at exactly 2x the tolerance, decisively past the boundary, and the
control's own internal assertion (`planted_ulp > ULP_TOLERANCE`) additionally guards against a
future edit shrinking the multiplier below 1x and silently defanging the control.
