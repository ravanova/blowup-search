# Leg 105 — Route-ICB v1: independent post-repair regression check of `solver/interval_certificate.py`

**Date: 2026-08-06. Kind: regression check — standard. No figure — same "no measurement, no
figure" convention established for legs 86/87/98/103 (audit/regression legs of this shape).
No new physics, and none claimed.**

## Gate, verbatim

> Post-repair, does `solver/interval_certificate.py` (a) correctly reject every case in leg 98's
> original fabrication battery, and (b) still reproduce leg 61's Kawahara known-answer gate with
> zero regression?

## Answer

**YES, on both halves.**

- **(a) the battery.** Leg 98's own 39-case battery (36 hypothesis-violating), re-run
  independently — bound to the pre-repair module read out of git as a **negative control**
  first, then to the current module — reproduces **12/36 false accepts (8 load-bearing)**
  pre-repair EXACTLY, and gives **0/36** post-repair. This is derived from a source outside the
  repair's own territory: leg 98's case-construction code
  (`experiments/p2_route_ica_v1_adversarial.py`) is imported and run unmodified against each
  module in turn via a `sys.modules` substitution, never copied or re-implemented, and never
  relying on the repair's own `test_interval_certificate_adversarial.py` assertions.
- **(b) Kawahara, bitwise.** `kawahara_certificate()` run from the pre-repair module
  (`solver/interval_certificate.py` at `3e52386^1` = `03acb4e`, i.e. immediately before the
  repair merged) and from the current module, **in the same process**: `Y_0`, `Z_1`, `Z_2`,
  `A_norm`, `B`, `budget`, `Y0_over_budget`, `r_min`, `r_max`, every `conversion` factor, the
  full Newton history, and the converged coefficient vector are **bit-for-bit identical** —
  22/22 fields, 0 differences. Separately, `test_interval_certificate.py`'s own gate 16
  (`test_kawahara_known_answer_gate`) was run directly against current `main`: **all 18 gates
  pass** (929 s wall clock), printing "0.53 decades above our r_min" — the exact figure that
  gate's own docstring records as banked at leg 61.

## Why this is not just re-running `test_interval_certificate_adversarial.py`

That file's `test_banked_battery_reproduces` was written **inside the same commit** as the
repair, calling leg 98's own runner against whatever module is on disk. It is a legitimate
regression pin but it is the repair grading its own homework, and it is silent on clause (b)
entirely. This leg is independent on both counts: the battery differential is bound to a module
read fresh out of git by THIS leg's own code, with a negative control proving the harness would
have caught the pre-repair defect had it still been there; and the Kawahara half is a check
nothing on `main` performs at all.

## The one thing the novelty pass predicted and the run confirmed

§3 of `writeup/novelty/leg_105.md` pre-committed, before any number was seen, that a
literal-value comparison against the banked `writeup/data/p2_route_ka_v1_kawahara.json` would be
the WRONG test for "zero regression" — because `Y_0 ~ 3e-17` sits at the float64 noise floor of a
fully-converged Newton iterate, an inherently environment-sensitive regime. The construction run
confirmed this precisely: the **literal leg-61-original source** (`solver/interval_certificate.py`
at `83099a8` together with `solver/interval.py` at the SAME commit, reconstructed via a
package-shadowing import and re-run today) gives `Y_0 = 2.9616446211384186e-17`, deterministically
and repeatably across three independent process launches — but the value **committed in the JSON**
is `3.024251708561549e-17`, a **~2.1% difference**, from the identical source text. This predates
BOTH repairs (leg 69's `solver/interval.py` fix and this leg's `solver/interval_certificate.py`
fix): re-running `03acb4e` (pre-`interval_certificate`-repair, post-`interval`-repair) and the
current module both give the SAME `2.9616446211384186e-17` as the literal leg-61-original code —
all three agree with each other and none agrees with the committed JSON. **Conclusion, stated
precisely so it cannot be mistaken for a regression finding:** this is an environment
(BLAS/LAPACK build, thread count) sensitivity of a converged-to-machine-precision quantity, not a
code regression, and it is orthogonal to this leg's gate. It is recorded, informationally, in
`writeup/data/p2_route_icb_v1_postrepair.json` under `part_d_banked_json_crosscheck_informational_only`
— explicitly excluded from the pass/fail criterion — and is NOT patched:
`writeup/data/p2_route_ka_v1_kawahara.json` is leg 61's territory, not this leg's, and re-running
it is not evidence of anything wrong with either repair (the bitwise same-process differential in
part (b) is the actual, environment-independent zero-regression evidence).

This is also why gate (b) is measured as a **same-process bitwise differential** rather than as
"matches the banked JSON": the differential holds the environment fixed and varies only the one
file under test, which is the only comparison that is actually informative here.

## What was done, in order

1. `plan_of_record.py` run first, all ten live bans read individually; none bites (see
   `writeup/novelty/leg_105.md` §0). `capabilities.py:170-190` (the
   `solver/interval_certificate.py` entry) read in full before construction.
2. Novelty pass run and **committed before construction** (`7d2791d`), pre-registering: the
   ban ruling, the in-repo prior-art sweep showing no independent post-repair check exists, and
   — the one substantive pre-commitment — that a same-process bitwise differential, not a
   comparison against the banked Kawahara JSON, is the correct zero-regression test (§3, backed
   by a three-repetition determinism check run BEFORE the pass was committed).
3. `experiments/p2_route_icb_v1_postrepair.py` built: locates the repair's merge commit by
   **subject substring** (`fix-interval-certificate-validation`), not by hash, so a rebase of
   history upstream of this leg cannot silently break the differential (leg 86's technique for
   the sibling repair); loads the pre-repair module via `git show <merge>^1:...` + `importlib`
   (leg 103's technique for `solver/gclm.py`); runs the battery both ways via a `sys.modules`
   substitution that redirects leg 98's own, unmodified case-construction code to whichever
   module is under test; runs `kawahara_certificate()` from both modules in the same process and
   diffs every returned field; replicates leg 61's gate-16 assertions directly (no 15-minute
   subprocess); and reads the banked Kawahara JSON once, informationally.
4. `test_interval_certificate_postrepair.py`: 6 gates, ~76 s, all pass — a negative control, the
   independently re-derived battery gate (a), the bitwise Kawahara differential gate (b), a
   sanity check that the pre-repair certificate independently closes (so "bit-identical" isn't
   vacuously comparing two failures), leg 61's known-answer gate reproduced directly, and a
   static-diff check that the repair only ADDED top-level definitions, never removed one.
5. `test_interval_certificate.py` (leg 61's own 18-gate suite) run directly against current
   `main` as an additional, independent confirmation: **all 18 pass**, 929 s.
