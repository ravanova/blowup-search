## The repair, in full

`solver/certificate_guards.py`, five surfaces, two new module-private helpers, no change to
any range, sign or message the module already produced on a hypothesis-satisfying input.

* **`_require_real(name, value, allow_none, why)`** — `TypeError` unless `value` is a
  `numbers.Real` that is **not** a `bool`. `bool` is tested **first and explicitly**, because
  `bool` being a `numbers.Real` subtype is exactly M3's trap. Installed at all three
  scalar guards, so the file stops giving two answers to the same value.
* **`_is_negative_below_the_float_floor(value, f)`** — `f == 0.0 and value < 0`. The sign is
  read from the **exact** value, so `float()`'s underflow of a negative rational to `-0.0`
  can no longer land it on the nonnegative side of the test. `-0.0` itself stays admissible:
  `-0.0 < 0` is `False`.
* **`ValueError` on the vacuous input** in `hypothesis_violations`,
  `positive_weight_violations` and `invalid_input_reason` — an empty constants tuple, an
  empty weight vector, and an empty violation list respectively.

The `TypeError` message template is byte-identical to the one `hypothesis_violations`
already raised; only its **tail** varies by surface (`WHY_CONSTANTS` verbatim as before,
`WHY_RADIUS` and `WHY_EXPONENT` new), because `r_min` is a radius and gamma/alpha are
exponents, and telling a caller that "the radii polynomial's constants are norms" when it
passed a string exponent would be a wrong sentence newly introduced by a repair.

`solver/nk_bounds.py` is **byte-identical** to what this leg inherited, as are all four
consumers.

## The 2 that resist, and the line of leg 199 that forbids claiming them

### `D1b_empty_at_the_consumer` — the accept is evaluated in a file this leg may not edit

Leg 199 measured this one at the **consumer**, and its `guard_accepted` flag is literally

```python
screen_passes_empty = bool(np.all(np.isfinite(np.array([]))) and np.all(np.array([]) > 0.0))
```

— an expression evaluated at `solver/nk_bounds.py:225`, where the numpy pre-screen decides
whether the shared guard is consulted **at all**. For an empty array it is `True`, so the
guard is never called, and the failure surfaces four lines later as numpy's
`ValueError: zero-size array to reduction operation minimum which has no identity`. Nothing
in `certificate_guards.py` is on that path. The repaired guard **does** now refuse the same
empty vector at its own surface — that is `D1_empty_ndarray`, counted, and it is a different
case. Widening the diff into `nk_bounds.py` to reach it would have violated the territory
(leg 215's file), and would have bought the gate a YES by editing a module this leg was
explicitly told not to touch.

### `B_nonreal_Fraction` — repairing it would refuse an input leg 199 banks as a control

`Fraction` **is** `numbers.Real` (it registers as `numbers.Rational`). Leg 199's M2 heading
calls its four probe types "non-`numbers.Real`"; two of the four — `bool` and `Fraction` —
are not, and leg 199's own JSON says so in the `reference` field for this very case: the
sibling `hypothesis_violations` returns `[]` on `Fraction(1, 2)`, i.e. accepts it.

So M2 as leg 199 *defined* it — "a type gate in one guard, absent in the others, **in the
same file**" — is fully repaired: the two guards disagreed on 2 of the 4 types and now
disagree on 0. What that does not do is make a `Fraction` radius reject, because the sibling
this guard was brought into parity with accepts it.

Closing the case would require refusing every non-`float` real, and that is blocked by leg
199's own text, twice over:

> The discrimination control lives in the same gate: `Fraction(-1, 3)` is correctly refused,
> so this is a **float-conversion boundary, not a `Fraction` blind spot**.

Refusing `Fraction` by type turns that control's `["Y_0 is negative …"]` into a `TypeError`
— a rejection of a different kind, decided before the value is ever looked at — and
re-litigates the finding leg's measurement, which the repair-family precedent (legs 150–154)
forbids. It would also refuse an *exact rational* bound, which is a strictly better input
than the float64 the caller would otherwise pass. The honest move was available and was
refused; the decision is recorded in `writeup/novelty/leg_216.md` §4, **before** the result,
not rationalised after it.

## Controls (17, all pass, 0 failures)

* **Over-rejection, the failure mode a rejection layer creates.** `float`, `np.float64`,
  `int`, `np.int64` and `Fraction` are accepted at **both** `hypothesis_violations` and
  `radius_violation` — 10 checks, 10 pass. A repair that started refusing `np.float64` would
  have broken every consumer silently, since numpy scalars are what the pipelines actually
  pass.
* **Leg 199's M4 discrimination control is intact.** `Fraction(-1, 3)` is still refused **by
  value**, with the negative-bound message, not by type.
* **`-0.0` is still an admissible bound** — the M4 fix tests `value < 0`, which is `False`
  for `-0.0`, so the docstring's "`0.0` and `-0.0` are legitimate bounds" still holds.
* **`allow_none` is unmoved.** `port_certification`'s kill-switch semantics still skip a
  `None`; with `allow_none=False` a `None` still raises.
* **Two pre-existing rejection strings are byte-identical**, asserted as string equality:
  the `str` `TypeError` and the `Y_0 is negative (-1.0)` violation.
* **A one-element weight vector is not swept up by the empty-container fix.**
