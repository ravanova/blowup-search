# Leg 129 — Route-SUR: the dealias-boundary repair, and the no-op that licensed it

**Branch** `leg/129-sur-v1`. **Exploration/repair leg, standard, CLAIM-BEARING** (it moves
numbers in a shared numerical core).
**Gate: YES on all three clauses — but PARKED, NOT LANDED, under escalation #4.** Both 2/3-rule
masks are now strict (`k < n/3`), bit-identical on every grid the repository has ever run;
`energy_production`'s alias error at `3 | n` falls from **1.6621e-01 to 1.4543e-15** (14.1
decades); and all five silent-absorption defects are closed with their seven pins inverted,
11/11 checks passing.

**Why it is parked (read this first).** The corrected cut moves the 2D solver's minimum
admissible grid from `n >= 3` to `n >= 4`, because under a *strict* 2/3 rule an `n = 3` grid
retains `|k| < 1` — the mean mode alone — and leg 89's condition-based guard rejects it
unmodified. That moves exactly **one of leg 133's 90 banked battery verdicts**: family
`E_degenerate_discretization` goes from `raised 13 / benign 3` to `raised 14 / benign 2`.
Making `test_boussinesq_postrepair.py::check_battery_family_census_matches_the_banked_one`
pass would require rewriting `writeup/data/p2_route_bob_v1_postrepair.json`, and **rewriting a
banked result in `writeup/` is escalation #4** — never merged without the user. Leg 133's own
check says so in its docstring: *"A change that kept the silent count at zero while moving
cases between `raised`, `flagged` and `benign` would be a real behavioural change and must be
looked at, not absorbed."* It fired, and it is being looked at rather than absorbed.

The move is strictly in the **safer** direction and nothing regressed: `n_quieter = 0`
(unchanged), `n_louder` 40 → **41**, `n_silent_to_raised` **23** (unchanged), all 90 cases still
report zero silent, and leg 133's bitwise `n = 32` regression hashes
(`check_zero_regression_n32_hashes_are_unchanged`) still **pass**. 15 of the 16 checks in that
file pass; the census check is the only failure in the entire affected-test set.

**The licence, stated first because it is the whole leg:** a bitwise A/B against the pre-repair
`solver/` tree read out of git moved **0 of 156** power-of-two and banked quantities — including
four end-to-end solver integrations — while the deliberate `3 | n` control moved **33 of 33**.

## What the novelty pass changed about the leg

A repair leg's novelty pass has a different job from an audit leg's, and this one earned its
place three times.

**It confirmed the repair direction from a source leg 120 did not have.** arXiv:2603.08892
(2026) zeroes every mode with `|k| >= (2/3)k_N = n/3`, making the retained set strict —
independently of Bowman 2013. This was the one direction in which the leg could have been
wrong: a single authority retaining `k = n/3` would have made this a contested convention change
rather than a defect fix, and the leg would have parked instead of landing.

**It stopped an over-claim.** The repair form `(n - 1) // 3` is **not published** — no source
found writes the retained set as an integer expression. So the runner *proves* it (0
counterexamples to `(n-1)//3 < n/3 <= (n-1)//3 + 1` over `n = 1..5000`) instead of citing it,
and the prose says "arithmetic identity", never "standard form".

**It recorded a source that appears to disagree, rather than only the two that agree.**
FourierFlows.jl's documentation says "filter out all modes with `k > N/3`", which read literally
retains `k = N/3`. A follow-up fetch found the page specifies only a *fraction*
(`aliased_fraction = 1/3`) and never an index expression, so it does not actually decide the
boundary case. It is recorded as an unresolved ambiguity, and the leg's argument is restructured
so that nothing depends on how it resolves — the elementary derivation (`n <= 3K` ⟺
contamination) and leg 120's measured 0.25 settle it without any authority at all.

## What was repaired

`solver/spectral_utils.py`: `dealias_mask` cuts at `(n-1)//3`; `derivative_hat` multiplies the
Nyquist entry by zero (Johnson Alg. 1) instead of assigning it; `velocity_hat` allocates
`complex128` and multiplies the mean mode by zero; `hilbert_hat`/`derivative_hat`/`velocity_hat`
validate `k` through one `_require_k`; `grid`/`wavenumbers`/`dealias_mask` refuse a degenerate
`n` through one `_require_grid_size`, with `dealias_mask` additionally refusing any `n` whose
strict cut retains no non-mean mode (leg 89's 2D guard, in 1D).
`solver/boussinesq.py`: `dealias_mask2d` takes the same `(n-1)//3` cut. Nothing else in that
file is touched — leg 133 measured it bitwise at `922af67` and that baseline is inherited.

The `+ 0.0j` in the two multiply-by-zero sites is not decoration: a multiplication can produce a
*signed* zero, and the A/B compares raw bytes, so `-0.0` would have registered as a moved
quantity. It normalizes to exactly `+0.0 + 0.0j` on finite input and lets `nan`/`inf` through.

## The measurement, and the mistake in it that the control caught

**Lesson 90, earned again, on my own harness.** The first run of the A/B reported *0 differing
in every bucket, including the `3 | n` control that the repair is guaranteed to change.* That
was not a no-op; it was a dead harness. Importing the runner executes its module-level
`sys.path.insert(0, REPO)`, which put the repaired tree ahead of the extracted pre-repair one,
so both sides of the comparison were the same module. Four identical numbers should read as a
bug, not a finding — and here 156 identical numbers did.

The fix: re-insert the extracted tree at the front *after* the module body runs, purge `solver`
from `sys.modules`, and make the control an **executable assertion** — if fewer than 33 of 33
control quantities move, the runner aborts with `HARNESS DEAD: … Every no-op claim in this run
is void.` Post-fix the control moves 33/33 (top retained mode drops by exactly one at all eleven
`3 | n` grids) and the banked buckets still move 0/156. Neither number means anything without
the other, and the figure carries both.

**The census was re-run, not quoted.** Leg 120 counted 107 banked `energy_balance_residual`
records in two files. Legs 103 and 133 have since banked more: **129 records in four files**,
still **0** exposed, because all eight declared grid sizes on the dealias path are powers of two.

## The escalation, in full

`solver/boussinesq.py` line ~366 carries leg 89's guard, which raises when *"the 2/3 dealias
mask retains only the mean mode"*. It tests the **condition**, not a hard-coded `n`, which is
why it needed no edit — and why it changed behaviour the moment the mask became correct:

| `n` | retained modes, old cut | retained modes, new cut | accepted? |
|---|---|---|---|
| 1, 2 | 1 | 1 | rejected, before and after |
| **3** | **2** | **1** | **was accepted, now rejected** |
| 4, 5, 6 | ≥ 2 | ≥ 2 | accepted, before and after |

At `n = 3` the strict band is `|k| < 1`. A 3-point grid genuinely cannot carry a non-constant
field under a correct 2/3 rule, so the rejection is right — but "right" is not the same as
"this leg's to land", and the number it moves was banked by another leg six commits ago.

**What is NOT affected, measured rather than asserted:** no power of two, no banked grid, no
`energy_balance_residual` record (0 of 129), and none of the 156 quantities in the bitwise A/B.
`n = 3` and `n = 4` appear in no run anywhere in the repository outside these two adversarial
batteries. The leg's own pre-committed no-branch — *"if ANY power-of-two-grid quantity changes
at all, stop and escalate"* — did **not** fire, and is recorded here as not having fired so
that the escalation is not confused with it. This is a different and narrower thing: a
non-power-of-two degenerate-grid verdict that another leg banked.

**What the user/DM is being asked to decide:** whether to re-bank leg 133's `E` family census
as `14/2` (the repair is correct and the move is strictly louder), or to reject the 2D half of
this repair. The 1D half is independent of this question and unaffected by it.

Two dependent test edits are already made and are *not* the escalation — they are ordinary
in-kind updates whose intent is preserved exactly:
`test_boussinesq_adversarial.py::check_repaired_degenerate_grid_is_rejected` (the `n = 3` case
moves from the "must run" list to the "must be rejected" list) and
`test_boussinesq_postrepair.py::check_CONTROL_valid_input_is_still_accepted` (whose "smallest
grid that can carry a non-constant field" becomes `n = 4`). Both files pass afterwards except
the census check named above. The guard's error message was updated from "n >= 3 required" to
"n >= 4 required" for the same reason.

## The price, measured rather than waved away

Per-call validation in the solver's inner loop is not free. Min-of-3 per variant, interleaved
and repeated (runner §C3): `hilbert_hat` **1.12×**, `derivative_hat` **0.88×**, `velocity_hat`
**2.06×**, and the headline — a full 200-step `n = 64` gCLM integration — **1.06×**, i.e.
**+6.4%**.

The first version was **+14.5%** because `_require_k` called `np.asarray`/`np.shape` every
call; reading `.shape` directly gives identical refusals for about a seventh of the cost.
Found by measuring, not by inspection, and only because the slow `test_critical_dissipation.py`
prompted the question.

**A cheaper `velocity_hat` exists and was deliberately refused**: divide the whole array by
`|k|` with the zero entry replaced by `inf` and add `0.0j` once. That removes the masked
assignment, but the trailing `+ 0.0j` would then also normalize signed zeros in the *non-zero*
modes, so any entry whose quotient is `-0.0` changes bitwise — trading this repair's entire
licence for 6%. Recorded so it is not silently rediscovered as an improvement.

## Honest limits

- Every number here is a statement about **code behaviour**. None is a physics measurement,
  none contests a banked result, and **no link of the L1→L4 chain moved**. The odds stay 0.05%.
- The no-op is measured at the configurations the repository uses — the strongest available
  form, but not "for all `n`". At `3 | n` the module deliberately returns something different.
- The "3 ∤ n unchanged" column shows the repair is *confined to the boundary*; it is not a proof
  that the rest of the module is correct.
- D4 stays the weakest of the seven, exactly as leg 120 reported it: the erased value was the
  intended zero-mean convention, so only the lost corruption signal was ever a defect.
- The repair was checked for **over-truncation** as well as under-truncation — the regression
  suite asserts `K + 1 >= n/3` alongside `K < n/3`, so a "fix" that silently threw away
  resolution would fail.
