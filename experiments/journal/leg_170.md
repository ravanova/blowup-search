**Reconciliation with leg 154's `15/15`, which is a different construction and not a

first, and that ordering is pinned.

`planted_dissipative_control(a=0, p=1.9, ...)` also refuses, so the guard is not bypassed by
the one entry point that routes through `dissipative_spectrum` without a `b0`.

## 4. The one assertion that did not survive re-running — and why it is not a gate failure

The interrupted session's test file asserted that the pre-repair module reproduces leg 121's
banked C2 triple `(residual, alpha, alpha_1)` **bit-identically**. **It does not, on 0 of 9
rows — 0 of 27 numbers.** I found this by re-running rather than inheriting it, and it is
reported here rather than papered over.

It is **not** the repair, and the harness separates the two rather than arguing it:

* the post-repair escape hatch and the pre-repair module at `9dba93f`, run through the
  identical harness in **one interpreter**, agree on **`9 / 9` rows**;
* both miss leg 121's banked JSON on **`9 / 9` rows**, by the same amount. A difference the
  pre-repair module shares cannot have been introduced by the repair;
* neither `experiments/p2_route_cda_v1_adversarial.py` nor
  `writeup/data/p2_route_cda_v1_adversarial.json` has been modified since leg 121's own
  commit `c4ddb7f`, and leg 121's C2 calls `mu_branch(0.0, p_fake, [0, 0.05, 0.1], K=64)` —
  byte-identical to the code path R4 drives. So the configuration is not the difference.

**Magnitudes, because ULP is the wrong unit here.** The raw worst is `1,407,374,883,553,281`
ULP, and that number is arithmetically correct and nearly meaningless: it sits on the
`p_built = 1` residual, `9.71e-16` banked against `1.25e-15` today — an absolute move of
`2.78e-16` on a machine zero. Excluding quantities that moved less than `1e-13` in absolute
terms:

| `p_built` | quantity | absolute | relative |
|---:|---|---:|---:|
| 2 | `alpha` | 1.17e-13 | 1.07e-13 |
| 2 | `alpha_1` | 1.10e-12 | 7.50e-13 |
| 3 | `alpha` | 1.01e-09 | 8.64e-10 |
| 3 | `alpha_1` | **1.04e-08** | **2.95e-09** |

The drift grows with `p_built` for a mechanical reason worth recording: the `p = 2` and
`p = 3` branches terminate Newton at residual `1.50e-05` and `2.88e-06` respectively, **not**
at machine precision, and a loose termination is exactly where a LAPACK change moves the
converged iterate. The `p = 1` branch, which does converge to `~1e-15`, drifts by `4.44e-16`
relative on `alpha` — two ULP.

**Consequence, stated plainly:** leg 121's banked JSON is a **drifted reference**. It cannot
serve as a *bitwise* reference for any future leg on this environment. It does **not** touch
either clause of this gate — clause (b) compares pre against post in one process, where the
environment cancels exactly, and clause (a) is about refusals. The test file now pins the
drift as a bounded characterization, `max(1e-13 absolute, 1e-7 relative)`, chosen loose
enough to absorb the measured `2.95e-09` and tight enough that a real regression in the
exponent path — which would move `alpha` by `O(1)`, the whole point of leg 121's finding —
still trips it. It can report the other answer.

## 5. Leg 121's own driver no longer runs — escalation, not a gate failure

Leg 135's rule: a repair that makes the escalating leg's battery unrunnable destroys the
record that authorised it. Leg 147 found leg 116's battery aborting in `0.9 s` and nobody
noticed. So this was probed directly, running leg 121's banked driver **unmodified** from a
scratch copy at the same directory depth (so its own `parents[1]` JSON write lands outside
the repository and no file outside this leg's territory is touched).

**It aborts in `0.18 s`, return code 1, completing `0 / 9` sections — including `0 / 3` of
the evidence sections that authorised the repair.** It dies at the first non-integer request
it makes, `p = 1.1` in C1, on the new `CriticalDissipationDomainError`.

This is the repair working as designed on a caller that predates it: leg 154's
`on_noninteger="truncate"` hatch exists precisely for this, and leg 121's driver predates the
hatch and does not pass it. The record is **not** lost — R4 reproduces leg 121's end-to-end
C2 triple through the hatch, `9 / 9` rows bit-identical to the pre-repair module in process,
which is a check leg 154 performed at construction level only (its banked rows carry
`alpha_pre = 0.8` off a synthetic `b`, not a Newton solve). The hatch emits exactly one
`RuntimeWarning`, it names the substitution, it is not the default, and it **does** reach a
default-configured interpreter's stderr (verified in a clean subprocess).

**But the banked suite must therefore be this leg's test file, not leg 121's driver.** The
yes-branch says "bank leg 121's battery as a permanent regression suite"; the battery as
literally shipped cannot execute against the repaired module, so what is banked is the
reconstruction in `test_critical_dissipation_postrepair.py`, whose cases are rebuilt from leg
121's JSON. Recorded so the distinction is not lost.
