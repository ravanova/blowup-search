## 1. One fix made before banking: `p2_route_cvf_v1_classify`'s false NON-PORTABLE

Auditing the ten checkpoints leaf-by-leaf (per this cycle's DM sharpening: don't accept a
surprising non-portability reading without checking the invocation first), `p2_route_cvf_v1_
classify` classified NON-PORTABLE with `max_rel_move = 0.0` and zero flag flips — the sole
disagreement was one string leaf, `sections_served_from_cache_this_invocation`, `True` in the
bank and `False` on regeneration.

Checked directly: this leg's own prior commit (`12732da`) had already verified `p2_route_cvf_v1_
classify`'s `CVF_CACHE` memoisation is inert when the env var is unset (`cached()` becomes a
passthrough) — so the *computed values* were never in question. The leaf itself just records
whether this particular invocation happened to find a warm scratch cache. The banked run had one
(built up over that family's own earlier legs); this census's regeneration runs inside a fresh
throwaway `git archive` copy with none. That is exactly the same shape of false-positive this
runner had already fixed once for `p2_route_cap_v1_audit`'s `head`/`interpreter` leaves
(`75971a4`) — a leaf that RECORDS how the run was invoked, not what it computed. Rather than
special-case one family, `is_provenance()` in `experiments/p2_route_epa_v1_census.py` was
extended with a substring marker (`served_from_cache`, `cache_this_invocation`) so any future
censused family with the same pattern is caught the same way, and the exclusion is disclosed in
full (`provenance_moves`) rather than silently dropped. The single affected family's checkpoint
was deleted and regenerated (`--families p2_route_cvf_v1_classify`); it now reads PORTABLE at
both refs with the disagreement recorded, not hidden, under `comparison.provenance_moves`.

This is disclosed as a leg-287 methodological correction to leg-287's own runner, not a value
change to any banked artifact under census — no banked JSON was written to, and the fix was made
and reran BEFORE the final `p2_route_epa_v1_census.json` was assembled, so the corrected number is
what is banked, not a post-hoc override of a wrong one.

## 3. The one genuine non-portable family, in detail: `p2_route_e_v1_spectrum`

At its own banking commit (`c45e8189`, 817 commits and 37 solver-file changes ago): `max_rel_move
= 1.880`, 62 of its numeric leaves moved by more than 10%. The worst mover is not quiet drift —
`E5_sweep[0].kept.0.1[5][1]` banked at `-8.1349` and regenerates at `+7.1563`, and the very next
sample (`[9]`/`[10]`) banked at `∓7.1563` and regenerates at `±14.828`. These look like an
ordering/labelling instability in a spectral sweep close to a degeneracy (adjacent kept-mode
values swapping sign and shuffling which index they land at), not a magnitude perturbation of one
number — structurally the same KIND of failure leg 252 found (a decision made at the edge of a
basin), reached by a different route (mode ordering rather than a converged/not-converged flag).
The determinism control (second independent regeneration at the same banking commit, same
environment) also disagrees with the FIRST regeneration on one leaf
(`determinism_control.two_processes_agree_on_nonvolatile_leaves: false`,
`n_leaves_differing_between_repeats: 1`) — so this family carries genuine run-to-run
nondeterminism WITHIN one environment as well as across environments, a strictly worse defect
than leg 252's (that family was at least deterministic within a single environment; this one
is not fully so even there). The positive control fired correctly beforehand
(`E6_control[1].strength` perturbed by 1e-9, detected exactly), so the "no movement" reading on
the other nine families is not a blind comparator.

## 4. `p2_route_nka_v1_adversarial`: distinguishing a genuine source-change break from both
   failure classes named in this cycle's DM ruling

At its own banking commit `p2_route_nka_v1_adversarial` is PORTABLE (`max_rel_move = 3.85e-12`,
below the `1e-9` threshold, driven by ordinary float noise, not a basin decision). At HEAD it
does not run at all: `solver/nk_bounds.py`'s `farfield_modelling_error_bound` now raises
`ValueError` because a downstream parameter (`LIVE_GAMMA`) evaluates to `alpha = 2.0`, exactly the
boundary the function's own docstring says the max-over-window trick stops being valid at
(`alpha < 2` required). `nka`'s own runner is unchanged since banking
(`runner_changed_since_banking: false`); `n_solver_files_changed_since_banking: 25`. Checked
against this cycle's two named failure classes:

- **Not leg 252's class (environment drift):** the failure does not occur at the banking commit
  where code is held fixed against this environment — it is entirely a HEAD-vs-banking-commit
  difference, i.e. `solver/nk_bounds.py` genuinely changed underneath this family (a validity
  check was added or tightened by a later, unrelated leg), reproduced identically in both of this
  leg's own two runs (no flakiness).
- **Not leg 335's class (a harness/runner argv bug):** the CENSUS's own invocation of `nka`'s
  runner is identical at both refs — `regenerate()` calls the same command with the same flags
  regardless of ref; only the checked-out `solver/` tree differs. There is no missing or wrong
  CLI argument to blame; the runner's own `run()` entry point is what raises.

So this is a third, distinct thing from either named class: a **downstream solver-code
tightening** that happens to make one of `nka`'s adversarial cases fall outside a validity
boundary that was fine (or unchecked) at banking time. It is banked here as
`classification_at_head: IRREPRODUCIBLE-AT-HEAD` with the traceback in full
(`head_failure_detail`), attributed correctly rather than folded into either the environment- or
harness-bug bucket.
