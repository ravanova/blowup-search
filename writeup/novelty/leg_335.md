## In-repo questions (answered from the repository, not the web)

### R1. Has the mechanism already been named, anywhere in the repo?

**No.** `experiments/journal/leg_221.md` measures the gap three independent times (403s and
1086s runner passes, plus an isolated hand-run, all 16 008/16 008 `odd_field_x_slope` calls
bit-identical to each other) but never inspects *why* the regenerated run diverges from the
banked one — it explicitly scopes that question out ("outside this leg's territory"). No other
journal entry, correction, or `writeup/novelty/*.md` file mentions `spike1_stepC_gate`'s

`experiments/journal/*.md` (only leg 221 and leg 286's unrelated mention of the same filename

### R2. Is there existing instrumentation in the repo relevant to an environment-sensitivity
hypothesis (BLAS/thread nondeterminism in the same solver family)?

**Yes — direct precedent, found and read before any diagnosis here.**
`experiments/leg_0_bench_newton_threads.sh` is a standing bench script that sweeps
`OMP_NUM_THREADS`/`OPENBLAS_NUM_THREADS`/`MKL_NUM_THREADS` against `solver/profile_newton.py`'s
continuation solve, built specifically to test "does a stall level move with the BLAS thread
count." Its own header note: "three repeats already showed it is deterministic WITHIN a fixed
environment." This is prior art for the *shape* of hypothesis (BLAS-thread nondeterminism in an
iterative solve) but is a different module (`profile_newton`, not `boussinesq_rescaled`) and a
different symptom (a Newton stall, not a relaxation-length mismatch), so it does not pre-empt
this leg's diagnosis — it only means the BLAS-thread-sensitivity hypothesis is not new to this
project and should be checked, not assumed, per this leg's process (§below).

### R3. Is `spike1_stepC_gate.py`'s relaxation known to drift / fail to converge?

**Yes — named and diagnosed for a different purpose.** `experiments/diagnose_stepC_drift.py`
(pre-dates leg 335, print-only diagnostic, listed in `UNBANKED_CALLERS` of
`experiments/p2_route_bvrr_v1_repair.py`) measures that the un-renormalized relaxation drifts
at a rate depending on grid/boundary parameters, which is why commit `1a3e63c` ("Spike 1 Step
C: diagnose relaxation drift + fix it — gauge renormalization") added `renorm=True`. This is
relevant background (the relaxation is known to not cleanly reach a fixed point even with the
fix — see this leg's own residual measurements) but is not a prior diagnosis of *this* gap: it
predates the gap by construction (it is the mechanism the renorm fix was built against, not an
explanation for why a post-renorm re-run in 2026-08 disagrees with the post-renorm banked JSON
from 2026-07-25).
