## 0. Calibration read first

Per `CONTINUATION_PROMPT.md`'s 2026-08-11 calibration: **arbitrary-precision interval
arithmetic is old, well-populated ground** — this is explicitly not a vacated cell in the
outside literature (unlike most of this repository's own object-level questions), it is one of
the most mature subfields of rigorous numerics. The weighting called for is therefore the
opposite of the usual instruction: **locate the existing prior art properly and say plainly why
this leg is not simply importing it**, rather than run a recency sweep.

## 1. What already exists, named and linked

- **INTLAB** (Rump, 1999–), MATLAB, the reference implementation of directed-rounding interval
  arithmetic with automatic differentiation and verified linear algebra:
  <https://www.tuhh.de/ti3/rump/intlab/> — the *same author* (S. M. Rump) whose BIT 2012 paper
  is already this repository's own citation for the underflow-aware error terms in
  `solver/interval.py` (see that file's header, `_ETA_TERMS_PLAIN`/`_ETA_TERMS_DOT2`). INTLAB is
  double-precision, not arbitrary precision, but is the ancestor of the verified-linear-algebra
  techniques this leg needs (verified `σ_min`, verified eigenvalue enclosures via Rohn's/Rump's
  methods) for leg 176's problem shape.
- **MPFI** (Revol & Rouillier, 2005), the C library for arbitrary-precision interval arithmetic
  built on MPFR: <https://gitlab.inria.fr/mpfi/mpfi>, and its algorithmic paper
  Revol & Rouillier, *Motivations for an arbitrary precision interval arithmetic and the MPFI
  library*, Reliable Computing 11 (2005), 275–290. This is the direct ancestor of "Fraction/
  arbitrary-precision endpoints + directed rounding," i.e. exactly this leg's shape, built on
  IEEE-754-style correctly-rounded arbitrary-precision floats (MPFR) rather than exact rationals.
- **mpmath's `iv` module** (Johansson et al.): <https://mpmath.org/doc/current/contexts.html#the-mpi-type>
  — arbitrary-precision interval arithmetic in pure Python, the nearest existing analogue to what
  this leg is scoped to build, and NOT a dependency this repository carries
  (`requirements.txt` is numpy-only; mpmath is not installed). This is the single closest prior
  artifact and the honest baseline this leg is measured against.
- **Arb / FLINT** (Johansson, 2012–), C library, ball arithmetic (midpoint-radius rather than
  endpoint intervals) at arbitrary precision, the current state of the art for verified
  transcendental function evaluation at high precision:
  <https://arblib.org/>, Johansson, *Arb: efficient arbitrary-precision midpoint-radius interval
  arithmetic*, IEEE Trans. Computers 66 (2017). Ball arithmetic is a different representation
  choice from this repository's own endpoint `Interval` (`solver/interval.py`'s docstring
  motivates endpoints), noted here as the alternative this leg does not adopt, matching the
  existing module's own choice rather than introducing a second convention.
- **kv library** (Kashiwagi, 2008–), C++, arbitrary-precision interval arithmetic plus verified
  ODE solving and eigenvalue enclosures: <https://github.com/mskashi/kv> — the nearest prior art
  specifically for the *verified eigenvalue / matrix problem shape* leg 176's re-measurement
  needs (Kashiwagi's verified eigenvalue enclosure methods, and Rohn's interval linear algebra
  more generally: J. Rohn, *A Handbook of Results on Interval Linear Problems*, 2005).
- **Boost.Interval** (Brönnimann, Melquiond, Pion, C++ Boost library) and **Sollya**
  (De Dinechin et al., INRIA) round out the standard C/C++ toolchain census; neither is Python,
  neither is stdlib, both are the shape of dependency this repository's `requirements.txt`
  explicitly excludes.
- **Julia's `IntervalArithmetic.jl`** (Benet, Sanders et al., JuliaIntervals) plus
  `ArbNumerics.jl` (Arb bindings) is the modern actively-maintained open-source arbitrary-
  precision interval stack, not Python and not stdlib.

**The pattern across all seven items: every one of them is either (a) not Python, (b) a
third-party Python dependency this repository's `requirements.txt` does not carry, or (c) fixed
at double precision (INTLAB).** None is `import`-able here without the dependency-change process
this leg's brief explicitly reserves to the orchestrator (`requirements.txt` is numpy-only and
scipy is excluded by name).

## 2. Why this leg does not simply import one of them

Two independent reasons, both binding:

1. **The dependency ban.** Every arbitrary-precision interval library above is a compiled
   extension or a pure-Python third-party package (mpmath). This leg is scoped to `stdlib`
   (`fractions.Fraction`, `decimal.Decimal`) precisely because `solver/spectral_certificate.py`'s
   own precedent is `fractions.Fraction` and the DM's brief says so explicitly. Any of the above
   would need `requirements.txt` changed, which is a proposal this leg can make in its journal
   (see integration note below) but never enact.
2. **The scope is two named numbers, not a library.** MPFI, Arb and kv all solve the *general*
   problem (arbitrary functions, arbitrary precision, verified transcendentals for their own
   sake). This leg's gate is "does arbitrary precision change leg 178's or leg 176's banked
   headline" — a much narrower question that does not need a general verified-eigenvalue solver
   or a general verified-elementary-function library. Building the general thing would itself be
   the named failure mode ("open-ended library port") the brief bans.

## 3. What is genuinely new here, stated precisely (so it can be checked against, not asserted)

- **Nothing about directed-rounding interval arithmetic itself is new** — outward rounding via a
  correctly-rounded arbitrary-precision base (here `decimal.Decimal`'s native context rounding
  modes `ROUND_FLOOR`/`ROUND_CEILING`, playing the role MPFR's rounding modes play for MPFI) is
  the textbook construction, unchanged from `solver/interval.py`'s own one-ulp float64 version
  scaled up.
- What is specific to this repository: **the interface is `solver/interval.py`'s own** (an
  `Interval`-shaped object with `+ - * /`, `isum`, `matvec`/`dot`), so the two re-measurements
  below can be written as close relatives of the leg-178/176 runners rather than a new API a
  reader must learn, and the precision needed is bounded by the two SPECIFIC condition numbers
  measured in §5/§6 below (not "however much a user asks for").
- **Leg 176's problem is not solved by interval arithmetic at all in its literal form** (see §6):
  its defect is loss of relative accuracy in an ill-conditioned *dense generalized eigenvalue
  problem*, not a place where an interval enclosure of a scalar formula is the natural tool.
  Rigorous verified-eigenvalue enclosure (Rohn/Kashiwagi-style) is exactly what kv and INTLAB
  exist for and is explicitly **out of scope here** — building that machinery from scratch would
  itself be the open-ended-library-port failure mode. What this leg builds instead for leg 176 is
  a **high-precision (Decimal, not interval-enclosed) recomputation** of the specific
  ill-conditioned step, explicitly flagged as non-rigorous, honest about the gap between "high
  working precision" and "verified enclosure" (lesson 86's discipline applied to this leg's own
  output, not just its targets).
