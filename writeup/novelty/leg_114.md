## 0. Novelty pass — is this question already answered anywhere in the repository?

Run **before** any construction, per the leg contract.  Five channels:

1. **Existing adversarial batteries.**  The repository carries eleven at this pass date
   (`test_bordered_hl_adversarial.py`, `test_boussinesq_adversarial.py`,
   `test_boussinesq_velocity_adversarial.py`, `test_fractional_gclm_adversarial.py`,
   `test_gclm_adversarial.py`, `test_gclm_family_adversarial.py`,
   `test_gclm_rescaled_adversarial.py`, `test_hilbert_pointwise_adversarial.py`,
   `test_interval_certificate_adversarial.py`, `test_line_hilbert_adversarial.py`,
   `test_marginal_flow_adversarial.py`, `test_target_norm_adversarial.py`,
   `test_weight_search_adversarial.py`).  **None names `collocation_newton`.**
   `grep -rln collocation_newton test_*adversarial*.py experiments/*adversarial*.py` returns
   nothing.

2. **The module's own gate.**  `test_collocation_newton.py` has exactly 6 tests
   (`test_1_velocity_integrals`, `test_2_a0_reduction_and_offnode`, `test_3_jacobian`,
   `test_4_certificate_system`, `test_5_two_builds_agree`, `test_6_defect_survives_the_solve`).
   Every one is a **correctness** assertion on a well-posed problem: exact anchor, exact
   Jacobian, finite-difference agreement, cross-build agreement with `solver/profile_newton`.
   Not one constructs a degenerate grid, a NaN-poisoned profile, or an unsolvable system; not
   one asserts that a degenerate input is *rejected*.  A correctness check on well-behaved
   input is not a robustness check (the leg 73 -> leg 99 relation, restated).

3. **In-module guards.**  `grep -n "raise\|assert\|isfinite\|isnan\|warn\|ValueError"
   solver/collocation_newton.py` returns **exactly one line in 405**: `if not
   np.isfinite(Xc)` at line 364, inside `zero_order`.  There is no validation of `J`, of
   `a`, of `c`, of `drop`, of the shape or finiteness of `om0`, of `max_iter`, or of the
   `theta_eval` passed to the off-node evaluator.  Every `converged` flag in the file is a
   bare float comparison with no finiteness precondition.

4. **The shared ledgers.**  `experiments/JOURNAL.md` mentions the module once (line 722),
   recording Route-D v12's development and its 6/6 pass, explicitly *"NOT a logged gate run
   — solver development."*  `LITERATURE_CHECK.md` does not mention it.  `ARCHIVE.md` names
   only the test file, in a suite inventory.  `writeup/novelty/leg_71.md` lists the module as
   row 21 of a capability table — an inventory entry, not a question.

5. **Leg 110's audit.**  Leg 110 audits the collocation realization's death at the **data**
   level (L1 measured dead in the collocation realization per leg 56).  It does not read this
   module's failure modes.  This leg is the **code**-level companion: zero file overlap,
   complementary question, exactly the relation `DIRECTION.md` §114 pre-commits.

**Novelty: confirmed.**  Nothing in the repository asks whether this module's convergence
report can be wrong.

**Live-risk precedent.**  This exact pattern has found real defects in eleven of ~15 tries
this session (`solver/gclm.py`, `solver/boussinesq.py`, `solver/boussinesq_velocity.py`,
`solver/interval_certificate.py`, `solver/holder_norms.py`, `solver/op_lower.py`,
`solver/marginal_flow.py`, ...).  The prior expectation is therefore *not* "robust."

**Why this module is worth the pass.**  `ACollocation.newton_gauged` is the solve whose
matrix **is** the certificate's approximate inverse `A` — the docstring says so — and whose
returned step size **is** `Y_0`.  A convergence flag that can be true on a wrong answer here
is a convergence flag on a number the Route-D bound layer consumes directly.
