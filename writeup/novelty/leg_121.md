# Leg 121 — Route-CDA novelty pass (run BEFORE construction)

**Date:** 2026-08-06. **Agent:** LEG-Q. **Branch:** `leg/cda-v1`.

**Verdict: `PROCEED_AS_AUDIT`.** This leg builds no new mathematics and claims no novel
mechanism. It is an adversarial robustness audit of `solver/critical_dissipation.py` — the
module `capabilities.py` records as holding "the marginal case and the invariant `alpha_1`"
(validated: `alpha_1 = 0` at `a=0` == ALS eq (61); `alpha_1 = +0.133683` at `a=1/2` is
**measured, not independently validated**). Everything this pass or the battery can find is
either (a) a defect in *our* code, or (b) a confirmation that the module refuses what it
should refuse. Neither is a discovery, and nothing below is claimed as one.

**It does not reopen, contest, or re-measure `alpha_1 = 0` at `a=0`, `sigma=3` at `a=1/2`, or
`alpha_1 = +0.133683`.** Those are settled per `capabilities.py` and are treated as fixed
background throughout. The distinction this leg holds to, stated once and obeyed throughout:
*the physics this module computes at admissible inputs is settled; what has never been
checked is whether the code that computes it refuses, or silently miscomputes, malformed or
degenerate input.* Every number this leg reports is a statement about **code behaviour**,
never a restatement or contestation of a banked exponent.

Per `writeup/novelty/README.md`: **links, not counts.** Query strings verbatim; every
on-topic link listed.

## What is being checked for prior art

* **(N1)** Is silent truncation of a float to an integer via a bare `int(x)` cast — with no
  check that the value was already integral — a documented, named software-defect class?
  This module's own docstring states a hard precondition, `p a positive integer (2s = p)`,
  enforced (where it is enforced at all) only by `int(p)` in two places
  (`lambda_power`, `CriticalDissipativeFlow.__init__`).
* **(N2)** Does the published fractional-Laplacian / spectral literature treat the operator
  order as continuous (any real exponent admissible), or does it, like this module, require
  an integer order? If the literature's admissible range is continuous, then a caller who
  knows the *physics* has every reason to expect a non-integer `p`/`s` to be legitimate input
  — the integer restriction is purely an artifact of *this* module's exact-representation
  trick, not a physical boundary, which sharpens why silent truncation is dangerous rather
  than a reasonable refusal of out-of-domain input.
* **(N3)** Is "adversarial battery against a numerical module, checking that invalid input is
  propagated or flagged rather than silently absorbed" an established method, and is silent
  absorption of an invalid parameter a documented failure mode? (Answered by leg 91's pass;
  re-checked as still on point for this module, not re-derived.)
* **(N4)** Does the dissipative-gCLM literature (the same corpus leg 91's pass already read)
  say anything about the *sign* of the dissipation strength — is a negative coefficient
  (anti-dissipation, an energy source) ever treated as admissible?

## Queries, verbatim, with the links returned

### Q1
`CWE-197 numeric truncation error silent floating point to integer conversion software defect`

- https://cwe.mitre.org/data/definitions/197.html — **MITRE, CWE-197: Numeric Truncation
  Error.** ← the settling reference for (N1).
- https://best.openssf.org/Secure-Coding-Guide-for-Python/CWE-664/CWE-197/ — OpenSSF Secure
  Coding Guide for Python, CWE-197 page.
- https://www.mathworks.com/help/bugfinder/ref/cwe197.html — MATLAB Bug Finder, CWE Rule 197.
- https://www.cvedetails.com/cwe-details/197/Numeric-Truncation-Error.html
- https://turbopentest.com/cwe/cwe-197-numeric-truncation-error
- https://appsec.backslash.security/cwe/197
- https://arxiv.org/pdf/1710.03720 — *Practical Integer Overflow Prevention* (adjacent —
  overflow, not truncation, but the same "cast to a smaller/different primitive loses
  information silently" family).

**On-topic finding for (N1), and it names the defect class exactly.** CWE-197: *"Truncation
errors occur when a primitive is cast to a primitive of a smaller size and data is lost in
the conversion ... the value cannot be trusted and the system will be in an undefined
state."* `int(p)` on a non-integral float is exactly this: the fractional part — the part
that distinguishes the requested dissipation order from the one the module actually builds —
is the "high-order information" silently discarded. This gives the battery a named class to
test against rather than an invented one.

### Q2
`Python int() truncation silent bug numerical software float to integer cast validation`

- https://github.com/numpy/numpy/issues/7730 — **NumPy, *Deprecate/remove silent truncation
  on assignment of floats into an integer array*.** ← the sharpest analogue: a researcher
  reports "wasted a month of research effort" tracking a bug from `a[0] = 1.1` silently
  becoming `1` in an integer array — the exact shape of this leg's finding (a fractional
  request silently rounded away with no error, no warning), in the same numerical-Python
  ecosystem this repository is built on.
- https://github.com/pola-rs/polars/issues/21326 — Polars, *type-casting float to int
  silently truncates values instead of throwing errors* (`5.8` → `5`, no exception).
- https://www.pythontutorials.net/blog/counterintuitive-behaviour-of-int-in-python/ —
  **settles (N1)'s companion question: why does `int(3.5)` truncate silently while
  `int("3.5")` raises `ValueError`?** Quoted: *"Numeric types like float already represent
  numbers, so `int()` assumes you want the integer 'core' of the value, and truncation is a
  safe, unambiguous way to extract this core"* — string input gets no such benefit of the
  doubt. This is precisely the asymmetry battery C4 measures in
  `CriticalDissipativeFlow(..., p=...)`: a string that already reads as non-integral
  (`'3.5'`) is refused, while a float that is *numerically* non-integral (`3.5`, or `2.9`) is
  silently accepted and rounded down. The asymmetry is a property of Python's own `int()`,
  inherited by the module without comment.
- https://www.weblineglobal.com/blog/python-float-vs-decimal-fintech-data-integrity/ — a
  FinTech case study, same family (silent float truncation of an ID past `2^53`), cited only
  for the pattern, not the domain.
- https://www.scribd.com/document/638504842/Python-cast-data-types,
  https://www.postgresql.org/message-id/15332.1543017494%40sss.pgh.pa.us (Postgres casting
  a float4 into int4 "gets the wrong sign instead of an out-of-range error") — adjacent,
  same defect family in other systems.

**On-topic finding for (N1), and it is the sharpest result of this pass.** The NumPy issue
is not a hypothetical: it is a maintainer-acknowledged, still-open report of exactly this
failure mode costing real research time in the same ecosystem. The pythontutorials.net
explanation supplies the *mechanism* behind the string/float asymmetry this leg's battery
measures directly in the module under audit.

### Q3
`fractional Laplacian spectral method exact matrix only integer order non-integer order silently rounds truncates`

- https://arxiv.org/html/2311.07814 and https://www.sciencedirect.com/science/article/abs/pii/S0898122124002621
  — *A novel and simple spectral method for nonlocal PDEs with the fractional Laplacian*:
  builds a discrete operator with symbol `|xi|^alpha` for continuous `alpha`, no integer
  restriction.
- https://www.sciencedirect.com/science/article/abs/pii/S0010465520303416 — open-source
  parallel spectral fractional-Laplacian code, 3D complex geometry, continuous order.
- https://www.researchgate.net/publication/314101220_The_spectral_collocation_method_for_efficiently_solving_PDEs_with_fractional_Laplacian
  — spectral collocation for `(-Delta)^{alpha/2}`, continuous `alpha in (0,2)`.
- https://arxiv.org/pdf/2605.23252 (and its ResearchGate mirror) — matrix-based spectral
  method for the fractional Laplacian and fractional `p`-Laplacian, order continuous.
- https://arxiv.org/html/2406.10524v1 — finite-difference method for the *variable-order*
  fractional Laplacian — the order is explicitly allowed to be a function, the opposite
  extreme from "must be a positive integer."

**On-topic finding for (N2).** Every method in the corpus treats the fractional order as a
**continuous** parameter over `(0,2)` or wider; none imposes an integer restriction, and one
explicitly generalizes to *variable*, space-dependent order. **This module's `p` must be a
positive integer for a reason specific to its own construction** (Route-E's compactified
sine basis makes `Lambda` exact only when `Lambda^p` widens the coefficient range by an
integer number of modes — see the module's own docstring, "THE KNOWN ANSWER" section) — it
is not a restriction the physics or the wider numerical literature would lead a caller to
expect. That sharpens, rather than closes, this leg's target: a caller arriving from the
published literature has every reason to believe a non-integer `s` (equivalently `p = 2s`)
is legitimate input, and nothing in the module's public interface (no exception, no
docstring warning at the call site, no type hint) corrects that expectation before the
silent truncation happens.

### Q4
`dissipative Constantin-Lax-Majda anti-dissipation negative viscosity coefficient energy source admissible`

- https://arxiv.org/pdf/1908.09385 — Lushnikov–Silantyev–Siegel, *Singularity Formation and
  Global Well-Posedness for the Generalized Constantin–Lax–Majda Equation with Dissipation*
  (same paper leg 91's Q1 already read).
- https://arxiv.org/pdf/2207.07548 — *Global existence and singularity formation for the
  gCLM equation with dissipation: the real line vs. periodic domains* (same paper).
- https://arxiv.org/html/2607.19762v1 — Xu, the same paper this module's own docstring cites
  for `sigma = 3` at `a = 1/2`.
- https://arxiv.org/pdf/2506.02800 — *Stability and Instability on the De Gregorio
  Modification*.

**On-topic finding for (N4), and it is the same finding leg 91 already banked, re-checked
for this module rather than re-derived.** The corpus works at `sigma = 2s >= 0` throughout;
nowhere is a negative dissipation coefficient (an energy source) treated as admissible. This
module's `mu = nu / (A L^{2s})` is the same physical quantity leg 91 audited as `nu` in
`fractional_gclm.py`, now carried into Route-E's rescaled flow — **the corpus's floor
applies unchanged, and this leg does not need a fresh literature boundary for it.** What is
new here is only whether *this* module, a different piece of code built around the same
physical quantity, repeats leg 91's finding (accepts `mu < 0` silently) or was built with
the guard leg 91's escalation recommended. It was not: `CriticalDissipativeFlow.__init__`
does `self.mu = float(mu)` with no sign check, in either module.

## What this pass changed about the leg, before construction

1. **It named the defect class instead of inventing one** (N1/Q1/Q2): CWE-197 numeric
   truncation, with a maintainer-acknowledged NumPy incident of the identical shape ("wasted
   a month" on a silently-truncated float-to-int assignment) in the same ecosystem this
   repository runs on. The battery's headline target is therefore a named, documented
   failure mode, not a taste judgement about what `int(p)` "should" do.
2. **It explained the string/float asymmetry the battery measures** (Q2): Python's `int()`
   gives a float "the benefit of the doubt" (truncate its integer core) but gives a numeric
   string none (raise on any non-integral literal). The module inherits this asymmetry
   without comment, so `p='3.5'` refuses while `p=2.9` (or any float in `[2,3)`) is silently
   accepted as `p=2` — the type that *looks* more like a validated input is the one that is
   actually more dangerous.
3. **It ruled out the most likely false-positive reading of the finding** (N2/Q3): the
   integer-`p` restriction is **not** a physical admissibility boundary anyone publishing on
   the fractional Laplacian imposes — it is local to this module's exact-representation
   trick. That means a defect here is a defect in *our* code's failure to communicate *its
   own* local restriction, not a rediscovery of a published boundary (contrast leg 91, where
   `s < 0` **was** outside a published range). This is the correct framing and is why no
   novelty is claimed.
4. **It set the sign boundary for `mu` from the same corpus leg 91 already used**, without
   re-deriving it: `sigma = 2s >= 0` throughout the dissipative-gCLM literature, so `mu < 0`
   is the literature-backed invalid case, exactly as `nu < 0` was for `fractional_gclm.py`.
5. **It pre-empts every novelty claim.** Nothing this leg can find is new mathematics. A
   defect is a defect in our code against either a named software-defect class (CWE-197) or
   a physical boundary already established by leg 91's own pass; a clean result is a
   confirmation of robustness. The leg claims **no** novelty, and makes **no** statement
   about `alpha_1` at any admissible `(a, mu, p)` — those remain exactly as banked in
   `capabilities.py`.
