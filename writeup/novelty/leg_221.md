### R2. Is leg 205's own prescribed repair sufficient? **Defect A yes; defect B under-specified, and the residual it names cannot carry the fix alone.**

Legs 150, 151 and 152 each found the escalating leg's prescribed predicate incomplete on its
own pins, so this is a standing check, not a courtesy.

* **Defect A.** Leg 205 prescribes "the same two lines leg 99 prescribed (count the mask,
  check `lstsq`'s returned rank), applied to `odd_field_x_slope` with **3** as the parameter
  count rather than 2." **Sufficient as written**, and it has a same-repo reference
  implementation to copy verbatim: `u_x_at_origin`'s `n_in_window < min_points` +
  `rank < A.shape[1]` pair at `solver/boussinesq_velocity.py:214-231`.
* **Defect B.** Leg 205 deliberately does *not* prescribe a repair — it lists three candidate
  responses ("gate on it, size the window from the field, or document the precondition") and
  calls the choice a module-owner decision. So there is no prescription to check for
  sufficiency; there is a design decision to make and to justify. **The measured constraint
  that decides it is leg 205's own recovery control**: same field, same grid, same code, only
  `r_win` varying, `0.4 → 0.269302` (86.5% wrong) through `0.02 → 2.000941` (inside tolerance).
  That control says the function is *capable* of the right answer at a window matched to the
  field's scale, which rules out "document the precondition" as adequate and makes
  **sizing the window from the field** the primary fix, with the residual as a backstop.
* **The residual cannot be the primary guard, for a documented numpy reason.** `lstsq`'s
  `residuals` array is **empty whenever `rank < N` or `M <= N`**
  ([numpy.linalg.lstsq docs](https://numpy.org/doc/stable/reference/generated/numpy.linalg.lstsq.html))
  — i.e. it is empty in exactly the under-determined configurations defect A produces. A
  residual-only repair would therefore close neither A (no residual exists there) nor,
  reliably, the boundary of B. The occupancy/rank guard must come **first**, and the residual
  is a fit-quality check applied after it. This is a correction to the shape of leg 205's
  escalation note 2, not to its finding.

### R4. The constraint that shapes the whole design: zero clean movement.

The gate demands the banked record be **bit-identical** pre/post. That forbids any repair
that changes the effective window on in-contract input. The adopted form — `r_win_eff =
min(r_win, ½ · r_scale)` where `r_scale` is read off the field's own projected radial
coefficient — is **non-binding by construction** whenever the field's scale is at or above
the module's validated regime, so `min` returns the caller's `r_win` *as the identical float*,
the mask is the identical boolean array, and the `lstsq` call is bit-identical. Movement is
possible only on fields concentrated *below* the hard-coded 0.4, which is precisely defect B's
regime. Leg 205 asserted the banked profiles were `exp(-r²)`-class; they are not — Step-C's
`profile_ansatz` uses the rational envelope `r/(1+r^{1-α})` — so that assertion is replaced
here by measurement, not inherited.

## Addendum, 2026-08-07 (resumed session): R5 — what the landed repair does NOT close

Added after the repair was verified rather than inherited. R4 above argues the window cap is
non-binding on in-contract input; that is confirmed. But the cap reads the field's radial scale
off the radius at which the projected `d1` **peaks**, and that heuristic is exact only for the
**single-scale** `a r exp(-lam r^2)` class the module is validated on and that leg 205's battery
is built from.

**Measured counterexample, outside leg 205's battery.** The two-scale field
`r cos(b) [exp(-r^2) + exp(-400 r^2)]` — smooth, odd-in-x, fully in contract — is returned as
**1.135121 against a truth of 2.0: rel. err 4.324e-1, 86x the module's own 5e-4 acceptance
tolerance, silently.** The peak resolves to the **outer** scale (deliberately: resolving inward
would shrink the window on fields with no small scale, a fabrication of the opposite sign), the
cap goes non-binding, and the inner scale is never resolved. A wider separation,
`exp(-r^2) + exp(-1e4 r^2)`, gives **1.006197** against 2.0 (**4.969e-1**).

**The residual backstop does not catch it, and the margin is thin.** Measured through the
public API by bisecting `max_rel_residual` (no re-implementation of the fit): worst legitimate
in-repository fit **4.301e-3** (Step-C `profile_ansatz` omega), tightest uncaught bad case
**1.910e-2** — a separation of only **4.44x**, against a landed threshold of **0.50**, roughly
26x above the tightest bad case. Any threshold in `(4.3e-3, 1.9e-2)` would catch both
counterexamples; none is adopted here.

**Why it is flagged and not fixed under this leg's authority.** This leg's territory is "the two
named mechanisms only", and its gate is scoped to leg 205's own battery, which contains no
two-scale case. Retuning the threshold is a behaviour change the gate did not scope: clause
(b)'s bit-identical sweep was run at 0.5, a new threshold would invalidate that evidence, and it
risks raising on legitimate banked calls — a regression against the gate's own zero-clean-
movement design driver. **So this is banked as residue with its magnitude and handed to the
postrepair-verification leg**, which the gate's yes-branch already calls for. The one change
made was to prose: the inherited docstring's claim that the residual is "a fit-quality backstop
for shapes the peak heuristic does not describe" is an **overclaim, measured false above**, and
now reads as a partial backstop with the counterexample named.
