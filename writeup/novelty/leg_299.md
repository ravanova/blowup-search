# Leg 299 — ROUTE-TESTA — test-suite freshness audit

**Role: read-and-report verification leg.** No solver module touched, no test assertion edited, no
repair. Every `test_*.py` file in the repo actually run (not just read) and its output audited
against the current behavior of four named repaired modules. Date 2026-08-12.

## 0. What is already known (prior art inside this repo)

The campaign carries a documented repair wave across four solver modules referenced by this
leg's Context: `solver/profile_newton.py` (leg 226's repair, re-derived independently by leg
229's `test_profile_newton_postrepair.py`), `solver/collocation_newton.py` (leg 150's repair of
8 named SILENT_WRONG corruption cases, re-derived by leg 166's
`test_collocation_newton_postrepair.py`), `solver/boussinesq_rescaled.py` (leg 221's repair of
`odd_field_x_slope`, commit `6a0abb8`), and `solver/dssp_screen.py` (leg 364's citation-only
re-attribution, commit `3bfe677`, no behavior change).

The repo's own convention (documented in `scripts/merge_gate.sh` and in several test docstrings,
e.g. `test_profile_newton.py`'s BLAS-backend discussion citing "leg 71's audit") is that `test_*.py`
files are self-running scripts, not pytest suites, and that some tests deliberately pin an OPEN
defect (`_adversarial.py`, KNOWN_GAP checks) so that a later repair must INVERT the assertion, not
silently weaken it. No prior leg has run the full `test_*.py` corpus end-to-end in one pass and
audited every skip/pass/fail against this convention; that is this leg's contribution.

## 1. Method

1. Enumerated every `test_*.py` file at repo root inside the isolated worktree
   (`/home/andy/projects/Unsolved/.leg299-work`): 126 files.
2. Ran each one as `python3 test_x.py` (the repo's own convention — no pytest, no scipy) using
   the absolute venv interpreter `/home/andy/projects/Unsolved/.venv/bin/python3`, capturing
   stdout/stderr and exit code for every file. First pass used a 180s per-file cap; the one file
   that hit the cap (`test_advection_scope.py`, whose own docstring states "no scipy; ~4 min") was
   re-run uncapped to get a real verdict rather than being reported as a failure.
3. Grepped the full transcript for `SKIP`/`skip` to confirm every skip carries a documented
   reason (repo standing practice), and for non-zero exits to isolate genuine failures.
4. For the four named repaired modules, cross-checked not just "did the test pass" but whether
   the test's assertions still match the module's current, post-repair behavior: read
   `test_profile_newton_postrepair.py`, `test_collocation_newton_postrepair.py`,
   `test_boussinesq_postrepair.py`, `test_gclm_postrepair.py` (gCLM's `stage1_5` bit-identity
   suite, adjacent to the profile-newton family), and `test_dssp_screen.py` in full or in the
   relevant part, and compared their pinned expectations against `git show` of the actual repair
   commits (`6a0abb8`, `3bfe677`, plus leg 226's and leg 150's repair branches).

## 2. What was found

**124/126 test files pass cleanly with no adjustment.** `test_advection_scope.py`'s only failure
was a harness artifact (my own 180s timeout under heavy concurrent-leg CPU contention on this
host); rerun uncapped, it passes all 6 checks (`ALL ADVECTION-SCOPE TESTS PASSED`).

**Exactly one documented skip exists in the whole corpus**:
`test_weight_search_adversarial.py`'s `test_8_figure_calibration_checks_itself` prints
`SKIPPED: Papers/2410.05480.pdf not present (Papers/ is gitignored; bash Papers/fetch.sh
2410.05480)` — a recorded, actionable reason, consistent with standing practice. No other skip
appears anywhere in 126 files' output.

**Two genuine, reproducible failures were found**, both inside "postrepair" re-derivation suites,
both requiring judgment about which side (test vs. banked artifact / module) is correct — per this
leg's territory, named here as rework flags rather than silently patched:

- **Finding #1 — `test_boussinesq_postrepair.py::check_banked_record_carries_no_out_of_domain_coefficient`
  is stale relative to a later, legitimate, self-documented artifact.** This check (committed by
  leg 133, `21e2498`, 2026-08-06 12:57:19) asserts every recorded `nu`/`kappa`/`nu_crit` across
  `writeup/data/*.json` is in `[0, inf)`. Leg 185's diagnostic (`fcd864e`, 2026-08-06 16:56:53,
  4 hours later) legitimately banked 295 negative-`nu` values in
  `writeup/data/p2_route_m2sd_v1_diagnostic.json`'s `D5_is_a_genuine_profile_reachable` sweep,
  each explicitly self-flagged `"admissible_positive_nu": false` — this is documented, intentional
  diagnostic data, not corruption. The check's assertion was written before that data existed and
  never updated to exempt self-flagged-non-admissible entries. This is a stale-test defect
  concerning `solver/boussinesq_rescaled.py`'s test suite (not the module itself, which is
  unaffected). Rework candidate: the check needs a clause distinguishing self-flagged diagnostic
  non-admissibility from an actual out-of-domain production leak — a judgment call left un-made
  here per territory.

- **Finding #2 — `test_gclm_postrepair.py::check_banked_stage1_5_t_stars_are_unmoved` pins a
  bit-identical (`float.hex`) assertion that is fragile to FFT-backend ULP drift, not to a module
  regression.** The `bump(kappa=2)` case now returns `6.412705280348239` against a banked literal
  of `6.412705280348236` — a 3-ULP difference. Traced to `solver/gclm.py`'s
  `clm_analytic_blowup_time`, which locates zeros via `np.fft.rfft`-based spectral interpolation;
  the module's own docstring documents this class of drift, and the repo already documents an
  analogous BLAS-backend-dependent phenomenon elsewhere (`test_profile_newton.py`'s "leg 71's
  audit" discussion, ~2.3 decades of cross-host variability in an iteration-capped stall). Nothing
  about `solver/gclm.py`'s repaired behavior has regressed; the test's tolerance (bit-identity) is
  simply tighter than the numerical guarantee the FFT backend can provide across environments.
  Rework candidate: the check concerns `solver/gclm.py`'s postrepair suite and needs either a
  relative-tolerance relaxation (with a documented floor, as `test_profile_newton.py` already
  models) or a note that this is environment-dependent — again a judgment call named, not made,
  here.

Both findings were reproduced twice (once in the full sweep, once isolated) and traced to root
cause; neither the tests nor `solver/gclm.py` / `solver/boussinesq_rescaled.py` / any
`writeup/data/*.json` file were edited by this leg.

**Cross-check of the four named repaired modules' assertions against current behavior**: all four
postrepair/status suites (`test_profile_newton_postrepair.py`, 439 lines;
`test_collocation_newton_postrepair.py`, 757 lines; `test_boussinesq_postrepair.py`, 540 lines,
modulo Finding #1; `test_dssp_screen.py`, 335 lines, including leg 362's regression-compatibility
checks) still exercise and correctly assert their modules' current, post-repair behavior — no
other pre-repair value found silently baked in. `test_gclm_postrepair.py` (389 lines) is correct
in substance modulo Finding #2's tolerance-fragility.

## 3. Classification and consequence

**Gate answer: NO — two stale/fragile tests named as rework candidates, not silently updated.**
Per the Gate's own branching ("no -> Name stale test(s); flag rework candidate, do not silently
update assertion to match new behavior without checking correct"), this leg names Findings #1 and
#2 above rather than patching either the test or the underlying module/data. The remaining
124/126 files, including every check inside the four specifically-named repaired-module suites
other than the two flagged checks, are banked as current: they pass, and their assertions were
independently verified to match present module behavior, not a stale pre-repair value.

**Consequence.** Neither finding touches a scientific conclusion already banked in
`writeup/CORRECTIONS.md` or any journal entry — Finding #1 is a test-suite hygiene gap (a
too-broad domain check written before a legitimately out-of-domain diagnostic dataset existed);
Finding #2 is a test-tolerance hygiene gap (bit-identity where the repo's own established practice
elsewhere uses a documented relative-tolerance floor). Both are safe to leave unaddressed for now
because the underlying modules and data are correct; both should be picked up as small, scoped
rework legs.
