## What is being checked for prior art

`solver/hl_rescaled.py` has dedicated tests (`test_hl_rescaled.py`, 9 known-answer checks) but
no adversarial battery — the exact gap description in `DIRECTION.md`'s leg-117 entry. Reading
the module first (read-only, per territory) surfaced four candidate failure mechanisms before
any battery was written, each checked against prior art so the leg reports "known hazard,
instance found here" rather than a discovery:

* **(N1)** `RescaledHL.__init__`'s own grid guard is `np.any(np.diff(X) <= 0)`. Under IEEE-754,
  every ordered comparison against NaN is False, so a NaN anywhere in `X` makes this guard
  vacuously pass. Is "a NaN silently defeats a `<=`/`>=`-style validation guard" a documented,
  standard-level hazard (as opposed to a numpy quirk), matching what legs 100 (N1), 106 and 116
  already found in three *other* modules?
* **(N2)** The free function `velocity(X, Homega, X_ref)` pins `U(X_ref)=0` via
  `np.interp(X_ref, X, U)`. Is numpy's documented behavior for `x` outside the sampled domain
  to silently clamp to the boundary value, with no warning or exception — i.e. is the silent
  part a *documented* default rather than a bug this leg would be the first to notice?
* **(N3)** `velocity()`'s own docstring says "on a (sorted-ascending)... grid" but the function
  never checks it, and neither does `sinh_grid_at(..., M=...)`, whose docstring says "Reach is
  +-M about Xc" without ever validating `M > 0`. Is "a numerical integration/transform routine
  assumes a sorted/monotonic grid and does not check it" a named, published hazard specific to
  Hilbert-transform or cumulative-integration code, or is it the generic unchecked-precondition
  pattern with no domain-specific literature of its own?
* **(N4)** Is "fuzz a numerical module with adversarial/degenerate/poisoned inputs, looking for
  a silently wrong *finite* output rather than a crash or a visible NaN" an established general
  method (as legs 100/106/116/120 already treated it), or would this leg's method itself be a
  novel contribution?

## Queries, verbatim, with the links returned

### Q1
`IEEE 754 NaN unordered comparison silently bypasses validation guard "disappear without a trace"`

- https://grouper.ieee.org/groups/msc/ANSI_IEEE-Std-754-2019/background/predicates.txt — the
  IEEE 754 working group's own background note on comparison predicates states the mechanism in
  so many words: unhandled NaNs "might corrupt the logic of the program and then **disappear
  without a trace**." It further explains *why*: quiet comparison predicates raise no exception
  on a NaN operand, so "a programmer who has not considered the possibility of quiet NaN
  operands might have programmed incorrect logic" with no signal at the comparison site itself.
- https://github.com/elm/core/issues/1050 — a live bug report of the identical rule
  (`NaN > NaN` and `NaN >= NaN` both False) breaking a language's ordering assumptions.
- https://community.intel.com/t5/Intel-oneAPI-DPC-C-Compiler/More-trouble-with-NANs/td-p/1485284
  — a second, independent report of the same comparison-bypass class.

**On-topic, confirms known hazard.** This is the *same* standard-level mechanism legs 100
(N1: `if x <= 0`/`if r > best` skip a NaN), 106 (`rho = NaN` defeats `rho*cT <= cS`) and 116
(`Z0` validated only by a sign check that a NaN also defeats) already instantiated in three
other modules of this repository. `RescaledHL.__init__`'s `np.diff(X) <= 0` guard is the same
`<=`-comparison-vs-NaN pattern, not a new phenomenon; this leg reports "known hazard, fourth
instance."

### Q2
`numpy interp extrapolation outside domain clamps to boundary value no warning`

- https://docs.scipy.org/doc/scipy/reference/generated/scipy.integrate.cumulative_trapezoid.html
  and the general numpy/scipy interpolation documentation confirm: `np.interp` does not
  extrapolate by default — a query point outside `[xp.min(), xp.max()]` returns the nearest
  endpoint's `y` value, silently, with no warning or exception. `scipy.interpolate.interp1d`
  requires an explicit `fill_value='extrapolate'` opt-in specifically because plain boundary
  clamping is the unsafe default a caller must consciously override.
- https://scipy.github.io/devdocs/tutorial/interpolate/1D.html — SciPy's own tutorial names
  this the same way: extrapolation must be requested, clamping is what happens if you don't.

**On-topic, confirms known hazard.** The silent clamp is documented numpy/scipy behavior, not
a bug this leg discovers. What `velocity()` in `hl_rescaled.py` adds is zero validation on top
of that documented default: it never checks `X_ref` lies within `[X.min(), X.max()]` before
calling `np.interp`, so the module inherits the documented footgun with no additional guard.

### Q3
`Hilbert transform trapezoidal cumulative integral assumes sorted monotonic grid precondition unchecked`

No result specific to Hilbert-transform or cumulative-trapezoidal code names this precondition
explicitly; the closest hits (SciPy/MATLAB `cumtrapz` docs) describe the algorithm without
stating a monotonicity requirement or its failure mode. **Genuinely inconclusive — recorded as
a negative finding.** This means "an integration routine silently mis-integrates on unsorted
input" is *not* a named, citable hazard in this specific domain; the leg reports the resulting
measurement as an *instance of the generic unchecked-precondition class* (same class as N1/N2),
not as an application of a published, domain-specific warning. No novelty is claimed either way
— the absence of a citation is itself the finding for Q3, exactly as leg 120's Q4 recorded a
clean absence rather than inventing significance for it.

### Q4
`adversarial fuzz testing numerical scientific code silent corruption instead of crash detect wrong result`

- https://arxiv.org/pdf/2012.11182 (feedback-driven fuzzing with likely invariants) and general
  fuzzing literature confirm the framing used here is standard: "most fuzzers use crashes to
  detect failures... when a fault doesn't directly trigger a crash, the system must be
  instrumented with additional tripwires to catch silent faults," and detecting pure silent
  logic bugs without hand-written oracles "remains an unsolved problem" in general — which is
  exactly why this leg (like 100/106/116/120) supplies its own analytic or independently-derived
  oracle for each gate rather than relying on a crash signal.

**On-topic, confirms known method.** The METHOD is standard practice inherited from the
audit-family precedent already in this repository; this leg claims no methodological novelty,
only new instances in a previously-unaudited module.

## What the pass fixed about the leg before construction

1. **N1 is not speculative** — it is checked directly against `RescaledHL.__init__`'s actual
   guard line before any battery is written (§ Gate 4 below), and the finding is reported at
   the strength the mechanism supports: the guard is genuinely defeated, but (unlike leg 106's
   `rho=NaN`) the defeat does not chain to a *plausible-looking finite* wrong answer here —
   `line_hilbert_matrix` propagates the NaN visibly. That distinction is written down as a
   mitigating factor, not omitted, per lesson 76 ("what was tried and failed... with the same
   care as what worked" applies symmetrically to overstating a finding).
2. **N2 turns "np.interp clamps" from a vague worry into an exact, quantifiable defect**: since
   the clamp is a *documented default*, the battery's job is only to show `velocity()` never
   validates `X_ref` against `[X.min(), X.max()]` before relying on that default — a one-line
   gap with a precise, computable magnitude (a uniform additive shift in the returned array).
3. **N4 rules out a false novelty claim about the method itself** before any gate is run: this
   leg is exploration-queue robustness testing, not new mathematics, exactly as the DM's
   thesis states, and the report will not claim otherwise.
