## What is being checked for prior art

* **(N1)** Are `Y_0, Z_0, Z_1, Z_2` **hypothesised positive/nonnegative and finite** in the
  published radii-polynomial theorem? If yes, a negative constant is *outside the theorem*, and
  a discriminant test that accepts it evaluates something the theorem does not cover — so
  measuring it here is bookkeeping against a published hypothesis, not a discovery.
* **(N2)** Is **silent truncation of a Galerkin/Fourier mode set** (a quadratic nonlinearity
  generating modes up to `2K` in a space that retains `K`) a standard, named phenomenon?
* **(N3)** Is **silently accepting NaN/±inf/negative inputs in a numerical library, with no
  input validation, producing a confidently-wrong output** a recognised, named hazard?
* **(N4)** Is **dividing by a user-supplied weight with no positivity check**, and letting NumPy
  return `inf`/`nan` quietly, a known failure mode?

## Queries, verbatim, with the links returned

### Q1 (2026-08-06)
`radii polynomial theorem hypotheses Y0 Z0 Z1 Z2 nonnegative bounds computer-assisted proof validated numerics`

* https://arxiv.org/pdf/1704.03128 — Polynomial interpolation and a priori bootstrap for
  computer-assisted proofs in nonlinear ODEs
* https://arxiv.org/pdf/1704.03827 — Existence and instability of steady states for a
  triangular cross-diffusion system: a computer-assisted proof
* https://arxiv.org/pdf/2101.00684 — Validated forward integration scheme for parabolic PDEs
  via Chebyshev series
* https://arxiv.org/pdf/2404.08529 — The 2D Gray-Scott system: constructive proofs of existence
  of localized stationary patterns
* https://arxiv.org/pdf/2405.07727 — Validated error bounds for pseudospectral approximation of
  delay differential equations

**Finding (N1): PRIOR ART, unambiguous.** The theorem is stated with **positive** constants
`Y₀, Z₀, Z₁` and `Z₂: (0,∞) → (0,∞)`, each *bounding* a specific norm (`‖AF(x̂)‖`,
`‖I_X − AA†‖`, `‖A(DF(x̂) − A†)‖`, `‖A(DF(x) − DF(x̂))‖`) — quantities that are norms and
therefore nonnegative by construction. The coefficients of the radii polynomial "are all
positive". Consequently a negative or non-finite `Y₀`/`Z₀`/`Z₁`/`Z₂` is **not a conservative
input**: it is outside the theorem's hypotheses entirely. **Anything this leg finds on that axis
is a documented hypothesis our code does not check — identical in kind to legs 79/98/116, and
it must be reported that way.** This is also exactly leg 116's N1 finding, re-derived here
independently so this leg does not inherit its conclusion.

### Q2 (2026-08-06)
`Galerkin projection silently truncating Fourier modes convolution aliasing validated numerics finite section error`

* https://link.springer.com/article/10.1007/s10915-013-9749-1 — Efficient and Generic Algorithm
  for Rigorous Integration Forward in Time of dPDEs, Part I (Cyranka; the rigorous-dPDE
  treatment of the discarded tail)
* https://math.jhu.edu/~feilu/notes/DealiasingFFT.pdf — De-aliasing in the FFT (Lu)
* https://people.esam.northwestern.edu/~chopp/course_notes/446-2.pdf — ES APPM 446-2, spectral
  methods notes
* https://www.mech.kth.se/~ardeshir/courses/literature/Notes_Spectral_Methods.pdf — Schlatter,
  spectral methods notes
* https://www.emergentmind.com/topics/fourier-spectral-galerkin-method

**Finding (N2): PRIOR ART, and the distinction that matters is named.** Galerkin methods
**project high-frequency modes to zero**; pseudo-spectral methods **alias** them. A quadratic
nonlinearity generates wavenumbers "up to twice as high as representable", and the standard
remedies (2/3 rule, padding) are textbook. So *truncation itself* is not a finding and must not
be reported as one. The audit question is narrower and is **not** answered by this literature:
does this module's own truncation happen **where its own docstring says it must not**, and does
any quantity that is documented as exact or as an upper bound get computed on a truncated mode
set? Truncation is legitimate; truncation *inside a routine that advertises exactness* is a
code defect. I will report only the latter, with the magnitude of the discarded mass.

### Q3 (2026-08-06)
`defensive programming numerical library silently accepting negative or NaN inputs returning wrong certified radius adversarial regression test`

* https://arxiv.org/pdf/2602.17454 — *Privacy in Theory, Bugs in Practice: Grey-Box Auditing of
  Differential Privacy Libraries* — audits DP libraries by injecting `±inf` and `NaN`; finds
  several implementations mishandle them, and states explicitly that although such values were
  "likely out of scope" for the original framework, they "showcase the widespread implication
  of not performing tight input validation on mechanisms."

**Finding (N3): PRIOR ART for both the hazard and the METHOD.** The grey-box audit paper is the
closest published analogue of what this leg does: take a library whose correctness rests on a
theorem, feed it inputs the theorem excludes, and report where it answers confidently instead of
refusing. Both the hazard (missing input validation on theorem-hypothesised quantities) and the
methodology (an adversarial poisoned-input battery, banked) are established practice. **This leg
therefore claims no methodological novelty whatsoever** — its only possible contribution is the
*specific measured magnitudes* on this specific module.

### Q4 (2026-08-06)
`weighted ell1 operator norm zero weight division by zero inf nan propagation numpy silent`

* https://github.com/numpy/numpy/issues/25362 — numpy BUG: `average()` returns `nan` when an
  `inf` value is given a 0 weight
* https://stable-baselines3.readthedocs.io/en/master/guide/checking_nan.html — Dealing with
  NaNs and infs (the canonical statement: only division by zero signals; the rest propagate
  invalid values **quietly**)
* https://tutorialreference.com/python/examples/faq/python-numpy-warning-runtimewarning-invalid-value-encountered-in-divide
* https://arxiv.org/pdf/2103.14478 — The Operator Norm on Weighted Discrete Semigroup Algebras
  ℓ¹(S, ω) (for the weighted-ℓ¹ norm's own hypotheses: the weight is **positive** by definition
  of the algebra)

**Finding (N4): PRIOR ART.** NumPy's documented behaviour is `x/0 → ±inf`, `0/0 → nan`, with a
`RuntimeWarning` that does not halt; invalid values propagate quietly. And the weighted-ℓ¹
setting itself *requires* a positive weight — an ℓ¹(S, ω) algebra is not defined for ω ≤ 0. So
a non-positive domain weight reaching `weighted_ell1_op_norm` is, again, an input outside the
definition of the object being computed. Bookkeeping, not discovery.
