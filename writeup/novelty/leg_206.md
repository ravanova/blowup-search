## What is being checked for prior art

* **(N1)** Is "`-inf` is a legitimate value of a *minimised* objective, and must not be
  conflated with an invalid individual" an established convention? If so, a minimiser that
  keys validity off `isfinite` is violating a known standard, and reporting it is **bookkeeping,
  not a discovery**.
* **(N2)** Is `np.clip(x, lo, hi)` with `lo > hi` returning `hi` *documented* behaviour? If so,
  the inverted-bounds collapse is our code relying on a documented sharp edge without checking
  its precondition — again bookkeeping, not a numpy bug we found.
* **(N3)** Do established optimisers *validate the box* (equal-length, finite, correctly
  oriented bounds) at entry? If so, "the box is unvalidated" is a gap against standard
  practice rather than a matter of taste.
* **(N4)** Is an adversarial poisoned-input battery, banked as a permanent regression test, a
  standard method? (Already resolved for this repo at leg 98 — re-stated, not re-litigated.)

### Q3 (2026-08-06)
`numpy clip a_min greater than a_max returns a_max unexpected behavior bounds inverted`

- https://numpy.org/doc/stable/reference/generated/numpy.clip.html — **the documentation states plainly that when `a_min > a_max`, `clip` returns an array in which all values equal `a_max`.** No check is performed that `a_min < a_max`.
- https://github.com/numpy/numpy/issues/15693 — *np.clip behavior inconsistent with documentation* (the `minimum(a_max, maximum(a, a_min))` identity would give `a_min`, not `a_max`).
- https://github.com/numpy/numpy/issues/27960 — *BUG: `numpy.clip` violates its document when `a_min` is greater than `a_max` and the input contains `nan`*.

## What the pass establishes, and what it takes away from this leg

**(N1) RESOLVED, and it supplies the standard for the leg's headline.** DEAP — the reference
Python evolutionary framework — keeps *validity* in a **dedicated flag** (`fitness.valid`),
never inferring it from the objective's magnitude. So the convention "an extreme value is not
the same thing as an invalid individual" is **established, not something this leg discovered**.
`ga_search.evaluate` does `vals[~np.isfinite(vals)] = np.inf`, which uses magnitude *as* the
validity test; because `np.isfinite(-inf)` is `False`, a fitness of `-inf` — the value any
`log10(residual)` objective takes at a **perfect** solution, and the shape of this repo's own
weight fitness `log10(Y_0/budget)` (`solver/weight_search.py:14`) — is classified invalid and
demoted to the worst rank. The leg claims **only the measurement** that our code does this,
and the magnitude. The design principle it violates is DEAP's, cited above.

**(N2) RESOLVED, and it *removes* a claim.** The inverted-`clip` collapse is **documented numpy
behaviour**, stated in the manual. So this leg must not, and does not, report "a numpy bug".
What it reports is that `ga_search` calls `np.clip(child, lower, upper)` **without ever
checking `lower <= upper`**, and therefore inherits a documented sharp edge as a silent
population collapse. Bookkeeping, not discovery.

**(N3) RESOLVED, and it converts a taste question into a gap.** SciPy's
`differential_evolution` *derives* the dimension from paired bounds, so the mismatch that
`ga_search` accepts (`dim = lower.size`, with `upper` never checked) is **structurally
impossible** in the reference implementation. "Validate the box at entry" is standard practice.

**(N4) UNCHANGED FROM LEG 98.** Adversarial fault injection with a soundness/completeness
partition is standard method (Arguzz, arXiv:2509.10819, established in `writeup/novelty/leg_98.md`);
no methodological novelty is claimed here either.

**Net effect on the leg.** Three of the four findings are re-framed *downward* by this pass,
from "defects we found" to "documented standards our module does not meet", which is the
correct and weaker claim. The leg's only assertions are the **measurements**: which
hypothesis-violating inputs produce a wrong return value, and by how much.
