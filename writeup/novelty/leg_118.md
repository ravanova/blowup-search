## 1. What the object is, and where the classification surface lives

The module's own docstring states the physics baldly: beyond a critical radius `X_c` the
profile's linearisation changes character — an *inner* mode that vanishes like
`(X_c - X)^{1/a}` and, past `X_c`, an *outer* mode that grows like `(log(X/X_c))^{1/a}`. Every
one of `homogeneous_far_field`, `inner_mode_exponent`, `log_growth_exponent`,
`graded_norm_by_radius` and `source_of_the_row` is built on the premise that `X_c` — "the
smallest `X > 0` where `E` changes sign" — has actually been located correctly. The whole
module's classification act is binary before it is continuous: *does a turning point exist
here, and if so, where.* `critical_radius`'s implementation is:

```python
s = np.where(np.diff(np.sign(E)) != 0)[0]
if s.size == 0:
    return float("inf")
i = s[0]
t = -E[i] / (E[i + 1] - E[i])
return float(X[i] + t * (X[i + 1] - X[i]))
```

`np.sign(E[i+1]) != np.sign(E[i])` is **not** the classical sign-change test. The classical
test for "does `[X_i, X_{i+1}]` bracket a genuine crossing" is the **strict** product
inequality `E[i] * E[i+1] < 0` (Bolzano's theorem, and what `scipy.optimize.brentq` enforces:
it raises `ValueError: f(a) and f(b) must have different signs` unless the product is
strictly negative). The module's `sign`-difference test additionally fires whenever **either**
endpoint is *exactly* `0.0`, which happens at a **tangency** (a local extremum of `E` that
grazes zero without the function actually going negative) — a degenerate branch the docstring's
own physical picture explicitly excludes (the analysis assumes `E ~ -a h_c (X - X_c)`, a
genuinely transversal, sign-changing zero, not a double root). This is exactly the failure
mode the general root-bracketing literature already names for tangent/double roots.

## 4. External prior art

No originality is claimed for the hazard class itself.

- **Bracketing methods require a *strict* sign change, and tangent/double roots are a named
  failure mode for exactly this reason.** Standard treatments of the bisection method state
  the bracketing condition as `f(a)·f(b) < 0` (Bolzano's theorem), and root-finding references
  observe explicitly that a root where the function is tangent to zero (touches without
  crossing) does not satisfy this and is not detectable by a sign-change test — see e.g. the
  bisection-method expositions at
  https://lemesurierb.people.charleston.edu/elementary-numerical-analysis-python/notebooks/root-finding-without-derivatives-python.html
  and https://mwrona.com/posts/bisection-method/, and the general observation (surfaced via
  search, not a single canonical source) that float comparisons at exactly zero and tangent
  roots of even multiplicity are the standard edge cases that break a naive sign-change test.
- **A real, shipped implementation of exactly this class of bug**: SciPy's Brent's-method
  bracketing check was patched (https://github.com/scipy/scipy/pull/14007, *"Fix root
  bracketing logic in Brent's method"*, issue #13737) because multiplying `f(a)*f(b)` and
  testing `< 0` can silently misbehave; the fix compares `sgn(f(a))·sgn(f(b))`, which is the
  same family of sign-based test this module uses, and the historical existence of a bug in
  that exact family in a widely-used library is the strongest available evidence that this is
  a real, recurring failure mode and not a hypothetical one.
- **`scipy.optimize.brentq` enforces the strict form as an API contract**: it raises
  `ValueError: f(a) and f(b) must have different signs` when the endpoints do not strictly
  bracket a root — i.e., the mainstream library treats "does not strictly bracket" as an error
  to surface, not a case to silently resolve one way or another. `critical_radius` has no
  such guard; it silently accepts whatever the sign-difference test flags.
- The NaN-comparison hazard (IEEE-754 §5.11: every comparison against NaN is `False`) is the
  same vocabulary leg 106's pass used for `hilbert_pointwise.py`'s `rho*cT <= cS`, cited there
  rather than re-derived; it recurs here because `np.sign(nan) = nan` and the module's own
  `!= 0` test on a NaN-containing diff is `True` (`nan != 0` is `True` in IEEE-754/NumPy),
  which is why a poisoned `E` produces a *flagged* `nan` output rather than a silently wrong
  finite one (measured in battery gate G3 below) — the tangency defect and the NaN-comparison
  hazard point in **opposite** directions for this module, and both are reported.

# FINDINGS (appended after the audit ran; the sections above are as committed BEFORE construction)

**Gate answer: YES — a silent-corruption gap. Escalated, not patched.** Full narrative in
`experiments/journal/leg_118.md`; every case in
`writeup/data/p2_route_tpa_v1_adversarial.json`; 12 permanent regression gates banked in
`test_turning_point_adversarial.py` (7 of them PIN CURRENT, DEFECTIVE behaviour, per leg 66's
own precedent for a read-only audit).

The mechanism is exactly the one named in §1/§4 above, confirmed both by direct construction
and by a case reached through the module's own real, unmodified `effective_speed` on a real
solved profile (no monkeypatch at all — see gate G5): a tangency (`E` touches `0.0` at one
grid node and is single-signed on both sides — genuinely **no** turning point) is classified
by `critical_radius` as a real one, and that false, finite `X_c` is then accepted without
question by every downstream function, which return fully finite, plausible-looking numbers
with **zero warnings and zero exceptions**. The sharpest instance (gate G6) plants a spurious
tangency *before* a real, well-separated crossing and shows the module reports the spurious
point and **misses the real turning point entirely**, off by **27.3×** in this construction —
a magnitude that is a property of where the adversary places the two features, not a ceiling.
