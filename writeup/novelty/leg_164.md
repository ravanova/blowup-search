## 0. THE BINDING FINDING — WHAT IS ALREADY BANKED, AND WHERE THE REAL GAP IS

`DIRECTION.md` §164 asks whether the `a = 0` CLM linearization "admits ANY compact-support
representation". Read literally as a statement about the **anchor profile's support**, leg 162
already answered it and measured it, on the parked branch `leg/162-capg-v1`:

> `writeup/data/p2_route_capg_v1_corner.json` → `CAPG9_support_transfer`:
> `Omega_0 = -4X/(1+4X^2)`, `decay_exponent = -0.99999673208657`, mass outside radius `R`
> falling `0.8656 → 0.7170 → 0.6044 → 0.5221 → 0.4607 → 0.4216 → 0.4095` over
> `R = 1, 4, 16, 64, 256, 1024, 4096` — **never reaching zero**; and
> `landed_module_refuses_a_equals_zero`: `solver/first_integral.py:414` raises
> `ValueError("a must be positive; a = 0 is the degenerate limit ...")`.

So **"the a=0 anchor profile is not compactly supported" is NOT novel and this leg must not
re-report it as its finding.** Re-deriving it would be leg-53's mistake in a new costume.

**Three things the banked record does NOT contain, which is where this leg's content is:**

1. **Existence of compactly supported elements in the linearization's own DOMAIN.** The anchor
   having full support says nothing about whether the *space the perturbation lives in* contains
   compactly supported elements. `solver/spectral_certificate.py` builds the domain as the odd
   sine system `{sin k theta}, k >= 1` on `theta` in `(-pi, pi)` with `X = tan(theta/2)`, and
   that system is **complete for odd `L^2(-pi, pi)`** — so it plainly does contain nonzero
   elements vanishing on a neighbourhood of `theta = ±pi`, i.e. compactly supported in `X`.
   Nowhere in the repository is that said. Leg 162's own report is phrased as the linearization
   having "no compact-support interval at all", which is the fact about the anchor being read as
   a fact about the domain. **This leg separates them.**
2. **The weight-class dichotomy.** `spectral_certificate.py` line 119 `weight_vector` defines
   three classes (`flat`, `algebraic (1+k)^s`, `geometric nu^k`) and its own docstring calls the
   geometric class "the literature's default: analytic profiles". A `nu^k`-summable coefficient
   sequence with `nu > 1` is exactly a real-analytic function on the circle, and a real-analytic
   function vanishing on an open arc is identically zero. **No prior leg states that the
   geometric weight class — the one standard radii-polynomial work uses — contains no nonzero
   compactly supported element at all, while `flat` and `algebraic` do.** Grepped: `analytic`
   appears in `spectral_certificate.py` only as a border label and in the docstring above; there
   is no statement connecting it to support.
3. **INVARIANCE, which is the question that actually decides the gate.** `solver/finite_support.py`
   states the `a > 0` mechanism in one clause — *"every term of `R = Omega H(Omega) - E Omega_X`
   carries a factor of `Omega` or `Omega_X`, even though `H(Omega)` does not vanish outside — so
   the problem closes on the support alone"*. **The `a = 0` converse of that clause is nowhere in
   the repository.** At `a = 0` the anchor never vanishes, so the linearized residual's
   `(H h) Omega_0` term is supported wherever `H h` is, and a compactly supported subspace is not
   invariant. This is the load-bearing new statement and it is a statement about the OPERATOR,
   not about the profile — which is precisely the distinction leg 127 made and lesson 90 asks
   for.

**Restated novelty claim after the pass:** not "does the `a = 0` object have a support interval"
(banked, leg 162), but **does the `a = 0` CLM linearization admit a compactly supported INVARIANT
subspace in its own domain, in any of its own three weight classes** — a question no leg has
posed, whose answer needs the anchor's support *and* the Hilbert term's non-locality *and* the
completeness of the sine system, and which decides whether leg 162's corner is a corner of leg
126's object or of a different one.

## 3. What the pass changed about the plan, before any code was written

1. **The headline moves from the PROFILE to the OPERATOR.** Re-measuring the anchor's support
   would duplicate leg 162 `CAPG9`. The leg measures **invariance** instead, and cites `CAPG9`
   read-only for the profile fact (§0).
2. **The existence half must be reported honestly and FIRST**, because it goes *against* the
   leg's expected answer: the domain does contain nonzero compactly supported elements, so "the
   domain is unbounded" is not by itself a reason for a NO. Anything less would be building the
   conclusion into the framing.
3. **A self-consistency gate is mandatory and is load-bearing**, not decoration: the pointwise
   operator `L h = cos(theta) h - (H h) sin(theta) - sin(theta) h_theta` must reproduce
   `bordered_linearization(K)` column-for-column in exact `Fraction` arithmetic. Without it the
   leg is measuring a lookalike operator, which is failure mode 85.
4. **Lesson 90 — the control must be able to report the other answer.** The escape measurement is
   run a second time with the anchor swapped for a *compactly supported* one (the `a > 0`
   structure of `first_integral.py`) through the **identical code path**. If that does not report
   escape exactly `0`, the negative is uninterpretable. This isolates the mechanism to the
   ANCHOR's support rather than to the Hilbert transform in general — which is the difference
   between a finding and a tautology.
5. **The escape floor is minimized, not sampled.** A single compactly supported bump with nonzero
   escape proves nothing; the quantity is the *minimum* over a `K`-dimensional family of
   compactly supported perturbations, reported as a ladder in `K` and in support radius
   (discipline 72: the shape of a ladder, not its endpoint).
6. **`X_c(a)` as `a` ↓ 0 is reported as a ladder with a fitted rate**, not as the single sentence
   "`first_integral.py` refuses `a = 0`". Leg 162 banked the refusal; the *rate* at which the
   corner's own parameter leaves is new and is what makes the two objects' separation quantitative.
7. **No BLOG / TECHNICAL / figure.** `DIRECTION.md` §164's declared territory is four paths and
   names none of them; the leg-115/120/130/150/151/152/154 precedent for a territory that does not
   declare them is to ship the runner, the JSON, the novelty log and the journal. Recorded here so
   the omission is a decision and not a lapse.
8. **`capabilities.py` is NOT edited** (outside territory), so no new solver module is created —
   every operator this leg uses is either imported read-only from `solver/` or built inline in the
   runner from the module's own exact identities.
