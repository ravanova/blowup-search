## What is being checked for prior art

* **(N1)** Is "a collocation/pseudospectral method's residual is enforced only at the chosen
  nodes, and a vanishing nodal residual does not certify the equation is satisfied elsewhere"
  an established property of collocation methods, or is it something this leg would be
  inventing? If it is established, then a battery that checks the *reported* residual against
  an *independently evaluated* off-node residual is testing a known failure mode of the
  *method*, and the question becomes whether `finite_support.py`'s own `solve()` diagnostic
  (`converged: bool`) warns the caller about it or not.
* **(N2)** Is `numpy.interp`'s treatment of query points outside its data range — silent
  clamping to the boundary value with no warning — the *documented* default, or would flagging
  it be over-reading undocumented behaviour? `FiniteSupportOps._velocity_matrix` builds `U` by
  `np.interp(self.v, grid, cum[:, k])`, and the battery's sharpest finding depends on this being
  the *published* default rather than an assumption.
* **(N3)** Is "adversarial battery against a shared or standalone numerical module, checking
  that invalid/degenerate input is propagated or flagged rather than silently absorbed" an
  established audit method in this repository's own lineage, and is the vocabulary for
  "overwrites/absorbs an invalid signal without raising" already banked? (Legs 91, 96, 120 have
  already settled this; re-checked here so it is not re-derived as if new.)

**On-topic finding for (N1), partial.** The corpus states the collocation/pseudospectral
definition plainly: the residual is required to vanish **at a discrete set of collocation
points**, not everywhere. That is the method's own contract, not a defect — between-node
residual is expected to be nonzero for any finite discretization, and shrinks only as the
discretization is refined (spectral convergence). It does **not** state what a *degenerate*
choice of that discretization (too few points to constrain the physics at all) should do, which
is exactly what Q2 was run to find.

- https://arxiv.org/pdf/2308.09781, https://arxiv.org/pdf/1412.1055, https://arxiv.org/pdf/1712.09478
  — adjacent CFD/solver-verification papers, none on the specific boundary case.

**On-topic finding for (N1), and it is what shapes the battery.** The corpus states plainly
that *"one cannot look at residual values and extend the argument that a small residual implies
an equally small error"* and that a relative reduction in the residual "cannot serve as a
universal convergence criterion" independent of context (MOOSE; the USPTO filing). No source
states the *specific* degenerate case this leg measures — a collocation count so small the
system has **zero** residual rows at all — because that is a code-level pathology, not a method
question a paper would address. **This absence is itself the leg's mandate**: the general
principle ("a converged-looking residual is not proof of a solved equation off the nodes") is
published and uncontested; whether `finite_support.py`'s own `converged` flag protects a caller
from the degenerate case is not published anywhere, because it is a property of this file, not
of collocation methods in general.

### Q3
`numpy.interp documentation default behavior extrapolation clamp to boundary value outside range silent`

- https://numpy.org/doc/stable/reference/generated/numpy.interp.html — **NumPy official
  reference, `numpy.interp`.** ← the settling reference.
- https://numpy.org/doc/1.15/reference/generated/numpy.interp.html,
  https://numpy.org/doc/1.13/reference/generated/numpy.interp.html,
  https://numpy.org/doc/1.21/reference/generated/numpy.interp.html,
  https://numpy.org/doc/1.22/reference/generated/numpy.interp.html,
  https://numpy.org/doc/2.1/reference/generated/numpy.interp.html — the same page across
  releases; the clamping default is unchanged since at least 1.13.
- https://docs.scipy.org/doc/scipy/reference/generated/scipy.interpolate.interp1d.html —
  SciPy's `interp1d`, which by contrast raises `ValueError` on out-of-bounds unless
  `bounds_error=False` is passed explicitly — the documented *opposite* convention, cited only
  to show clamp-by-default is a `numpy.interp`-specific choice, not universal.
- https://docs.scipy.org/doc/scipy-1.13.0/tutorial/interpolate/extrapolation_examples.html,
  https://docs.scipy.org/doc/scipy/tutorial/interpolate/extrapolation_examples.html — SciPy's
  own tutorial on the hazards of extrapolation.

**On-topic finding for (N2), and it is the sharpest result of this pass — it sets the
mechanism from the documentation rather than by inference.** The NumPy reference states,
verbatim, for `left`/`right`:

> "left : optional float corresponding to fp, value to return for `x < xp[0]`, default is
> `fp[0]`." / "right : ... value to return for `x > xp[-1]`, default is `fp[-1]`."

and separately warns that if `xp` is not increasing "the results are nonsense" — a second,
independent hazard the module also does not guard (`_velocity_matrix`'s cumulative-quadrature
grid is built ascending internally, so that half does not apply to `U`, but nothing in
`FiniteSupportOps.__init__` checks that a caller-supplied `v_eval` is sorted or in-range
either). **This confirms the clamping is the documented default, not a bug in NumPy** — the
battery's finding is entirely about `finite_support.py` calling `np.interp` with no range check
of its own on `self.v`, not about NumPy doing anything wrong.

**Finding: nothing on-topic, and that absence is recorded so no novelty attaches to it.** None
of these treat a free-boundary Newton iteration collapsing onto a zero-measure trivial domain as
its own named failure mode; they treat well-posed free-boundary problems with a genuine nonzero
solution. The absence is expected for the same reason as leg 120's Q4: a defect of this shape in
*this* file, at *this* file's own near-zero-`c` boundary, is a bug in our code against a general
principle (Newton can converge to *any* root that satisfies the algebraic system, including a
degenerate one, if nothing in the residual excludes it), not a published phenomenon with its own
name. The battery reports it as a measured code behaviour, not a discovery.

## What this pass changed about the leg, before construction

1. **It ruled out the most likely false-positive reading of the K-battery** (N1/Q1–Q2): a
   nonzero off-node residual on a coarse collocation grid is *expected* of any correct
   collocation method and is not, by itself, evidence of a code defect — Q1 settles that. What
   Q2 leaves open, and what the battery therefore targets, is narrower and code-specific: does
   `solve()`'s own `converged` flag distinguish "the system was under-determined so nothing was
   actually checked" from "the equation is genuinely satisfied"? Nothing in the literature
   claims collocation solvers must make that distinction, so a failure to make it is reported at
   the strength the evidence supports — a code characteristic, not a violation of any stated
   theorem.
2. **It set the domain-violation mechanism from NumPy's own documentation, not from reading the
   source and guessing** (N2/Q3): `np.interp`'s clamp-to-boundary default is exactly as
   documented since at least NumPy 1.13, and SciPy's `interp1d` is cited as the *opposite*,
   equally standard convention — so the finding is "this module calls the clamping function with
   no guard of its own," never "NumPy clamps unexpectedly."
3. **It confirms this leg re-uses banked vocabulary rather than re-deriving it** (N3): the
   "silent absorption vs. flagged/propagated" framing is leg 91's and leg 120's, cited here
   rather than restated as new; this leg's only original content is *where* in
   `finite_support.py` the same shape of gap recurs.
4. **It pre-empts every novelty claim.** Nothing this leg can find is new mathematics, and the
   module under audit is dead code (superseded, zero importers) to begin with. A defect is a
   defect in our own unused file; a clean result would have been a confirmation. Every number
   reported below is a statement about code behaviour under degenerate or poisoned input, not
   about the CLM/gCLM physics the rest of the repository studies.
