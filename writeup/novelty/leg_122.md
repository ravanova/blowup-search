## 0. What this leg claims, and what it does not

**Claimed:** a *software* fact about one module — that `solver/advection_scope.py`, driven by
deliberately degenerate or poisoned inputs (malformed array order, non-finite entries, extreme
scale, malformed arguments), either does or does not return a value that looks like a plausible
answer but is not one, instead of raising or propagating a flag (`nan`/`inf`/an exception).

**Not claimed:** any mathematical novelty about the advection term, the `a`-scope finding
itself, the stagnation point, or Route-D. Like every leg in the adversarial-audit family
(69/IA, 79/PC, 80/BHN, 83, 85, 88/GCA, 89/BOA, 100/HNA, 101/OLA, 120/SUA), this leg can only
*withdraw* confidence or bank a regression test; it adds no result about blow-up and sharpens no
bound. The external-literature dimension is therefore split in two: (a) is this audit itself a
repeat of prior work — searched exactly as the sibling legs did, and answered below at (N3); and
(b) is the *specific mechanism* the pass turns up already a documented hazard rather than an
invented one — which, unusually for this family, turned out to have a direct, quotable answer
(§2), so it is reported rather than skipped.

## 2. The literature dimension — this time it resolved, not just cleared

Two of this module's five public functions reduce, at bottom, to two textbook primitives whose
own preconditions are documented outside this repository: `profile_mass` (and, through it,
`velocity_log_rate`'s `mass`/`mass_window` fields) is a **composite trapezoidal rule**, and
`stagnation_point` is a **sign-change (bracketing) root scan**. Both primitives carry a
precondition this module's docstrings never state and its code never checks.

**Query:** `numpy trapezoid trapz x array sorted monotonic requirement documentation` and
`composite trapezoidal rule reversed integration limits sign` (WebSearch, 2026-08-06).

- https://numpy.org/devdocs/reference/generated/numpy.trapezoid.html — the current NumPy manual
  states, in the function's own documentation and verified by direct fetch of the page text:
  **"If `x` is provided, the integration happens in sequence along its elements — they are not
  sorted."** The manual's own worked example demonstrates the consequence directly:
  `np.trapezoid([1, 2, 3], x=[8, 6, 4])` returns `-8.0` against `np.trapezoid([1, 2, 3],
  x=[4, 6, 8])`'s `8.0` — the identical data, reordered, returns the exact negative.
- The general calculus fact this instantiates — `int_b^a f = -int_a^b f`, i.e. reversing the
  direction of traversal negates a definite integral — is standard (any calculus reference;
  not reported as a search result because it needs none).

**What this settles.** `_trapz` in `solver/advection_scope.py` is a two-line wrapper around
exactly this NumPy primitive, with no sorting, no monotonicity check, and no docstring
mentioning order. `profile_mass`'s own docstring — `"M = int Omega dX"` — states a *mathematical*
integral, which is order-independent by definition; the code computes NumPy's *sequential*
quadrature, which is not. The gap between what the docstring promises and what the code
computes is therefore not a matter of numerical taste (rounding, tolerance, scale) but a
**documented, named difference in NumPy's own contract** that this module inherits silently.
This is the sharper, literature-backed version of what would otherwise have been an invented
adversarial case ("what if someone shuffles the array") — it is instead NumPy's own worked
example, applied to a wrapper that never re-imposes the missing precondition.

**No equivalent published precondition was sought for `stagnation_point`'s sign-change scan**,
because none is needed to state the hazard precisely: the function's own docstring says
*"smallest X > 0"*, a claim about **physical position**, while the implementation (`np.diff` over
the array **as given**, `idx[0]`) finds the smallest **array index**, not the smallest coordinate
value — those coincide if and only if the caller's `X` is already sorted ascending, a
precondition the function never checks or documents. This is a self-contained code/docstring
mismatch, verified in §5 below rather than sourced to a citation.

**(N3) Is "adversarial battery against a module, checking whether malformed order/shape/value
input is propagated, flagged, or silently absorbed" an established method?** Yes — established
by leg 91 and re-used without re-derivation by every subsequent audit leg in this family

## 3. Pre-committed decision rule (fixed BEFORE the run)

The gate is decided on this definition and no other, mirroring legs 100/101/120's discipline of
grading against an *independently computed* reference rather than the module's own internal
consistency:

> **SILENT-CORRUPTION VIOLATION** := on an input for which a reference answer is independently
> computable (a closed-form integral for `profile_mass`/`velocity_log_rate`'s mass fields, or a
> constructed exact root for `stagnation_point`), the module returns a **finite** value that
> differs from the reference by more than a stated, generous tolerance, **without** raising an
> exception and **without** the returned value (or any companion field) being `nan`/`inf`.

Deliberately **excluded** from deciding the gate, and measured and reported anyway (leg 101's
"under-reporting is a pass" pattern, adapted):

- **`nan`/`inf` output is a PASS**, whatever poisoned the input — that is the flag the gate looks
  for the *absence* of, not a violation itself.
- **Raising an exception is a PASS.** Loud failure on a malformed call (wrong shape, unknown
  `grading` key) is correct behaviour; this leg does not grade the quality or tidiness of the
  exception.
- **A `ComplexWarning` (Python's own warnings machinery firing) is graded separately from a
  fully silent case** — it is a strictly weaker flag than an exception or a `nan`, since a
  caller that does not inspect `warnings` sees nothing, but it is not *zero* signal either, so it
  is reported as its own category rather than folded into either PASS or VIOLATION.

**Discipline: magnitudes, never booleans.** Every case reports the returned value, the
independent reference, and their deviation in the sharpest available unit (exact sign check,
relative error, or absolute error in `X`-units for the root-finding cases).

## 4. Battery design, fixed before the run

**Category T — trapezoidal order-dependence** (`profile_mass`, and through it
`velocity_log_rate`'s `mass`/`mass_window`/`predicted` fields): ascending control against a
closed-form analytic integral; exact reversal; five seeded random permutations; a single
adjacent-pair transposition (the minimal possible perturbation); the propagated consequence in
`velocity_log_rate`, isolating that its polyfit-based `measured` field is order-independent while
its trapz-based fields are not.

**Category S — sign-scan array-order-dependence** (`stagnation_point`): a single-crossing ground
truth built from an analytic effective-speed profile with a known root; five seeded shuffles of
the same data (values and positions permuted together, so every array entry is still physically
correct, only its *storage order* changes); a two-crossing construction, to check whether a
shuffle merely swaps which of two real crossings is reported or fabricates a value belonging to
neither; a regression control that NaN poisoning placed strictly before the true crossing (in
correct sorted order) still returns `nan`, never a plausible finite crossing — establishing that
what fails is order, not non-finite poisoning, which the module already handles safely.

**Category C — controls** (reported as loudly as any finding, leg 91's rule): mismatched array
shapes; an unknown `grading` key; `nan`/`inf` passed as the scalars `a` or `c`; extreme dynamic
range (`1e150`) with correctly sorted order; a duplicate grid node; a window with fewer than the
required 8 points; a negative/zero `_log_fit` window bound that forces a `log` of a non-positive
number; a complex-valued profile array; the `a = 0` control (no crossing) surviving an adversarial
shuffle.
