## 2. The four defect classes I will probe, and whether each is already known ART

Written down **before** measuring, so a hit cannot be retro-fitted into novelty.

### (N1) A Krylov solver reporting the PROJECTED (Arnoldi least-squares) residual as if it were the TRUE residual

`gmres` returns `rel = ‖H y − βe₁‖/β`, computed inside the Hessenberg least-squares
problem, and never forms `‖Av − b‖/‖b‖`. `gmres_controls` computes a `rel_true` for the
well-conditioned case only; the `cond ~ 1e8` control has **no** `rel_true` field. If the
two diverge, every ladder number in this module's docstring (0.6623, 0.3596, 0.0188, …) is
a projected residual quoted as a solve quality.

**Already known art, thoroughly.** The gap between the recursively-computed and the true
residual under modified Gram-Schmidt is a classical result, not a discovery:

* Greenbaum, Rozložník & Strakoš, *Numerical behaviour of the modified Gram-Schmidt GMRES
  implementation*, BIT 37 (1997) — https://link.springer.com/article/10.1007/BF02510248
* Paige, Rozložník & Strakoš, *Modified Gram-Schmidt (MGS), Least Squares, and Backward
  Stability of MGS-GMRES*, SIAM J. Matrix Anal. Appl. — https://epubs.siam.org/doi/10.1137/050630416
  (preprint: https://www.karlin.mff.cuni.cz/~strakos/download/2006_PaRoSt.pdf)
* Giraud, Langou & Rozložník, *The loss of orthogonality in the Gram-Schmidt
  orthogonalization process* — https://www.sciencedirect.com/science/article/pii/S0898122105003366
* Björck & Paige, *Loss and recapture of orthogonality in the modified Gram-Schmidt
  algorithm* (foundational; cited throughout the above)
* Survey context: *GMRES algorithms over 35 years* — https://arxiv.org/pdf/2110.04017

The literature's headline is that MGS-GMRES **is** backward stable and the residual gap is
bounded, so a large divergence here would be a statement about *this implementation's*
extra choices (`lstsq` on the raw Hessenberg, no restart, no reorthogonalisation, `tol`
compared against the projected quantity) rather than about MGS-GMRES. Whatever I measure is
reported as a magnitude with that citation attached. **No novelty is claimed on N1 under
either outcome.**

*Query (2026-08-06):* `modified Gram-Schmidt GMRES loss of orthogonality residual gap
computed vs true residual Greenbaum Rozloznik Strakos`
*Query (2026-08-06):* `GMRES recursive residual underestimates true residual restart
deflation "residual gap" backward stability` → additionally returned
https://arxiv.org/pdf/2506.18408, https://arxiv.org/pdf/2201.09827,
https://arxiv.org/pdf/2509.17077, https://people.math.ethz.ch/~mhg/pub/JirRG-08fin.pdf,
https://link.springer.com/article/10.1007/BF01732607 (Drkošová–Greenbaum–Rozložník–Strakoš,
*Numerical stability of GMRES*).

### (N2) A stated precondition that the code never checks — `line_sweep_solve` requires `s_rho > 0`, and `outward_upwinding_holds` is a separate function nobody calls

The docstring says the exactness *requires* outward upwinding. The check exists, one
function away, and is tested (`test_port_certification.py`) — but `line_sweep_solve` does
not call it. A violating `s_rho` yields an array-shaped answer with no flag.

**Not novel; it is this repo's own recurring lesson** (`certificate_guards.py`'s
`unit_range_violation`: *"two of the three modules carry exponent hypotheses in their
docstrings that the code did not check … the docstring states the hypothesis, the code
evaluates anyway"*). External framing for the class exists too:

* *Tolerating Silent Data Corruption in Opaque Preconditioners* — https://arxiv.org/pdf/1404.5552
* *Silent error detection in numerical time-stepping schemes* — https://arxiv.org/pdf/1312.2674
* *Adversarial Inputs for Linear Algebra Backends* — https://www.mlsec.org/docs/2025-icml.pdf
* *Metamorphic testing of programs on partial differential equations* —
  https://i.cs.hku.hk/~tse/Papers/2000s/jqpdeTR.pdf

*Query (2026-08-06):* `metamorphic adversarial testing numerical linear algebra library
silent wrong result unchecked precondition upwind sweep`

### (N3) `zeros_like`/`empty_like` dtype inheritance — `leading_order_solve` does NOT cast its input to float, its sibling `line_sweep_solve` DOES

`line_sweep_solve` opens with `rhs = np.asarray(rhs, float)`. `leading_order_solve` opens
with `out = np.zeros_like(rhs)` and no cast. An integer `rhs` therefore gives an integer
output buffer and every `out[i] = prev` truncates. This is a documented NumPy footgun, not
a finding about numerics:

* numpy#7730 *Deprecate/remove silent truncation on assignment of floats into an integer
  array* — https://github.com/numpy/numpy/issues/7730
* numpy#8733 *Unexpected truncation when storing float to int array* — https://github.com/numpy/numpy/issues/8733
* numpy#21603 *`zeros_like` does not always override `dtype`* — https://github.com/numpy/numpy/issues/21603
* https://numpy.org/doc/stable/reference/generated/numpy.zeros_like.html

*Query (2026-08-06):* `numpy zeros_like integer dtype silently truncates float assignment
bug preserves input dtype`

### (N4) A NaN slipping past a comparison into a CONFIDENT verdict string — `stall_verdict`'s `flat = bool(gain < 2.0)`

`NaN < 2.0` is `False`, so a NaN ladder reports `flat: false` **and** the prose reading
*"bending => finite ill-conditioning, and more Krylov work would help"*. This is
byte-for-byte the same mechanism `certificate_guards.NAN_HINT_GE_ONE` was written for
(*"note that `NaN >= 1.0` is False, so an unguarded NaN would slip past the contraction
test"*), transplanted from a certificate verdict to an attribution verdict. **Entirely
prior art, in this repository, with a named constant.**
