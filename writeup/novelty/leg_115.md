## What is being checked for prior art

* **(N1)** `gauged_jacobian` builds a square linear system by taking one collocation row out of
  the discretized nonlinear operator and replacing it with a gauge/normalization row — is this a
  named technique in the spectral-collocation literature, and does that literature record a
  known failure mode when the number of *retained* rows runs out? If "row deletion + boundary
  bordering" is published with a documented ambiguity, the leg has a boundary to test against
  rather than an invented one.
* **(N2)** `sup_op_norm` accepts `A` as an arbitrary array and calls `np.atleast_2d` on it before
  treating dimension 0 as the domain axis and dimension 1 as the codomain axis. Is the row-vector
  default of `atleast_2d` on a 1-D input a *documented* NumPy convention (so an ambiguous input
  orientation is a real, citable hazard) rather than an invented edge case?
* **(N3)** `norm_domain`/`norm_codomain` end in `float(...)`. Is casting a NumPy complex value to
  `float` a *documented*, silent (warning, not exception) truncation, and does it differ from
  Python's own built-in `float()` on a complex number? If the library's own behavior is looser
  than the language's, a complex-valued (type-degenerate) grading exponent is a real hazard, not
  an invented one.
* **(N4)** Is "adversarial battery against a numerical module, checking that invalid or
  degenerate input is propagated/flagged rather than silently absorbed" an established method,
  and is "the code returns a plausible-looking answer that never used the poisoned input" a named
  failure mode? (Leg 91 and leg 120 already established this vocabulary; re-checked here for the
  collocation module, not re-derived.)

### Q2
`Driscoll Hale "Rectangular spectral collocation" boundary conditions row deletion ambiguities`

- https://repository.kaust.edu.sa/handle/10754/599473 — **Driscoll & Hale, *Rectangular
  spectral collocation*, IMA J. Numer. Anal. 36 (2016), 108–132.** ← the settling reference.
- https://appliedmaths.sun.ac.za/~nhale/publications/DriscollHale2015.pdf — author's own PDF of
  the same paper.
- https://kar.kent.ac.uk/58496/1/4rectdiff.pdf — a mirrored preprint of the same result, citing
  Trefethen 2000 p.135 and Boyd 2001 §6.4 for "boundary bordering" as the standard name for the
  row-replacement technique.
- https://www.researchgate.net/publication/272372545_Rectangular_spectral_collocation — same
  paper, ResearchGate listing.

**On-topic finding for (N1), and it is the settling reference.** The abstract states the
technique this module implements, by name, and flags exactly the hazard this leg's battery
targets:

> "Boundary conditions in spectral collocation methods are typically imposed by removing some
> rows of the discretized differential operator and replacing them with others that enforce the
> required conditions at the boundary. ... [A new method] avoids ambiguities that arise when
> applying the **classical row deletion method** outside of two-point scalar boundary-value
> problems."

`gauged_jacobian` is exactly the classical row-deletion/boundary-bordering method the abstract
describes: one row of `col.jacobian_matrix(om, c)` is deleted (`drop`) and replaced by a gauge
row (`GAUGES[gauge](col)`). The module's own docstring independently states the count that makes
this well-posed — `gauged_jacobian`'s own comment: *"Speed c is FIXED (gauge condition 1) and one
scalar normalization replaces one collocation equation (gauge condition 2) — the two conditions
Route-D v1 Q2 counted"* — and `writeup/4_p2_lottery/TECHNICAL_P2_ROUTED.md` §4 independently
*measures*, via singular values of the genome-map Jacobian, that **exactly two** scalar gauge
conditions are needed to remove a genuine 2-parameter symmetry kernel and isolate a nondegenerate
zero. Driscoll & Hale's paper is explicit that this exact technique — outside the "two-point
scalar boundary-value problem" case it was designed for (this module's operator is nonlinear,
non-local via the Hilbert transform, and not a two-point BVP) — is documented to carry
ambiguities. The battery's first family (**G1**) instruments the row count directly: at grid size
`J = 1` there is exactly one row available for the "one scalar normalization" and **zero** left
for the differential operator itself, which is a concrete instance of exactly the ambiguity the
paper names, not a boundary invented by this leg.

### Q3
`numpy atleast_2d 1-D array shape (1,N) row vector documentation ambiguous orientation`

- https://numpy.org/doc/stable/reference/generated/numpy.atleast_2d.html and
  https://numpy.org/devdocs/reference/generated/numpy.atleast_2d.html — **NumPy official
  documentation.** ← the settling reference.
- https://runebook.dev/en/docs/numpy/reference/generated/numpy.atleast_2d — community mirror
  of the same documentation, with a worked example.
- https://www.sfu.ca/~jtmulhol/py4math/linalg/np-matrices/ — SFU course notes, *Vectors &
  Matrices - Python for Linear Algebra*.
- https://numpy.org/devdocs/user/absolute_beginners.html — *NumPy: the absolute basics for
  beginners*.

**On-topic finding for (N2).** NumPy's own documentation and the community walkthroughs agree,
without qualification: `atleast_2d` on a 1-D array of shape `(N,)` *always* returns shape
`(1, N)` — a row, never a column. `sup_op_norm`'s own docstring states the convention it expects
("Rows of A are domain slots, columns codomain slots") but the function never checks that a
caller's flattened operator matches that orientation before calling `atleast_2d` on it — a
degenerate (rank-collapsed, e.g. functional-shaped) operator handed in as a flat 1-D array is
silently reinterpreted with codomain and domain swapped. This is a documented, citable NumPy
convention, not an invented edge case; battery family **G2** measures the resulting numeric
error on constructed cases.

### Q4
`numpy ComplexWarning casting complex values to real discards imaginary part float() documentation`

- https://numpy.org/doc/2.1/reference/generated/numpy.exceptions.ComplexWarning.html and
  https://numpy.org/doc/stable/reference/generated/numpy.exceptions.ComplexWarning.html —
  **NumPy official documentation, `numpy.exceptions.ComplexWarning`.** ← the settling reference.
- https://numpy.org/doc/2.0/release/1.5.0-notes.html — NumPy 1.5.0 release notes, where the
  warning was introduced.
- https://www.slingacademy.com/article/solving-numpy-complex-warning/ — worked example of the
  warning firing on assignment.

**On-topic finding for (N3).** NumPy's documented behavior: casting a complex value to a real
dtype "discards the imaginary part" and raises `ComplexWarning` — a `Warning` subclass, not an
exception, so it does not stop execution and is silent under any pipeline that does not
specifically elevate warnings. This is the *opposite* of Python's own built-in `float()`, which
raises `TypeError: can't convert complex to float` unconditionally (verified directly against
the running interpreter as part of this pass, not asserted from memory). `norm_domain` and
`norm_codomain` end in `float(np.max(...))`; if `alpha` (the decay-grading exponent, meant to be
a single real number per the module's docstring `(1+X^2)^{alpha/2}`) is complex — a type-level
degenerate grading parameter — NumPy's looser convention lets the whole pipeline run to
completion and return an ordinary `float` with no signal in the return value that `alpha` was
never a valid exponent. Battery family **G3** quantifies how much information the discarded
imaginary part carried before it is thrown away.

- https://www.gnu.org/software/c-intro-and-ref/manual/html_node/Handling-NaN.html — GNU C

**Confirms (N4), inherited rather than re-derived.** The vocabulary — "silently overwrites/
absorbs a poisoned value without raising" as the specific bug shape to look for, versus ordinary
IEEE-754 propagation as the default, correct behavior — is exactly leg 91/120's framing. This leg
adds no new methodological claim; it applies the same instrument to a different module.

## What this pass changed about the leg, before construction

1. **It gave family G1 a citable boundary instead of an invented one** (N1/Q2): Driscoll & Hale
   name the "classical row deletion" technique this module implements and flag it as carrying
   "ambiguities" outside the two-point scalar case this module is not. Combined with this
   repository's own measured invariant (`TECHNICAL_P2_ROUTED.md` §4: exactly two gauge
   conditions are required), the battery's target is precise: does `graded_inverse_norm` ever
   run with *fewer* real collocation rows than the two required conditions leave room for, and
   if so, what happens to the reported number?
2. **It gave family G2 a citable hazard instead of an invented one** (N2/Q3): NumPy's own
   documentation states the row-vector default unconditionally, so a 1-D array handed to the
   module's own public `sup_op_norm` is a real, documented ambiguity, not a contrived misuse.
3. **It gave family G3 a citable asymmetry instead of an invented one** (N3/Q4): NumPy's
   `ComplexWarning` is documented to be non-fatal, which is a strictly looser contract than
   Python's own `float()`. A type-degenerate `alpha` is therefore a real gap between what the
   module's docstring promises (`alpha` a real exponent) and what the code enforces (nothing).
4. **It requires passes to be recorded as loudly as failures** (N4, inherited): every input that
   the module correctly propagates or flags is part of the map, not omitted.
5. **It pre-empts every novelty claim.** Every citation above documents either a technique this
   module already implements, a library convention the module already relies on, or a
   vocabulary already banked by legs 91/120. Nothing below is new mathematics or a new method;
   a defect is a defect in this repository's file against boundaries already in print, and a
   clean result is a confirmation of robustness.
