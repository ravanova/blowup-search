## 3. Scouting run (executed before design; two findings that fix the construction)

### 3a. Leg 116's battery does not survive contact with the repaired module

`run()` in `experiments/p2_route_nka_v1_adversarial.py` aborts, in **0.9 s**, before writing
anything:

```
ValueError: farfield_modelling_error_bound: alpha is 2.0, outside the required range
[-inf, 2.0). ...  For alpha >= 2 the Hilbert term grows and the true supremum is not in
the window, so the value would be a LOWER bound reported as an upper one.
                                    (experiments/p2_route_nka_v1_adversarial.py:425, family_B)
```

So DIRECTION.md's instruction — "re-run leg 116's original battery **from the battery's own
driver**" — cannot be executed as written, and **that is itself part of the finding**: the repair
landed a guard that the battery it was built against cannot run past, and nobody noticed, because
nobody re-ran the battery.

### 3b. The blast radius of 3a is exactly one loop, and the battery is parameterised for it

Running the four family functions separately, under the repaired module:

| family | result | cases |
|---|---|---|
| `family_P()` | **runs clean** | 10 |
| `family_A()` | **runs clean** | 27 |
| `family_B(out_alphas=())` | **runs clean** | 56 |
| `family_C()` | **runs clean** | 8 |

10 + 27 + 56 + 8 = 101, against leg 116's banked **105**. The missing 4 are exactly the **B2**
loop — `farfield_modelling_error_bound(a, 0.5, 1.0)` for `a ∈ {2.0, 2.25, 2.5, 3.0}` — the only
place in the battery where a now-guarded producer is called **bare**, outside a `try`. B5 and B6
in the same family already use the battery's own `try/except → outcome "raised"` idiom (leg 116's
pre-committed criterion records `raised` as *sound but loud*), so the repair's refusal is a
correctly-classified pass everywhere the battery thought to ask for it. B2 was written as a *read
of a value*, not as a probe, because pre-repair there was no value it could fail to produce.

**Construction consequence:** no case is re-implemented and no criterion is re-invented. The
runner calls the battery's own `family_*` functions unmodified, uses `family_B`'s own
`out_alphas` keyword to hold back the four bare calls, and re-issues exactly those four through
the battery's own B5/B6 `try/except` idiom so their refusals are classified by leg 116's own rule
instead of aborting the run. Case count must return to **105**.

### 3c. The zero-regression test must be a same-process bitwise A/B

`solver/nk_bounds.py` has exactly two commits, so the pre-repair source is available as a
content-addressed blob (`d7c65df:solver/nk_bounds.py`). The runner loads it as a second module in
the same process and runs the battery **twice** — once bound to the pre-repair functions, once to
the repaired ones — so clause (b) is answered by comparing floats produced in one process rather
than by diffing two JSON files written at different times by different code. This also supplies
the **positive control that can come out differently** (lesson 90): the pre-repair pass must
reproduce leg 116's banked JSON, including its **21** false accepts and **19** load-bearing cases;
if it reproduces 17 instead, the harness — not the module — is what changed.

## 4. External prior art (verbatim queries; the two things a literature pass could bear on)

Neither of the two ideas this leg leans on is ours, and the pass exists to say so before the
construction quotes any number.

**Query 1 — the method.** `regression test after bug fix "fails before the fix" independent
verification standard practice`

* [IBM — What is Regression Testing?](https://www.ibm.com/think/topics/regression-testing) — after a revision the suite is re-executed to confirm previously-failing cases now pass *and* previously-passing cases still pass. This leg's clauses (a) and (b) are those two halves, nothing more.
* [mabl — The Difference Between Regression Testing and Retesting](https://www.mabl.com/blog/regression-testing-vs-retesting) and [Drizz — Retesting vs Regression Testing](https://www.drizz.dev/post/retesting-vs-regression-testing) — retest (same case, same inputs, same environment) precedes regression; a retest that fails returns the ticket rather than proceeding. This is the ordering the runner uses.
* [Bird Eats Bug — Software Regression Testing](https://birdeatsbug.com/blog/software-regression-testing), [Leapwork — Regression Testing guide](https://leapwork.com/blog/regression-testing/), [Testbirds — Regression Testing](https://www.testbirds.com/en/services/quality-assurance/regression-testing/) — same practice, industry framing.
* [On the Interaction between Test-Suite Reduction and Regression-Test Selection Strategies (arXiv:2207.12733)](https://arxiv.org/pdf/2207.12733) — the research framing of re-running a banked suite against a modified program.

**Verdict on query 1: fully standard practice, named and documented.** Nothing about running a
defect battery again after the fix is a contribution of this leg, and it is not presented as one.

**Query 2 — the theorem's hypotheses** (so that any constant this leg calls inadmissible is *a
documented hypothesis the code does or does not check*, never a discovery): `radii polynomial
approach hypothesis Y0 Z0 Z1 Z2 nonnegative upper bounds validated numerics`

* [A proof of Wright's conjecture (arXiv:1704.00029)](https://arxiv.org/pdf/1704.00029) — the radii polynomial `p(r) = Z_2 r^2 + (Z_0 + Z_1 - 1) r + Y_0`, with `Y_0`, `Z_0`, `Z_1`, `Z_2` *bounds* satisfying `‖T(x̄) − x̄‖ ≤ Y_0` and the operator estimates on `B(r)`; a zero is concluded inside the ball for `r` with `p(r) < 0`.
* [Rigorous numerics for ill-posed PDEs: periodic orbits in the Boussinesq equation (arXiv:1509.08648)](https://arxiv.org/pdf/1509.08648), [Validated forward integration for parabolic PDEs via Chebyshev series (arXiv:2101.00684)](https://arxiv.org/pdf/2101.00684), [Rigorous numerics for NLS (arXiv:1310.6531)](https://arxiv.org/pdf/1310.6531), [A constructive proof of the Cauchy–Kovalevskaya theorem for ODEs (arXiv:1912.03836)](https://arxiv.org/pdf/1912.03836), [Analytic continuation of local (un)stable manifolds (arXiv:1706.10107)](https://arxiv.org/pdf/1706.10107), [Computation of maximal local (un)stable manifold patches (arXiv:1508.02615)](https://arxiv.org/pdf/1508.02615) — the same constants, same hypotheses, across six independent applications.

**Verdict on query 2: the hypotheses are textbook.** They are also already recorded as such in
`solver/certificate_guards.py`'s docstring, which cites van den Berg & Lessard (*Notices AMS*
62(9):1057, 2015) and Hungria–Lessard–Mireles James (*Math. Comp.*). This leg adds no
hypothesis and re-derives none; it only checks which ones the landed code enforces.

**Not searched, deliberately:** whether a *shared* guard layer of this kind exists in
RadiiPolynomial.jl / CAPD / Arb / INTLAB. Leg 128's own novelty pass already recorded that
absence as an unaudited README-level observation and explicitly **not** a priority claim, and
nothing in this leg's gate turns on it. Re-asking would risk promoting a soft absence into a
claim by repetition.
