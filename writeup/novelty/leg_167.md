  established method with a name, outside this repo? If it is, this leg has a published

* **(N2)** Is the zero-regression half's chosen instrument — *bitwise* identity of float64

**(N1) SETTLED — the method is named, standard, and NOT novel.** The technique this leg's
clause (b) implements is *characterization testing* / *golden master*, coined by Michael
Feathers: tests that "describe the actual behavior of an existing piece of software, and
therefore protect existing behavior of legacy code against unintended changes." The published
statement of purpose is clause (b) verbatim — "verify that the modifications made to a
reference version of a software system did not modify its behavior in unwanted ways" — and the
literature states the bug-fix application explicitly: golden-master testing "helps confirm that
your bug fix doesn't inadvertently change other existing behavior."

**Two published limitations are adopted into this leg's own reporting, not discovered by it:**

1. *"Golden Master testing does not infer correctness of the results. It merely helps detect
   unwanted effects of software changes."* → **Clause (b) answering YES is NOT evidence that
   any banked number is right.** It is evidence only that the repair did not move it. This
   leg will say so in its own prose rather than let a 0-ULP count read as validation.
2. *"Volatile and non-deterministic values need to be masked... If too many elements need to be
   removed, it can render Golden Master testing impractical."* → the masking question is real
   here, and Q2 plus in-repo finding F1 below decide it.

**(N2) SETTLED, WITH A SHARP CAVEAT THAT SHAPES THE DESIGN.** The literature splits the
question exactly where this leg needs it split:

- *Across* codes/hardware/schedules, "strict bitwise reproducibility is not achievable... even
  tiny differences in floating-point operation ordering lead to round-off divergence."
- *Between versions of the same implementation*, it is: **"True bitwise reproducibility is
  achievable when comparing different versions of the same implementation, enabling CI/CD
  regression testing."**

That second sentence is precisely clause (b)'s setting — same machine, same NumPy, same BLAS,
same process, two versions of one file — so **0 ULP is the correct and defensible ask here, and
a tolerance would be the weaker instrument.** The first sentence is why the comparison must be
run **in one process against the pre-repair module loaded out of git**, and must NOT be run
against a committed JSON from another day: that is a cross-environment comparison, where the
literature says bitwise identity is *not* expected. In-repo finding F3 below shows this repo
already paid for that lesson at leg 105.

## 4. What this pass changed BEFORE construction — three findings

### F1 — Leg 115's own runner ABORTS against the repaired module, on its FIRST probe.

Measured, not argued. `experiments/p2_route_dca_v1_adversarial.py` run against current `main`
dies at `run_all()` → `g1_rows_vs_J()` → `_rows_retained(J)` line 114, with
`DecayCollocationDomainError: gauged_jacobian: J = 1 leaves 0 collocation rows...`. It is the
**first** G1 probe, so the runner never reaches G2 or G3 at all.

**This is the leg-147 shape, and leg 147 named it: "the repair landed a guard the battery could
not run past and nobody noticed."** Leg 131 found the same. It is now three for three, which
makes it a property of *repair legs in this repo*, not an accident.

Design consequence, decided here and not during construction: **the re-run harness must catch
per-case, never per-battery.** Every one of leg 115's cases is invoked in its own `try/except`
and classified into `{REFUSED, FLAGGED, SILENT_VALUE}`, so that a raise is *data* rather than
an abort. A driver that inherits leg 115's control flow would report "0 cases checked" and
could be mistaken for a pass.

### F2 — The on-disk battery is NOT leg 115's battery. It is leg 151's rewrite of it.

`git diff --stat 53f03fe 746c57a -- test_decay_collocation_adversarial.py` →
**191 insertions, 91 deletions** — leg 151 inverted leg 115's 7 pins *in the same commit as the
repair*. Running the on-disk file today prints `all decay_collocation ADVERSARIAL checks passed
(15 checks)`, and its own trailer says so: "REPAIRED at leg 151. G1/G2/G3's 7 pins are
INVERTED — they now assert the guards."

**Running that file is not an independent check of the repair. It is the repairer grading its
own homework, and it is exactly lesson 90: a control that cannot come out differently.** Those
15 checks pass *because* leg 151 wrote them to pass against the code leg 151 wrote.

Design consequence: **leg 115's cases are read out of git at `53f03fe`** — the pre-repair
revision of both the battery and the runner — and re-derived from leg 115's *own* case
definitions and its banked `writeup/data/p2_route_dca_v1_adversarial.json` magnitudes, never
from the on-disk post-151 file. Leg 105 established this exact discipline ("imported unmodified,
bound to the pre-repair module read out of git via a `sys.modules` substitution, never relying
on the repair's own test file"); this leg inherits it rather than reinventing it.

### F3 — The zero-regression comparison must be same-process, not JSON-versus-JSON.

Leg 105 measured this and it is banked: comparing against a committed JSON from another day
gave a ~2.1% discrepancy on a converged-to-noise-floor quantity, identical between pre-repair
and post-repair modules, i.e. **environment/BLAS drift that predates both repairs** — so a
JSON-literal comparison would have reported a regression that does not exist. Leg 147 saw the
same: 22 of 763 leaves moved by ≤3 ULP, 6 of them on paths that never call the module under
audit at all.

This agrees exactly with Q2's split (bitwise identity holds *between versions of the same
implementation*, not *across environments*). Design consequence: **clause (b) is a same-process
bitwise differential** — pre-repair `solver/decay_collocation.py` loaded from blob `a595dcb`
into the live interpreter alongside the current one, `sha256` over raw float64 bytes, 0 ULP as
the criterion. Leg 151 used the same instrument; this leg's independence is **not** in the
instrument but in the *enumeration*: leg 151 chose which 1672 quantities to compare, and a
re-run of leg 151's own quantity list would inherit whatever leg 151 failed to look at. **This
leg enumerates its own coverage set from the module's public surface, and reports the count it
reaches against leg 151's 1672 as a magnitude, not as a target to match.**
