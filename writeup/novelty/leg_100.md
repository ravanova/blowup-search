## What is being checked for prior art

The audit targets four behaviours the module's code exhibits by construction. For each, the
question is whether the *mechanism* is a known, published floating-point hazard (in which case
the leg reports "known hazard, instance found here") or would be a novel observation (it is not).

* **(N1)** IEEE-754 says every NaN compares **unordered** with everything. So a guard of the
  form `if x <= 0: continue` or `if r > best:` **silently skips** a NaN candidate rather than
  propagating it. Is this a recognised, documented hazard for max/min-style reductions?
* **(N2)** `pow(1.0, x) == 1.0` **even for `x` = NaN**, by IEEE-754 special case. The module's
  `decay_weight(X, alpha) = (1 + X^2)**(alpha/2)` therefore returns an exactly-1.0 weight at the
  grid node `X = 0` under a NaN grading exponent. Is that a standard-mandated special case
  rather than a numpy quirk?
* **(N3)** Is Python's builtin `max(a, b)` known to be non-propagating for NaN in the second
  argument (returns `a`), unlike `np.max` which does propagate?
* **(N4)** Is "fuzz a numerical library with NaN/Inf-poisoned and degenerate inputs, looking for
  silently wrong finite output rather than crashes" an established method — i.e. is the METHOD of
  this leg standard practice, so the leg claims no methodological novelty?

## Queries, verbatim, with the links returned

### Q1
`IEEE 754 NaN unordered comparison silently skipped maximum reduction hazard numerical software`

- https://grouper.ieee.org/groups/msc/ANSI_IEEE-Std-754-2019/background/predicates.txt — IEEE
  754 working-group note on comparison predicates: quiet vs signalling predicates, and the
  explicit rationale that unordered NaN operands of ordered comparisons can "corrupt the logic of
  the program and then disappear without a trace."
- https://grouper.ieee.org/groups/msc/ANSI_IEEE-Std-754-2019/background/minNum_maxNum_Removal_Demotion_v3.pdf
  — the 754-2018 removal of `minNum`/`maxNum`, driven precisely by inconsistent NaN handling in
  min/max reductions.
- https://groups.google.com/d/topic/comp.lang.fortran/MwVfrvUowHU — Fortran `MAXVAL` with
  Inf/NaN; same reduction hazard in another language.
- https://blog.ngzhian.com/ieee754.html — summary of the unordered-comparison rule.
- https://github.com/elm/core/issues/1050 — a language-level bug report of the same rule.

**On-topic finding for (N1) and (N3).** The hazard is documented at the level of the standard
itself, including the exact "disappear without a trace" framing. Anything this leg finds of this
shape is a **known hazard instantiated in our code**, not a new phenomenon. The 754-2018
minNum/maxNum removal note is the closest published statement that max-style reductions are the
canonical place it bites.

### Q2
`numpy pow 1.0 ** nan returns 1.0 IEEE 754 pow special cases nan exponent`

- https://docs.python.org/3/library/math.html — `math.pow`: "`pow(1.0, x)` and `pow(x, 0.0)`
  always return 1.0, even when `x` is a zero or a NaN."
- https://numpy.org/doc/stable/reference/generated/numpy.power.html — numpy's `power`, same
  IEEE-754 special-case family.
- https://github.com/numpy/numpy/issues/8931 — historical platform inconsistency for
  `numpy.power(1, nan)`, since settled to the standard's behaviour.

**On-topic finding for (N2).** Confirmed a **standard-mandated special case**, not a numpy bug.
So a NaN grading exponent producing an exactly-1.0 weight at `X = 0` is expected behaviour of
the primitive; the audit question is only whether our code lets that survive into a returned
number.

### Q3
`fuzzing numerical library NaN Inf input validation silent wrong result computer-assisted proof norm computation`

- https://dl.acm.org/doi/pdf/10.1145/3729394 — "Automatically Detecting Numerical Instability"
  (ACM FSE/TOSEM 2025): fuzzing that targets *silently corrupted output* (NaN/Inf and wrong
  finite values), not just crashes.
- https://github.com/ISU-PAAL/soft-assertion-fuzzer — the accompanying tool.
- https://yangchenyuan.github.io/files/ICSE23-NablaFuzz.pdf — NablaFuzz: silent
  wrong-value bugs in AD libraries, same "wrong finite output beats a crash" framing.
- https://arxiv.org/pdf/2201.06589 — FreeFuzz; NaN/Inf oracle discussion.

**On-topic finding for (N4).** The method is standard software-engineering practice with a
current literature. **This leg claims no methodological novelty**; its only claim is the
measured behaviour of one specific module.

# FINDINGS (appended after the battery ran; the pass above is unchanged)

**Gate answer: YES — a silent-corruption gap, six distinct mechanisms**, all of them the
*same* published IEEE-754 hazard (N1/N3) instantiated at five different sites, plus one
initialiser that survives an emptied filter as a plausible answer. Per the pass's own
commitment, none of this is claimed as a discovery: it is a known hazard, located here.

| # | site | poisoned input | returned | clean value |
|---|---|---|---|---|
| 1 | `conformal_check` / `jacobian_identity_error` | one NaN grid node | **1.517287054473293e-04**, bit-identical | 1.517287054473293e-04 |
| 2 | `jacobian_identity_error` initialiser | all-NaN 16-node grid | **(0.0, 0.0)** = exact agreement | — |
| 3 | `family_op_norm` | one NaN operator entry | **0.0** (`arg = -1`) | 661.207572 |
| 4 | `family_op_norm` | NaN in the true maximizer of `extra` | **105.435714** (**2.1053× understatement**) | 221.978372 |
| 5 | `holder_H_constant` random arm | NaN γ / γ<0 / NaN or Inf grid node | **0.0** | 0.891421 |
| 6 | all Inf twins | one Inf | same wrong value; warnings **[1, 0, 0]** over 3 calls | — |

Structural cause, measured by AST: **0 `raise`, 0 `assert`, no `isfinite`/`isnan`/`isinf`/
`warn`** across 7 public entry points.

**Confirming (N2):** `decay_weight([0,1,10], alpha=NaN) = [1.0, nan, nan]` — the standard's
`pow(1.0, NaN) = 1.0` special case, exactly as the pass predicted. Recorded as **latent,
not live**: the sup over the grid still sees the other NaNs.

**Confirming the pass's "no methodological novelty" clause (N4):** the method is the
standard NaN/Inf fuzz-for-silent-wrong-output practice of the 2023–2025 literature above,
and the leg's only claim is the measured behaviour of one module.

**What is NOT broken:** `HolderNorm.sup_part` / `.seminorm` / `.__call__` reduce through
`np.max` and propagate NaN on every poisoned exponent and every poisoned grid node. The
difference between finding 5 and this is one function name — python's builtin `max` versus
`np.max`.

**Disposition, per the pass's clause 3:** `solver/holder_norms.py` was NOT edited.
`test_holder_norms_adversarial.py` pins the silence and must be *inverted*, not weakened,
when a guard lands. Full detail: `experiments/journal/leg_100.md`.
