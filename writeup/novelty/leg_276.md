## 4. Family 3 — the `0.71465` provenance chain, corrected as printed

PUB2 printed, at two sites (§3.2 and §3.5), a **two-step** chain: round leg 163's largest sampled
ratio to `1.3993`, invert, then round the result **up** in the fifth decimal by `7.0e−06`. Neither
step reproduces. `1/1.3993 = 0.7146430`, which rounds to `0.71464`, not `0.71465`; and leg 163's
banked witness is `implied_sigma_min_lower_witness = 0.7146549471256172`, verified this pass to be
exactly `1/1.39927667753796` — the **full-precision** ratio — which rounds to `0.71465` with no
round-up at all.

Both sites now print the one-step chain. The leg brief asked which framing is actually wrong: it
is **the printed chain**, not the number — `0.71465` is right, its `≤` direction is right (leg
250's fix), and `0.0908 ≤ 0.71465` stands.

**One thing this leg found that leg 270 did not flag, and repaired in the same sentence.**
Rounding the witness to five decimals is a round-**down** of `4.947e−06`, so `σ_min ≤ 0.71465`
is, strictly, `4.9e−06` tighter than the witness itself licenses — the same class of defect as
N1–N4, at a site leg 270 verdicted `MATCH on the value`. The digit `0.71465` was **not** changed
(it is printed at six sites and is one of the 116 byte-exact values this leg's gate protects);
instead §3.2 now states the witness bound itself, `σ_min ≤ 0.71465495`, and names `0.71465` as
the display form. Fixing it by moving the digit would have been the wrong trade.

**N6, in the same paragraph.** `0.868155` was seed 0's `M = 8192` convergence value, presented as
a figure "over four data"; the four-data max is `0.868153885807814`. Now printed as **`0.8681539`**,
