# Leg 292 — Route-CAPA novelty pass: what `capabilities.py` claims NOW, before the
# second-generation audit touches it

**Leg.** 292, Route-CAPA, `leg/292-capa-v2`. **Merge base.** `4db7d1c` (leg 0/ORCH
integration cycle following leg 291's landing). **Date.** 2026-08-07.

## Why this is not a literature search

Same family as leg 71 (Route-CAP, the first-generation audit): there is no external
paper to pre-empt here, the "prior art" is the repository's own index and its own
drift detector. The discipline is identical — pin, in writing, what the artifact under
audit currently claims and what the existing automated check does and does not cover,
**before** running anything that could be read back as having been aimed at the
answer it found.

## Prior art: leg 71 already exists, and its finding constrains this leg's scope

Leg 71 (`10fed85`, `e742f6d`) ran the first-generation audit at merge base `e203b52`,
42 rows / 40 distinct test files. Its finding, load-bearing for this leg:

> **`test_capabilities.py` (the drift detector) enforces exactly three things**: the
> `test` field is non-empty, the cited path exists on disk, and `validated` is longer
> than 20 characters. **It does not check that the cited test runs, passes, or has
> anything to do with the module citing it.** Existence is checked; greenness and
> relevance are not.

Reading `test_capabilities.py` at this leg's merge base confirms nothing has changed
in the detector since: its five tests are still
`test_every_solver_module_is_indexed`, `test_entries_are_complete_and_point_at_real_files`
(existence + length, no execution), `test_objects_are_distinct_enough_to_search_on`,
`test_the_search_finds_the_thing_route_m_nearly_rebuilt`, and
`test_superseded_modules_say_so`. **The gap leg 71 named is still exactly the gap
today.** This leg's contribution has to be in the same two categories leg 71 could not
fully close in one pass: whether every currently-cited test is actually green at HEAD,
and whether any row's `validated`/`test` prose has gone stale relative to what the
module now does.

## What has changed since leg 71 (expected drift, stated before measuring it)

Per this leg's brief: roughly 220 legs and at least 4 new solver modules have landed
since leg 71's `e203b52` base, `solver/bc_weighted_sobolev.py` named explicitly. The
intervening `git log -- capabilities.py` shows the append-only convention
(`ORCHESTRATION.md` §5a: a landing leg appends its own row) has in fact been followed
— repeated commits of the form "register solver/X.py in capabilities.py" or
"capabilities.py gets its APPENDED entry" appear at legs 55, 57, 125, 128, 176, 187,
256 (`bc_weighted_sobolev.py`), plus several `Leg 0: ORCH` corrections to existing rows
(hl_rescaled.py's stale "~1%" figure at leg 78, critical_dissipation.py and
holder_norms.py annotations, fractional_boussinesq.py, derivative_hat/target_norm.py,
nk_bounds.py + certificate_guards.py, energy_coercivity.py's novelty cap, chen_inviscid
_certificate.py).

**Prediction, made before running the diff**: because every landing leg is contractually
required to append its own row on the same commit that adds its module, the
*module-completeness* axis (leg 71's "S1 missing file" category) is likely already
clean — this is a self-maintaining property of the append-only convention, not
something that needs 220 legs of drift to break. The higher-probability findings are
in the two categories leg 71's own audit could not fully certify:
- **S3 red at HEAD** — a test that was green when its row was written but has since
  been invalidated by a later change to the module it doesn't itself touch (leg 71
  found exactly two of these: `test_fractional_boussinesq.py` G6 and
  `test_profile_newton.py`'s inverted assertion — both flagged, deliberately left
  unfixed by leg 71 per its own charter).
- **S4 name/coverage drift** — a `validated` field whose prose has been overtaken by a
  later leg's finding on the same module without the row being corrected (this is
  exactly the pattern of leg 78/hl_rescaled.py, corrected in a `Leg 0: ORCH` commit,
  not by leg 71 itself — meaning corrections have historically come from the
  orchestrator's integration commits reading a leg's finding, not from a dedicated
  capabilities-audit leg. Whether every such correction landed, or some slipped
  through between leg 71 and now, is this leg's actual question.)

## Distinctness from leg 71's territory

Leg 71 committed at `e203b52`/`10fed85`/`e742f6d`. Nothing between that point and this
leg's merge base `4db7d1c` is a `capabilities.py` self-audit leg (`git log --oneline --
capabilities.py` shows only append/correction commits from landing legs and the
orchestrator, never a second dedicated audit leg number). This leg is the second
generation the brief names it as, not a redundant re-ask.

## Plan, pinned before execution

1. `ls solver/*.py` (excluding `__init__.py`, which is an empty package marker, not a
   module with a capability row) vs. `grep '"module"' capabilities.py` — module-set
   diff, both directions (S1: missing rows; the "ghost" direction: rows for deleted
   modules).
2. For every distinct `test` field cited, confirm the file exists (S1's sibling on the
   test side, already covered by the existing detector's assertion but re-verified
   independently here rather than trusted).
3. **Run every distinct cited test file** under `.venv/bin/python <file>`, at this
   leg's merge base, and record pass/fail + wall time. This is the check
   `test_capabilities.py` does not do and leg 71 established as the actual audit
   surface.
4. For any RED result, do not silently patch the solver — report it as a finding, same
   as leg 71's two priority-bug flags, unless the fix is a trivial, obviously-correct
   restoration of a `capabilities.py` prose field (e.g. correcting a `test` pointer to
   the file that actually exercises the module, leg 71's `ga_search.py` precedent).
5. Spot-check a sample of `validated` fields against the module's current behavior for
   staleness (S4), prioritizing the four modules named as new since leg 71.
6. Report exact counts: modules audited, missing, stale (and how), red tests, files
   corrected — never a yes/no.

This file is committed in its own commit, ahead of the test-run results and any edit
to `capabilities.py`.
