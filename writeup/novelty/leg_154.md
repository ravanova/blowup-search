Two failures, both of which the adopted predicate has to fix or declare:

**(i) `±inf` raises the wrong type.** `OverflowError` is not a `ValueError`, so it escapes
leg 121's own CONTROL's `except ValueError` and escapes any caller written against the
module's documented failure mode. Worse, the *obvious* tightening — testing integrality as
`p == floor(p)` — **admits `inf` outright**, because `floor(inf) == inf` is `True`. The
integrality clause alone is not merely imprecise on infinity; it is **blind** to it. So the
adopted predicate needs an explicit finiteness clause, and that clause is **measured
necessary**, not defensive decoration:

```
if not np.isfinite(pf):            # NECESSARY: floor(inf) == inf, so integrality alone admits inf
    raise CriticalDissipationDomainError(...)
if pf != np.floor(pf):             # NECESSARY: the gate's subject, p = 1.9
    raise CriticalDissipationDomainError(...)
```

This is [SEI CERT **FLP04-C**, *Check floating-point inputs for exceptional
values*](https://cmu-sei.github.io/secure-coding-standards/sei-cert-c-coding-standard/recommendations/floating-point-flp/flp04-c/)
(Java twin [NUM08-J](https://wiki.sei.cmu.edu/confluence/display/java/NUM08-J.+Check+floating-point+inputs+for+exceptional+values)),
whose stated rationale is the same one that bites here — comparisons involving exceptional
values do not behave the way the guard's author assumes. It is the **same class of
polarity/blindness error leg 152 found one leg ago** (`np.any(d <= 0)` defeated by a NaN,
CERT NUM07-J) and the same class leg 130 found in leg 106's prescribed predicate
(`rho = 1e300` is finite). **This is now the fourth consecutive repair leg in which the
finding leg's prescribed predicate did not survive measurement** — legs 150, 151, 152, and
now 154.

**(ii) `1e300` is accepted, and is NOT patched.** Declared as a residue, with the reason
stated before the differential runs: a 301-digit `p` makes `lambda_power`'s loop a resource
exhaustion (unbounded matmul chain, growing `n`, eventual `MemoryError`) — **loud, not
silent**. The gate's subject is *silent substitution of a different exponent*, and any cap on

## Q3 (PRIOR ART) — is "reject a non-integral float where an integer is required" published?

Thoroughly, and the repair claims nothing here.

* [**PEP 357**](https://peps.python.org/pep-0357/) is the canonical statement of the exact
  design question this repair answers. Its motivating sentence is the finding: slicing
  "can't just use the existing `__int__` method … If slicing used `__int__`, floating-point
  numbers would also become legal slice indexes and that's clearly an undesirable
  behaviour." `int(p)` in this module is precisely the `__int__`-style coercion PEP 357 was
  written to stop being used as a validator. `operator.index` is its remedy.
* **NumPy applies exactly this remedy** to a numeric-order argument of the same shape:
  `np.linspace`'s `num` began raising `DeprecationWarning` when it "cannot be safely
  interpreted as an integer" in **1.13** ([release
  notes](https://docs.scipy.org/doc/numpy-1.13.0/release.html)) and is now the hard
  [`TypeError: object of type <class 'numpy.float64'> cannot be safely interpreted as an
  integer`](https://github.com/numpy/numpy/issues/15345). This is the closest published
  analogue to the repair and it is in the very library this module runs on.

**A DELIBERATE DIVERGENCE FROM NUMPY, DECIDED HERE AND RECORDED BEFORE THE PATCH.** NumPy's
`operator.index` route rejects **even exactly-integral floats** — `np.linspace(0, 1, 3.0)`
is refused. This repair does **not** adopt that, and takes the weaker `float(p).is_integer()`
predicate instead, because leg 121's C4 battery **pins `p = 3.0` and `np.float64(3.0)` as
correctly ACCEPTED**, and the gate's clause (b) forbids moving any previously-passing input.
Adopting `operator.index` would satisfy clause (a) and **fail clause (b)**. The stricter
predicate is the better library design and the wrong repair for this gate; the reason is
recorded so it is not silently rediscovered as an improvement (the discipline leg 129 used
when it refused a 6%-faster `velocity_hat` that would have normalized signed zeros).

* Leg 121's own Q-pass already banked the defect class — [CWE-197 *Numeric Truncation
  Error*](https://cwe.mitre.org/data/definitions/197.html) and
  [numpy/numpy#7730](https://github.com/numpy/numpy/issues/7730) — and already established
  the load-bearing point that **the integrality restriction here is a property of Route-E's
  compactified sine basis, not of the physics**: the fractional-Laplacian literature treats
  the order as continuous, so a caller has every reason to expect a non-integer `s` to be
  legitimate. Not re-derived, cited.
